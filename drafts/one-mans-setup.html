[ Hero image: TK. ] One Man's Setup Phillip Harrington Install as little as possible, run everything else in Docker, and keep one shared set of local services that every project plugs into. Every project gets a real-looking address like reuselists.test, with real HTTPS, so local behaves like production.

Every developer's setup is a pile of decisions they made once and stopped thinking about. These are mine, with the reasons, because the reasons are the useful part.

Install as Little as Possible

The rule I keep coming back to: if it can run in a container, it does. Software I install directly on my Mac is software I have to update, untangle and eventually uninstall. Software in a container is a line in a file, and it goes away when I'm done with it.

The few things that do live on the Mac come from Homebrew, never from installers downloaded off websites. One command installs, one updates everything, one removes. On mine right now:

  • git and the GitHub CLI, the AWS CLI, Node, and mkcert (more on that below).
  • ImageMagick and the WebP tools. Every image on this site went through them: resized, cropped, converted to WebP, in two sizes. Doing it by command means doing it the same way every time.
  • GoAccess, which turns server logs into a readable traffic report.
  • curl, for asking a server a question directly, many times a day.
    •

    Apps come from Homebrew too, not just command-line tools: Docker Desktop, iTerm2, VS Code, Inkscape, and the non-dev ones like Spotify, Slack and Zoom. Updating everything on the machine is one command.

    PHP and Composer are in there too, which breaks my own rule a little. They're for quick one-offs. Every real project runs its PHP in a container, pinned to the version production runs.

    Docker

    Docker Desktop is the one big install, and it comes from Homebrew like everything else. Every project has a Docker Compose file that says exactly what it needs to run: which PHP, which web server, which settings. Clone the repo, run one command, and it's up. No "works on my machine," because my machine isn't really involved.

    It also means a project from five years ago still runs, on the PHP it was written for, without me keeping five years of PHP versions around.

    Basic Services

    Most of my projects need the same few things: a database, a way to look at the database, somewhere for email to go, and a front door. Rather than give every project its own copies, I keep them in one Compose project I call basic services, and every other project joins its network.

  • MySQL. One database server for every project, each project with its own database. Same version as production, 8.4, because a database that behaves differently locally is a bug you haven't met yet. The exception is a project that needs a particular setup, like a primary and a replica to test replication. Those run their own, in that project.
  • Adminer. A database admin tool in a single PHP file, running in its own container. It's a browser tab, not an app, and it's there when I need it.
  • Mailpit. Every email any project sends lands here instead of in someone's inbox. Nothing local ever emails a real person by accident. It replaced MailHog, which I'd used for years and which stopped getting updates.
  • An nginx proxy. The front door, on ports 80 and 443, for every project at once. Each project gets a few lines of config, and the proxy sends reuselists.test to Reuse Lists, streamtostory.test to Stream to Story, and so on. Projects don't fight over ports.

    • Redis isn't in there. It runs only in the projects that actually need it, when they need it, instead of always. A tool for looking inside it would be a different story: like Adminer, a web app I'd want handy across projects, it would go in basic services. At my last job I used a simple Redis viewer for exactly that.

    [ The Redis viewer from the last job: name it, or leave it unnamed. ] .test and Real HTTPS

    Every project gets an address ending in .test, like reuselists.test. That ending is reserved for exactly this: it will never be a real domain on the internet, so there's no chance of a local address colliding with somebody's real site. One line in /etc/hosts points all of them at my own machine.

    Why .test and not .dev, which a lot of us used for years? Because .dev became a real top-level domain, owned by Google, and in late 2017 Chrome started forcing every .dev address to HTTPS. Local sites broke overnight, all over the world, and .test became the usual choice. One more quirk: type a bare reuselists.test into the address bar and some browsers search for it instead of going there, because they don't recognize the ending. Type the https:// the first time, and they remember.

    And they all use HTTPS, with a real padlock. mkcert makes a little certificate authority that only my machine trusts, and signs a certificate for each project. The proxy serves them.

    Why bother? Because production is HTTPS, and things behave differently without it. Cookies marked Secure don't get sent. Some browser features refuse to work. I once shipped login cookies without the Secure flag for months, because the code that was supposed to notice HTTPS never saw it. The closer local is to production, the fewer of those I find in production.

    The Apps

    The list of things I actually open every day is short:

  • iTerm2, for the terminal. Most of my day happens in it.
  • VS Code, for code. Free, fast enough, and everything else plugs into it.
  • Inkscape, for anything drawn: logos, icons, the occasional diagram.
  • Spotify, always.
    •  And Claude

    There's one more thing in the terminal these days: Claude, Anthropic's AI, working right alongside me in the same project. A good chunk of the work on this site, and the setup above, got done that way. How that actually works, the good and the weird, is a post of its own.

    Keep your setup in a repo, even a small one: the Compose file, the proxy config, a README with the steps you'd otherwise forget. Mine is basic services. The next time you get a new computer, or a new teammate, it's an afternoon instead of a week.
