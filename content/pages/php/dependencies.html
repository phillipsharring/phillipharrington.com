Your Dependencies Are Your Code Too Phillip Harrington

Security Headers finished the work on your own code. But on most sites, your own code is the small part. One composer require brings in a package, and the packages it needs, and the ones they need. Every one of them runs with all the access your app has. When one of them has a hole, your site has the hole. Nobody visiting can tell whose code it was.

What's a Dependency?

Code your project uses that someone else wrote and maintains: a library you installed with Composer, or with npm for JavaScript. The ones you asked for are direct dependencies. The ones they brought with them are transitive, and there are usually more of those.

What's a Lock File?

composer.json says what you'll accept: "guzzlehttp/guzzle": "^7.4" means any 7.x from 7.4 up. composer.lock records exactly which version of every package was installed, transitive ones included. Commit both. composer install installs what the lock file says, so every machine gets the same code. composer update picks new versions within your rules and rewrites the lock file.

That's the catch. A lock file keeps you on the versions you had the day you made it, forever, until someone runs an update.

What's an Advisory?

A published notice that some versions of a package have a known security hole: which versions, how bad, and which version fixes it. Many get a CVE number, a public id for the vulnerability. Packagist, Composer's package list, collects them for PHP packages, and composer audit checks your lock file against them.

In March 2024, Andres Freund, a Microsoft engineer who works on PostgreSQL, noticed that SSH logins on a test machine were using more processor time than they should, about half a second slower. He followed it into xz, a compression library almost every Linux system has, and found a backdoor. A contributor had spent around two years earning the project's trust before slipping it in. It was caught weeks before it would have reached the stable releases of the major Linux distributions. How It Works
  1. You require a package. Composer picks a version and writes it in the lock file.
  2. Months pass. The lock file keeps installing that same version, everywhere.
  3. Someone finds a hole in it. The maintainers fix it in a new version, and an advisory is published.
  4. Your site is now running code with a published hole: published means attackers can read about it too.
  5. composer audit compares your lock file with the advisories and lists what it finds. composer require and composer update mention it too.
  6. You update the package, run your tests, and deploy. The audit comes back clean.

Steps two to four happen without you. Only five and six take any effort, and they only happen if you make them a habit.

Try It

A project that depends on Guzzle, a popular HTTP client, and was set up a while ago. You'll make one on purpose, by asking for the version from October 2021. In an empty folder, make version.php, which reports what's installed:

Now ask Composer for Guzzle 7.4.0:

docker run --rm -v "$PWD":/app -w /app composer:2 composer require guzzlehttp/guzzle:7.4.0 Only the new part: After the package name, the version you want. This asks for exactly 7.4.0 and nothing else.

It refuses: "Your requirements could not be resolved to an installable set of packages." Recent versions of Composer know which versions have published security advisories, and won't pick one. That guard is the whole lesson in one message. For this lesson only, switch it off, and ask again:

docker run --rm -e COMPOSER_NO_SECURITY_BLOCKING=1 -v "$PWD":/app -w /app composer:2 composer require guzzlehttp/guzzle:7.4.0 docker run --rm -v "$PWD":/app -w /app php:8.4-cli php version.php New here: Set an environment variable in the container, as in PHP Files. Composer reads this one and stops refusing versions with known security problems.

This time it installs, and says why it shouldn't have: "Found 14 security vulnerability advisories affecting 1 package." Never set that variable in a real project. Then version.php says Guzzle 7.4.0, after a screenful of warnings: "Implicitly marking parameter ... as nullable is deprecated." Code from 2021 uses a style PHP 8.4 has started to complain about. Old dependencies don't stay still; the language moves on around them. Two more questions worth asking any project:

docker run --rm -v "$PWD":/app -w /app composer:2 composer outdated --direct docker run --rm -v "$PWD":/app -w /app composer:2 composer why guzzlehttp/psr7 What's new: List installed packages that have newer versions out. Only the ones your project asked for itself, not what they pulled in. Show which packages require the one you name.

The first lists what's behind, and by how much. The second says why a package you never asked for is installed: Guzzle requires it.

In PHP
  • composer audit: known advisories for what's in the lock file. It exits non-zero if it finds any, so a script or a CI job can stop on it.
  • composer outdated --direct: your direct dependencies with newer versions.
  • composer why vendor/package: what pulled a package in.
  • composer update vendor/package --with-all-dependencies: update one package, and whatever it needs updated along with it.
  • composer install --no-dev in production, from the committed lock file. Never composer update on a server.
  • For JavaScript, npm audit does the same against npm's advisories.
    •  Gotchas
  • Your version rules can hide a major upgrade. ^7.4 never installs 8.0. When the fixes only come in a new major version, composer update says nothing; composer outdated shows it, and the upgrade takes real work.
  • Installing a package runs its code. Composer plugins and scripts run at install time, which is why Composer asks before allowing a plugin (allow-plugins). Read what you're allowing. A package name one letter off from a popular one is a classic trap.
  • Copied files aren't audited. A JavaScript library downloaded into public/js years ago isn't in any lock file, so no audit will ever warn you about it.
  • Abandoned packages get no fixes. If nobody maintains it, the next hole stays open. Composer marks packages their authors have abandoned; plan to replace them.
  • Data from a library is still input. A response parsed by Guzzle, a value decoded by a JSON library, a header from an API: it came from outside your code. The Oracle at Delphi had it on the wall, right next to "know thyself": never trust input, whoever's code carried it in.
    • Break It

    Your project installed cleanly, and it works. Ask Composer what's known to be wrong with it:

    docker run --rm -v "$PWD":/app -w /app composer:2 composer audit New here: Check every installed package against the published security advisories, and list any that match. Found 14 security vulnerability advisories affecting 1 package: ... | Package | guzzlehttp/guzzle | | Severity | high | | CVE | CVE-2022-29248 | | Title | Cross-domain cookie leakage | | Affected versions | >=7,<7.4.3|>=4,<6.5.6 | ...

    Fourteen when this was written; more will have been found by the time you run it. That one from 2022 means Guzzle 7.4.0 could send cookies set by one site to another. Others leak Authorization headers when a request is redirected. No attack on your code needed: your site would do it for the attacker, on its own, through a library you installed once and forgot. Each advisory has a link with the details, which attackers read too.

    You had to switch off a guard to get here. A real project gets here without one: a lock file made before the advisories were published installs exactly as written, with no complaint, on every machine, for as long as nobody looks.

    Fix It

    Asking for exactly 7.4.0 wrote exactly 7.4.0 into composer.json, so a plain update would stay put. Ask for any 7.x from 7.4 up instead, and let Guzzle's own dependencies move too, since the newer Guzzle needs newer versions of them:

    docker run --rm -v "$PWD":/app -w /app composer:2 composer require "guzzlehttp/guzzle:^7.4" --with-all-dependencies docker run --rm -v "$PWD":/app -w /app composer:2 composer audit docker run --rm -v "$PWD":/app -w /app php:8.4-cli php version.php Only the new parts: The ^ means "7.4 or any newer 7.x." It's in quotes because some shells give ^ a meaning of their own. Let the packages Guzzle depends on update too, as far as they need to.

    Guzzle and two of its dependencies upgrade, the lock file is rewritten, and the audit says "No security vulnerability advisories found." version.php reports the new 7.x version, without the warnings. In a real project, the next step is your test suite, then committing the new composer.lock, then deploying it.

    In March 2016, a developer removed all of his packages from npm after a dispute over a package name. One was left-pad, eleven lines that added spaces to the start of a string. Thousands of projects depended on it, most without knowing, through other packages, and their builds broke all at once. npm restored it within hours, and changed its rules so that a package others depend on can't simply be withdrawn.

    Add composer audit to your CI, and run it on a timer as well as on every push: once a week, on a project nobody has touched, is when it earns its keep. Advisories are published about code you haven't changed, so a project that passed last month can fail today. A failing build in your inbox beats finding out from someone else.
