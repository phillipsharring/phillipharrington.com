Passwords: password_hash() and Nothing Else Phillip Harrington

Sooner or later, plan on someone getting a copy of your database: through an injection, a backup left somewhere public, a laptop, an employee. What they can do with the passwords in it depends entirely on how you stored them. In PHP, there's one right answer, and it's two functions long.

What's a Hash?

A one-way function: text goes in, a fixed-length string comes out, and there's no way to run it backward. The same input always gives the same output. You store the hash, not the password. When someone logs in, you hash what they typed and compare. You never need to know the password itself, and you never could.

That's not encryption. Encryption is two-way: with the key, you get the original back. A password you can decrypt is a password an attacker can decrypt, once they find the key. Passwords get hashed, never encrypted.

What's a Salt?

Random bytes, different for every password, mixed in before hashing and stored next to the hash. Without a salt, two people with the same password have the same hash, and an attacker can hash a list of guesses once and check every account at once. With a salt, every account has to be attacked on its own.

Slow on Purpose

Hashes like md5 and sha1 were built to be fast, for checking files. Fast is exactly wrong for passwords: it means fast guessing. Password hashes, like bcrypt and Argon2, are slow on purpose, and you can choose how slow. A fifth of a second is nothing to a person logging in once. To someone making millions of guesses, it's everything.

In 1979, Robert Morris and Ken Thompson of Bell Labs published "Password Security: A Case History," about how Unix stored its passwords. They had found that a stolen password file could be checked against a list of common words quickly. Their fix included a random salt for every password and a deliberately slow hash. Both ideas are in password_hash() today. How It Works
  1. Someone signs up with a password.
  2. password_hash() makes a new random salt, hashes the password with it slowly, and returns one string with everything in it: the method, the cost, the salt and the hash.
  3. You store that string. Nothing else, and never the password.
  4. When they log in, password_verify() reads the method, cost and salt from the stored string, hashes what they typed the same way, and compares.
  5. If it matches, password_needs_rehash() asks whether the stored hash is weaker than today's default. If it is, you have the password in hand, so you hash it again and save the new one.

A stored hash looks like this:

$2y$12$iMdR6ImRzDQjCz70NLr/J.1Gqc01nnKvPyi1eJ1Y3ZL7hkJ4eDP0S

$2y$ is bcrypt. 12 is the cost: each step up doubles the work, and PHP 8.4 raised the default from 10 to 12. The next 22 characters are the salt, and the rest is the hash.

Try It

Hash the same password twice:

docker run --rm php:8.4-cli php -r 'echo password_hash("sunshine", PASSWORD_DEFAULT), "\n", password_hash("sunshine", PASSWORD_DEFAULT), "\n";'

Two different strings, because each got its own salt. Both still check out. Paste one of them into this, in single quotes so the shell leaves the $ signs alone:

docker run --rm php:8.4-cli php -r 'var_dump(password_verify("sunshine", $argv[1]));' 'PASTE-THE-HASH-HERE'

bool(true). Change sunshine to Sunshine, and it's bool(false). Notice how long each command takes, too. Most of that is Docker starting, but some of it is bcrypt, doing its job.

What's new:

An argument after the code. PHP hands it to the code as $argv[1], the same way a script gets its arguments.

New to Docker or the terminal? Tools has the setup.

In PHP
  • password_hash($password, PASSWORD_DEFAULT) to store. Today the default is bcrypt; it can change in a future PHP, which is why it's the one to use.
  • password_verify($typed, $storedHash) to check. It returns true or false.
  • password_needs_rehash($storedHash, PASSWORD_DEFAULT) after a successful login, to upgrade old hashes as people come back.
  • PASSWORD_ARGON2ID is available too, if your PHP was built with it. Argon2 won the Password Hashing Competition in 2015. Either it or bcrypt is a fine choice.
  • A VARCHAR(255) column for the hash. Today's are 60 characters; leave room for tomorrow's.
    • Gotchas
  • No md5, no sha1, no sha256, not even with a salt. They're all fast. A salt stops the shortcut of attacking every account at once, but each account still falls at millions of guesses a second.
  • Don't write your own. Hashing many times in a loop, mixing in the username, adding a secret: every homemade scheme is weaker than password_hash(), and none is ever reviewed as hard.
  • Don't change the password before hashing it. No trimming, no lowercasing, no stripping characters. Take it exactly as typed, any length, any characters, UTF-8 included.
  • bcrypt only reads the first 72 bytes. Anything after is ignored, so two long passwords that start the same match each other. It rarely matters for a real password; it's one reason to consider Argon2.
  • Say "wrong email or password," never which one. Telling someone the email is right tells an attacker who has an account. See Expressive HTTP Response Codes.
  • Passwords go nowhere else. Not in logs, not in error messages, not in an email confirming signup. A request logger that saves every form field saves every password. Never trust input to be harmless to keep.
    • Break It

    Four members, the way a lot of sites stored them for years: md5. In a folder, make users.php with the members and the passwords they chose:

    Then naive.php, which stores them as md5 and writes the table to leaked.txt, as if someone had copied your database:

    docker run --rm -v "$PWD":/app -w /app php:8.4-cli php naive.php

    The usual: a throwaway PHP container, your folder shared in as /app, running one script.

    alice@example.com 0571749e2ac330a7455809c6b0e7af90 bob@example.com 0571749e2ac330a7455809c6b0e7af90 chloe@example.com 9cc2ae8a1ba7a93da39b46fc1019c481 dana@example.com 936ca969784bfe546a096ff543db8270

    Alice and Bob have the same hash, so they have the same password. Nobody has guessed anything yet, and that's already given away. Now the attacker's side. Make words.txt, a hundred common passwords, one per line (copy it from the examples repo, from the same folder as crack.php), and crack.php, which tries each one, then each one with a number from 0 to 9999 on the end, for up to five seconds:

    docker run --rm -v "$PWD":/app -w /app php:8.4-cli php crack.php leaked.txt Cracked alice@example.com: sunshine Cracked bob@example.com: sunshine Cracked dana@example.com: dragon2024 1,602,327 guesses in 0.3 seconds. Cracked 3 of 4.

    Your numbers will differ a little. Three of four, in a third of a second, on a laptop, in PHP, with a list of a hundred words. Real attackers use lists of millions of leaked passwords and graphics cards that make billions of md5 guesses a second. Only Chloe's survived, because "correct horse battery staple" isn't on the list and is too long to guess character by character.

    Fix It

    Make fixed.php. It stores the same members with password_hash(), writes leaked-fixed.txt, then logs Alice in the way a login page would:

    docker run --rm -v "$PWD":/app -w /app php:8.4-cli php fixed.php

    Alice's and Bob's hashes are different now. "sunshine" logs Alice in, "Sunshine" doesn't, and an old cost-10 hash is flagged for rehashing. Then give the attacker the same five seconds against the new leak:

    docker run --rm -v "$PWD":/app -w /app php:8.4-cli php crack.php leaked-fixed.txt 32 guesses in 5.3 seconds. Cracked 0 of 4.

    From over a million to a few dozen. Each guess now costs about a sixth of a second, and because every member has their own salt, each guess has to be made again for every member. "sunshine" is on the list, and the attacker didn't get that far. Given days, they'd eventually find it; weak passwords are weak. But they'd find them one account at a time, slowly, instead of the whole table before lunch.

    In 2009, an attacker got into RockYou, a company that made apps for social networks, and found its 32 million passwords stored as plain text. The list was published, and it became one of the most widely used wordlists in password cracking: real passwords, chosen by real people. Three years later, millions of LinkedIn's password hashes were posted online. They were unsalted sha1, and a large share were cracked within days.
