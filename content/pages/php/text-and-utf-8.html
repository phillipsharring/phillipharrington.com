Text and UTF-8 Phillip Harrington

Strings said a string is a row of bytes, and quietly assumed one byte is one letter. That's true for plain English, and false for "café," for "Zoë," for Chinese, for emoji, and for a good share of your visitors' names. This is the whole story: what the bytes mean, how PHP counts them, and the four places on every trip where text gets mangled. Content Types introduced the charset; this is what it's for.

What's a Character Set?

A list that gives every character a number. Computers only store numbers, so text is stored as the numbers of its characters, and both ends have to agree on the list.

ASCII

The old American list, from 1963: 128 characters, numbered 0 to 127. English letters, digits, punctuation, and some control codes like the new line. Each fits in one byte, with room to spare.

Unicode

One list for every writing system, with well over a hundred thousand characters, each with a number called its code point: U+0041 is A, U+00E9 is é, U+1F44D is 👍. Unicode is the list. It doesn't say how to store the numbers as bytes. That's the encoding's job.

UTF-8

The encoding nearly the whole web uses. It stores each code point in one to four bytes. The ASCII characters keep their old one-byte form, so plain English text is the same in ASCII and UTF-8. Everything else takes more: é is two bytes, c3 a9, and an emoji is four. Use UTF-8 for everything, everywhere, and say so at every boundary.

Bytes and Characters

So "café" is four characters and five bytes. PHP's plain string functions, strlen(), substr(), strtoupper(), work in bytes. The mb_ functions (for "multibyte") work in characters: mb_strlen(), mb_substr(), mb_strtoupper(). When it's text a person typed or will read, use the mb_ ones.

UTF-8 was designed in September 1992 by Ken Thompson and Rob Pike, two of the people behind Unix, and the first sketch of it was drawn on a placemat in a New Jersey diner. They needed it for Plan 9, the operating system they were working on, and had it running within days. Its trick, keeping ASCII exactly as it was, is why it could take over a web that was already mostly ASCII. How It Works

Text crosses a boundary every time it moves, and at each one, both sides have to agree it's UTF-8. Follow one name, "Zoë," from a form to a page:

  1. The page. Your form page says it's UTF-8, in the Content-Type header and in <meta charset="utf-8">.
  2. The form. The browser sends what's typed in the page's encoding. A UTF-8 page sends UTF-8: Zo%C3%AB.
  3. PHP. $_POST['name'] is the bytes as sent. PHP doesn't check them. You do, because never trust input: anyone can send bytes that aren't UTF-8 at all.
  4. The database. The table, and the connection to it, both have to be UTF-8. In MySQL that's utf8mb4, the subject of Character Sets and Collation.
  5. The page again, or an email. Out it goes, with the charset said again. Email has its own rules: the body needs a charset in its Content-Type, and a subject line with anything but ASCII has to be encoded specially.

Get one wrong, and you get mojibake: UTF-8's two bytes for é read as two separate one-byte characters, so "café" turns into "cafÃ©." When you see Ã followed by another odd character, some boundary read UTF-8 as something older.

Try It

Bytes and characters, side by side. In a folder, make bytes.php:

docker run --rm -v "$PWD":/app -w /app php:8.4-cli php bytes.php

strlen() says 5, mb_strlen() says 4. substr() took four bytes and cut é in half, leaving c3, which isn't a character at all. strtoupper() skipped the é. The two "café"s look identical and aren't equal: one has é as one code point, the other as an e plus a combining accent. And "Read wrong" is mojibake, made on purpose.

Now a page that takes a name, checks it, and counts it. Make index.php:

docker run --rm -it -p 8000:8000 -v "$PWD":/app -w /app php:8.4-cli php -S 0.0.0.0:8000

Open http://localhost:8000 and type a name with an accent, or an emoji. It counts characters and bytes separately. Then, from a second terminal, send "café" both ways, first as UTF-8 and then as a single Latin-1 byte for é:

curl 'http://localhost:8000/?name=caf%C3%A9' curl 'http://localhost:8000/?name=caf%E9'

The first says 4 characters, 5 bytes. The second is refused: E9 alone isn't valid UTF-8, and mb_check_encoding() caught it before it got anywhere near the page or a database.

New to Docker or the terminal? Tools has the setup.

In PHP
  • mb_strlen(), mb_substr(), mb_strtoupper(), mb_strtolower(), mb_str_pad(), and, new in PHP 8.4, mb_trim() and mb_ucfirst(): the character-counting versions.
  • mb_check_encoding($input, 'UTF-8'): is this valid UTF-8? Ask it of every string from outside.
  • mb_convert_encoding($text, 'UTF-8', 'Windows-1252'): convert text you know is in an older encoding, like an old CSV export.
  • htmlspecialchars() assumes UTF-8, and since PHP 8.1 it replaces broken bytes with � rather than returning nothing.
  • default_charset, a setting, is UTF-8 out of the box. It's what PHP puts in the Content-Type it sends.
  • mb_encode_mimeheader(): an email subject that isn't plain ASCII.
  • grapheme_strlen(), from the intl extension, counts what a person would call one character. It isn't in the Docker image by default.
    • Gotchas
  • A length limit in bytes rejects real names. "Twenty characters" checked with strlen() means ten for someone writing in Greek. Count with mb_strlen(). (Databases count characters too, in a VARCHAR.)
  • Cutting text with substr() breaks it. A summary cut at 100 bytes can end in half a character, which shows up as � or makes the whole string invalid. Use mb_substr().
  • Some characters are several code points. An emoji family, a flag, an accent added separately: mb_strlen() counts the code points, so one visible character can count as five. For most limits that's fine. For exact counting, use the grapheme_ functions.
  • Text that looks the same can be different. é as one code point and é as e plus an accent don't compare equal. Searching and logins can trip on it. Normalizer::normalize(), in intl, turns both into one form.
  • MySQL's utf8 isn't UTF-8. It stops at three bytes, so emoji can't be stored. Use utf8mb4, in the tables and the connection.
  • The invisible BOM. Some editors start a UTF-8 file with three bytes, EF BB BF, called a byte order mark. In a PHP file, they're output before <?php, and headers already sent, as in Output. Save as UTF-8 without a BOM.
    • The word for garbled text is Japanese: mojibake, roughly "character transformation." Japanese computing had several competing encodings for decades, so text shown in the wrong one was common enough to need a name. Everyone else borrowed it.

    When text looks wrong, stop guessing and look at the bytes: bin2hex($text) in PHP, or xxd file.txt | head in the terminal. c3 a9 is a UTF-8 é. A lone e9 is a Latin-1 é. c3 83 c2 a9 is UTF-8 that got encoded twice. ef bb bf at the start is a BOM. Once you can see which, you know which boundary to fix.
