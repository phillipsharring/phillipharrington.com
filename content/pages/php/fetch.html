fetch() and AJAX Phillip Harrington

In JavaScript, the data came with the page. Often a page needs more after it's loaded: search results as you type, the next set of comments, a check that a username is free. JavaScript can make its own request, get the answer, and change just part of the page, while the rest stays where it is. On the server, that request is a request like any other.

What's fetch()?

The browser's JavaScript function for making an HTTP request. You give it a URL, and optionally a method, headers and a body, and it gives you back the response:

const response = await fetch('/search.php?q=blue'); const body = await response.json();

await means wait for the answer without freezing the page. The response has a status, headers and a body, exactly the ones from Request and Response.

What's AJAX?

The name for the idea: a page that talks to the server in the background and updates itself. It stood for Asynchronous JavaScript and XML, from when the answers were usually XML. Now they're almost always JSON, and the tool is fetch(), but people still say AJAX.

The way to make background requests, XMLHttpRequest, came from Microsoft, for the web version of Outlook, and shipped in Internet Explorer 5 in 1999. Other browsers copied it. It got its famous name in 2005, when Jesse James Garrett called the approach "Ajax" in an essay, around the time Gmail and Google Maps showed what it could do. fetch() is the modern replacement. How It Works
  1. Something happens on the page: the visitor types a letter.
  2. JavaScript calls fetch() with a URL on your server.
  3. The browser sends the request, with your site's cookies, as it would for a page.
  4. PHP answers, usually with JSON and Content-Type: application/json, instead of a page.
  5. JavaScript reads the answer and changes the part of the page that needs it.

From PHP's side, nothing is new. It's a request, with a method, a query string, maybe a body. Your JavaScript made it, but nothing proves that: anyone can call the same URL with curl and send whatever they like. Never trust input, even from your own scripts. An endpoint checks everything a form handler checks.

curl 'http://localhost:8000/search.php?q=b'

The same JSON the page got. Now type more than 50 letters into the box. The server answers with a 400 and a reason, and the page shows the reason, because the script checked response.ok instead of assuming.

In PHP
  • header('Content-Type: application/json') and echo json_encode($data): an endpoint's answer.
  • http_response_code(400) and the rest still matter. Send a real status with an error, so scripts can tell success from failure.
  • A fetch() that sends a FormData body arrives in $_POST, like a form. One that sends JSON doesn't: it's in php://input, and the JSON lesson reads it.
  • A fetch() that changes something is a request that changes something: POST, and the same CSRF protection as a form.
    • Gotchas
  • fetch() only fails when the network does. A 404 or a 500 is still a response, and fetch() hands it over as if all went well. Check response.ok, or response.status, every time.
  • Answers can arrive out of order. Type fast, and the answer for bl can land after the one for blu, showing the wrong results. Real search boxes cancel the old request with an AbortController, or wait until typing stops.
  • A PHP error in the middle breaks the JSON. A warning printed into the response turns it into text that isn't JSON, and response.json() throws. Keep display_errors off, and read the error log instead.
  • Another site's URL is a different matter. fetch() to your own site just works. To another origin, the browser asks that server's permission first. That's CORS, two lessons from now.

    • In the developer tools' Network tab, right-click any request and choose Copy, then Copy as cURL. You get a curl command with the same URL, headers, cookies and body. Paste it into a terminal, and you can replay the request, change it, and see what the server does, without the page in the way.
