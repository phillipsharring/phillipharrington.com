CORS Phillip Harrington

In fetch() and AJAX, a page asked its own server for JSON, and it just worked. Point the same fetch() at a different site, and the browser blocks it, unless that site says this page may read its answers. The rule is the same-origin policy, and the way a server makes exceptions to it is CORS: Cross-Origin Resource Sharing.

What's an Origin?

The scheme, host and port of a URL, from Anatomy of a URL. https://example.com is one origin. Change any of the three, and it's another:

  • http://example.com: a different scheme.
  • https://api.example.com: a different host, even on the same domain.
  • https://example.com:8443: a different port.
    •

    The path doesn't count. Every page on one origin is the same origin.

    What's the Same-Origin Policy?

    The browser's rule that a page's JavaScript can read answers only from its own origin. Without it, any site you visited could quietly fetch() your email or your bank, with your cookies, and read the answer. The rule stops the reading. It doesn't always stop the request from being sent, which is why CSRF is a separate problem.

    What's CORS?

    The server's way of saying "this other origin may read my answers." It's a set of response headers. The main one, Access-Control-Allow-Origin, names the origin allowed, or * for any. If it matches the page's origin, the browser hands the answer to the script. If not, the script gets an error, and the answer is thrown away.

    The Preflight

    For anything beyond a plain GET or a form-style POST, such as a JSON body, a custom header, or a PUT or DELETE, the browser asks first. It sends an OPTIONS request, the preflight, saying which method and headers it wants to use. Only if the answer allows them does it send the real request.

    The same-origin policy never applied to <script src>: a page could load a script from anywhere. So before CORS, sites shared data by sending it as a script. You'd ask for /data?callback=show, and the server answered with show({...}), which called your function with the data. It was called JSONP. It only did GET, and it meant running whatever the other site sent as code on your page. CORS replaced it. How It Works

    A page on http://localhost:8001 POSTs JSON to an API on http://localhost:8000:

    1. The browser sees a different origin, and a JSON body, so it sends a preflight first: OPTIONS, with Origin: http://localhost:8001, Access-Control-Request-Method: POST and Access-Control-Request-Headers: content-type.
    2. The API checks the origin against its allow list and answers with Access-Control-Allow-Origin: http://localhost:8001 and the methods and headers it accepts.
    3. The browser compares. It matches, so it sends the real POST.
    4. The API answers, with Access-Control-Allow-Origin again, and the browser lets the script read it.

    Every step is the browser's doing. curl doesn't care about any of it, and neither does any program that isn't a browser. CORS protects your visitors from other sites' pages; it doesn't protect your server from anyone. The Origin header is a header, and from anything but a browser it says whatever the sender wants. Never trust input: your API still checks who's asking, the way it would without CORS.

    Only the new part:

    Port 8001 on your computer, connected to port 8000 in this container. Each container has its own 8000, but your computer has only one, so the second site gets 8001.

    Open http://localhost:8001: "Hello from the API." The API's terminal shows two requests, an OPTIONS and then the POST. That's the preflight. Now change the allow list in api/index.php to some other origin, and reload. The page says it's blocked, and the browser's console names CORS as the reason. Change it back.

    Then ask the way a browser does, and the way anything else can:

    curl -i -X OPTIONS -H 'Origin: http://localhost:8001' -H 'Access-Control-Request-Method: POST' http://localhost:8000/ curl -i -H 'Origin: http://evil.example' http://localhost:8000/

    The first is a 204 with the permission headers. The second has no permission at all, and gets the message anyway. A browser would hide it from the page; curl just shows it.

    In PHP
  • $_SERVER['HTTP_ORIGIN'] is the requesting page's origin. Compare it against an allow list, exactly, with in_array(..., true).
  • header('Access-Control-Allow-Origin: ' . $origin) only for an origin on the list.
  • Access-Control-Allow-Methods and Access-Control-Allow-Headers answer the preflight's questions.
  • Access-Control-Allow-Credentials: true lets the browser send cookies along. It only works with a named origin, never *.
  • header('Vary: Origin') whenever the answer depends on the origin, so a cache in the middle doesn't hand one origin's answer to another.
    • Gotchas
  • Echoing back any Origin is the same as *, only worse. Copying the request's Origin into the answer without checking it allows every site, and with credentials on, lets every site read your logged-in visitors' data. Use an allow list.
  • localhost and 127.0.0.1 are different origins. So are http and https, and the same host on two ports. Allow exactly the origins your pages use.
  • The preflight needs an answer too. An app that only handles GET and POST turns away the OPTIONS request, and the real one never gets sent.
  • The browser won't tell your script why. A CORS failure looks like a network error to JavaScript, on purpose. The details are only in the console.
  • Errors need the headers as well. If your 500 page or your proxy's error page has no Access-Control-Allow-Origin, the script sees a CORS error instead of your error.

    • If you control both sides, put them on one origin: serve the API at /api on the same site, with a reverse proxy sending those paths to the API server. Same origin, no preflights, no headers to get wrong.
