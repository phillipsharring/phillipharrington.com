CRUD Phillip Harrington

Single Point of Entry gave every page a row in a table of routes. Look at the routes of almost any app, and most of them come in sets of four, one set for each kind of thing it keeps: notes, users, orders, posts. Make one, show it, change it, delete it. That set has a name.

What's CRUD?

Create, Read, Update, Delete. Each one has a SQL statement, from the SQL lessons, and a usual way to ask for it over HTTP:

  • Create: INSERT. A form that POSTs to /notes.
  • Read: SELECT. GET / for the list, GET /notes/1/edit for one.
  • Update: UPDATE. A form that POSTs to /notes/1.
  • Delete: DELETE. A button that POSTs to /notes/1/delete.

    • HTML forms can only send GET and POST, so a page in a browser uses POST for all three changes and tells them apart by URL. An API can use PUT, PATCH and DELETE too; that's REST, two lessons from now.

    The relational database comes from Edgar F. Codd's 1970 paper, "A Relational Model of Data for Large Shared Data Banks," written at IBM. Donald Chamberlin and Raymond Boyce, also at IBM, designed a language for it called SEQUEL. The name was already a trademark, so it became SQL, which is why people still say it both ways. Repeated side story: the SEQUEL story is also told in SQL. Keep one, make this a callback, or cut it. How It Works
    1. Read is a GET. It changes nothing, so it's safe to reload, bookmark and share.
    2. Create, Update and Delete are POSTs. Each checks its input, runs one prepared statement, and answers with a 303 redirect back to a GET page: Post/Redirect/Get, from Request and Response.
    3. Update and Delete first look the thing up. If it isn't there, that's a 404, not a quiet nothing.
    4. Bad input gets the form back, with the reason and a 422.

    An empty note is a 422, with the reason. Updating a note that isn't there is a 404. A method the app doesn't take is a 405. The browser's required and maxlength never ran, and the server caught it anyway: never trust input. docker compose down -v stops it and throws the data away.

    In PHP
  • $db->prepare(...)->execute([...]) for every statement with a value from outside. Always. See SQL Injection.
  • $db->lastInsertId() after an INSERT, for the new row's id.
  • $statement->rowCount() after an UPDATE or DELETE, for how many rows it touched. With MySQL, an update that changes nothing counts 0 rows, even when the row exists, which is why the example looks the note up first.
  • header('Location: /', true, 303) and exit after every change.
  • mb_strlen(), not strlen(), to count characters, so "café" is four, matching the VARCHAR(500) limit in characters. See Text and UTF-8.
    • Gotchas
  • Never delete with a link. A GET must not change anything. Browsers prefetch links, crawlers follow them, and a "delete" link gets clicked by things that aren't people. Delete is a POST, from a button.
  • This example leaves out CSRF protection. Any site could make your browser submit these forms. A real app needs a token in every form that changes something; see CSRF.
  • Anyone can change anything here. There are no users, so there's nothing to check. In a real app, Update and Delete check that the note belongs to whoever is asking, and answer 404 when it doesn't.
  • Delete is forever. Many apps "soft delete" instead: a deleted_at column, set rather than removed, and every Read that leaves those rows out. It's kinder to people who click the wrong button.

    • When you add a new kind of thing to an app, write its create, find, update and delete functions before any page, and try them from a small script. Every page after that is just a form and a call, and the SQL is in one place when you need to change it.
