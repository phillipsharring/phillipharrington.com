Observers Phillip Harrington

Factories ended with a signup that keeps collecting jobs: send the welcome email, add to the newsletter, write the audit log, tell the team. Each one is a reasonable thing to do after a signup. None of them is the signup's business. The observer pattern lets the signup say "this happened" and leave the rest to whoever is listening.

What's an Observer?

Code that has asked to be told when something happens, so it can react. You'll also hear it called a listener or a subscriber. The thing being watched, the subject, keeps a list of observers and calls each one when it has news. It doesn't know what they do.

Events

In most PHP code today, the news is an event: a small object that says what happened, like UserSignedUp, with the details as properties. An event dispatcher keeps the lists, one per kind of event, and passes each event to everything listening for it.

Smalltalk-80, the system MVC came from, built this in. Any object could have "dependents." When a model changed, it sent itself changed:, and every dependent, usually a view, got update: and redrew itself. That's how a desktop MVC view kept up with its model: it was an observer. How It Works
  1. When the app starts, it registers listeners with the dispatcher: "when UserSignedUp happens, call these."
  2. Someone signs up. Signup saves the account.
  3. It makes a UserSignedUp event and hands it to the dispatcher.
  4. The dispatcher calls each listener for that event, in the order they were registered, passing it the event.
  5. Each listener does its one job. Signup carries on, none the wiser.

A new job after signup is a new listener and one line of wiring. Signup doesn't change, and doesn't need retesting.

In PHP
  • __invoke() makes an object callable, so a listener can be a small class with its own dependencies, passed in through its constructor, and still be called like a function.
  • $event::class gives an object's class name, which is how the dispatcher finds the right list.
  • PSR-14 is the standard interface for event dispatchers (psr/event-dispatcher), and Symfony and Laravel both have one. Use theirs in a real app; the idea is the one here.
  • PHP also ships SplSubject and SplObserver, the classic Gang of Four version: attach(), detach(), notify() and update(). You'll see them in older code more than new.
    • Gotchas
  • It's harder to see what happens. Reading Signup.php no longer tells you an email gets sent. Keep all the wiring in one file, like app.php, so there's one place to look.
  • One listener's exception stops the rest. In this dispatcher, if the welcome email throws, the newsletter and the audit log never run, and the error reaches Signup anyway. Decide whether a listener's failure should stop the signup, and catch it in the listener if not.
  • Slow listeners make slow requests. They run during the request. Sending an email can take seconds; a listener that puts a job on a queue takes milliseconds. The Queues project is about that.
  • Events are for things that happened. Name them in the past tense (UserSignedUp, OrderShipped), and don't use them to ask a question and wait for an answer. That's a method call.
    • One of my apps sent a verification email the moment anyone signed up. Someone found that useful: they signed up strangers' addresses, over and over, and each one got an email from us they never asked for. The fix was to send nothing at signup, limit how much mail the app would send, and put a bot check on the form. The listener that sends an email is the one to look at hardest, because it's the one that reaches outside your app. Repeated side story: the signup inbox bomb story is also told in Rate Limiting. Keep one, make this a callback, or cut it.

    Add one line to the dispatcher during development: log the event's class and how many listeners heard it. When "the email didn't go out," you'll know in seconds whether the event was never dispatched or nobody was listening.
