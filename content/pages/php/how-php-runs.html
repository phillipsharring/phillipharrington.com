How PHP Actually Runs: nginx and PHP-FPM Phillip Harrington

Every Try It so far has used PHP's built-in server, php -S, sometimes with nginx in front of it. That's the right tool on your own computer, and the wrong one on a live server. Most real PHP sites run two programs: a web server, usually nginx, and PHP-FPM, which keeps PHP ready to run. Document Root said a .php file gets run instead of sent. This is how.

The Pieces PHP's Built-in Server

One program that does everything: listens for requests, sends files, runs PHP. By default it handles one request at a time. PHP's own documentation says it's for development and shouldn't be used on a public network. Keep it for that.

PHP-FPM

The FastCGI Process Manager. It's a master process that starts a pool of PHP workers and keeps them waiting. Each worker runs one request at a time, then waits for the next. The master starts more when it's busy, up to a limit, and stops some when it's quiet. PHP-FPM doesn't speak HTTP at all. It only talks to a web server.

FastCGI

The protocol a web server uses to hand a request to PHP-FPM and get the answer back, usually on port 9000. The request arrives as a set of named values: the script to run, the method, the query string, the headers. PHP turns those into $_SERVER, $_GET and the rest.

Apache and mod_php

The older way, still common on shared hosting: PHP built into Apache itself, as a module, so every Apache process can run PHP. Apache can also use PHP-FPM, the same way nginx does.

The first way to run a program from a web server was CGI, from the NCSA server team in 1993: start a new program for every request, hand it the request, and send whatever it prints. That's slow when the program is PHP, which has to start up every time. FastCGI, from the mid-1990s, keeps the program running between requests. PHP-FPM began as a separate patch, and became part of PHP itself in 2010, in PHP 5.3.3. How It Works
  1. A request reaches nginx.
  2. If it asks for a file that exists in the web root and isn't PHP, like style.css, nginx sends it and is done. PHP never hears about it.
  3. Otherwise, nginx connects to PHP-FPM and sends the request over FastCGI, including which script to run: index.php, for most apps.
  4. The master gives it to a free worker, which runs the script from the top.
  5. What the script prints goes back to nginx, which sends it to the visitor. The worker waits for the next request.

The worker is reused, but nothing your code made survives. Variables, objects, open database connections: all of it is gone when the request ends, and the next request starts with nothing. That's why sessions and databases exist. It's also why one bad request can't leave a mess behind for the next one.

The pool has a limit, pm.max_children. When every worker is busy, new requests wait in line. If they wait long enough, nginx gives up, and the visitor gets the 504 from Access and Error Logs.

In PHP
  • PHP_SAPI (or php_sapi_name()) says how PHP is running: fpm-fcgi, cli-server for php -S, cli in a terminal, apache2handler for mod_php.
  • $_SERVER['SCRIPT_FILENAME'] is the file the web server told PHP to run.
  • fastcgi_finish_request(), under PHP-FPM only, sends the response to the visitor and lets the script keep working afterward. Handy for a slow job the visitor doesn't need to wait for.
  • max_execution_time limits how long a script may run. PHP-FPM has its own limit too, request_terminate_timeout.
    • Gotchas
  • Forget the PHP block, and nginx sends your source code. Without the location ~ \.php$ part, index.php is just a file that exists, and nginx sends it as a download, every line of it. Test a new server with curl before anything else.
  • Both sides need the files, at the same path. nginx tells PHP-FPM a path to run. If PHP-FPM sees the files somewhere else, it can't find the script, and the visitor gets "File not found." That's why both containers mount the code at /app.
  • Only run PHP files that exist. try_files $uri =404 in the PHP block stops an old trick, where a path like /uploads/cat.jpg/x.php got an uploaded image run as PHP. Uploads are input, and, as I may have mentioned, never trust input; this one line keeps them from running.
  • The pool size is a memory budget. Every worker uses memory, so pm.max_children times the memory per worker has to fit on the server. Too few workers, and visitors wait; too many, and the server runs out of memory.
  • PHP-FPM reads its settings when it starts. Change php.ini or a pool file, and nothing happens until it reloads.

    • X-Powered-By: PHP/8.4.28 tells every scanner which version you run, and so which bugs to try. expose_php = Off in php.ini removes it, and server_tokens off; in nginx drops the version from its Server header. It doesn't fix anything, but there's no reason to advertise.
