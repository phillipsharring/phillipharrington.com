Separating Concerns Phillip Harrington

The Style section was about making each piece of code read well. This section is about how the pieces fit together. Almost every pattern in it starts from one idea: a page does several different jobs, and each job belongs in its own place.

What's a Concern?

One kind of job your code does, with its own reasons to change. A typical page has three:

  • Reading: where the data comes from. A file, a database, an API. Changes when the storage changes.
  • Deciding: the rules. Which posts are published, what a shirt costs, who's allowed in. Changes when the business does.
  • Showing: the HTML, or JSON, that goes back. Changes when the design does.

    • Separating them means each lives in its own function, file or class, and talks to the others through plain values. The rules don't know there's a database. The template doesn't know there are rules.

    Edsger Dijkstra used "the separation of concerns" in a 1974 essay, "On the role of scientific thought." His point was about thinking, not code: you can only study one aspect of a problem well at a time, so you deliberately set the others aside while you do. Code that's separated lets the reader do the same. How It Works
    1. The entry point reads: it asks a function for the data, and gets back plain arrays or objects.
    2. It decides: it hands that data to the rules, and gets back what to show.
    3. It shows: it hands the result to a template, which only prints.

    The entry point becomes a few lines of glue. Each concern can be read without the others in your head, swapped without touching the others, and tested with no server, no file and no HTML.

    In PHP
  • Functions or classes for reading and deciding, in files that only declare (see Declaring Symbols vs. Causing Changes).
  • A plain PHP file as a template, using <?= ?> and the foreach: ... endforeach; form, with htmlspecialchars() on everything it prints. PHP was a template language first.
  • public/ for the entry point only, and everything else beside it, out of reach, as in Document Root.
  • Check the data where it's read. loadPosts() treats the file as input: a row without a title is skipped, and a missing draft counts as a draft. Never trust input, even a file you wrote.
    • Gotchas
  • Rules creep into templates. An <?php if ($post['draft'] ...) ?> in the view is a rule in the wrong place. A view can loop and choose how to show things; it shouldn't decide what to show.
  • Escaping belongs to showing. Don't store titles pre-escaped, or escape them in the rules. The template knows it's writing HTML, so the template escapes, every time; see XSS and Escaping Output.
  • More files isn't the goal. A twenty-line page doesn't need three folders. Separate when a concern grows, changes on its own schedule, or needs testing.

    • Before you put code somewhere, imagine the next change to it: a new database, a new rule, a new design. If any one of those would make you edit this file and two others, or edit one file in three unrelated places, the concerns are tangled. Fix that while it's small.
