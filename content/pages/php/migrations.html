Migrations Phillip Harrington

Every Try It in this section started from an empty database, with an init.sql that built the tables from scratch. That only works once. A real app's database is full of rows that have to survive, and the tables still have to change: a new column, a new index, a new table, a column that turned out to be a mistake. And the change has to happen the same way on your laptop, on everyone else's, and on the live server. Migrations are how.

What's a Migration?

One change to the database, written down in a file, with a name that sorts in the order the changes were made:

migrations/ 2026_11_01_0900_create_users.sql 2026_11_08_1400_add_phone_to_users.sql

The files live in git, next to the code that needs them. Together they're the whole history of the database's shape: start with nothing, apply them all in order, and you get today's tables.

The Runner

A small script that brings a database up to date. The database keeps its own list, in a migrations table, of which files it has had. The runner applies every file that isn't on the list, in order, and adds each one to the list as it goes. Run it twice, and the second time it does nothing.

Forward Only

Many migration tools have each migration come in two halves: up(), which makes the change, and down(), which undoes it, so you can roll back. This course doesn't write down(). Migrations go forward, and when a change has to be undone, the undoing is a new migration.

  • Nobody runs the downs. They're written once, rarely tested, and run for the first time on the worst day, against production.
  • Undoing isn't free. The down() of "add a column" drops it, along with everything people typed into it since. That should be a decision you make and write down, not a side effect of a rollback.
  • The history stays true. Every database got every change in the same order, and the files say exactly what happened, including the mistakes and their fixes.
    • Seed scripts fill a new database with sample rows, so there's something to click on in development. One of my apps had seeds that created an admin account, admin@example.com, with the password password, and the deploy ran them on production, every time, until we caught it and stopped it. Migrations change the shape of every database the same way. Seeds are for your laptop, and never go near the live one. Repeated side story: the seed admin story (admin@example.com / password on production) is also told in Configuration and the Environment. Keep one, make this a callback, or cut it. How It Works
    1. You need a change. You write a new file, named with the date and time and what it does, and commit it with the code that uses it.
    2. Everyone who pulls your code runs the runner, and their database gets the change.
    3. The deploy runs the runner on the live database, before the new code starts taking requests.
    4. If the change was wrong, you write another file that fixes it, and it goes out the same way.

    Step three means that for a moment, the old code runs against the new tables. So make changes the old code can live with: add a column that can be NULL, deploy, fill it in, and only then make it NOT NULL, in a later migration.

    docker compose up -d --wait db docker compose run --rm php php migrate.php docker compose run --rm php php migrate.php

    The first run applies both, in order. The second says there's nothing to do, because the migrations table already lists them. Add a user, with a phone number, from the mysql command:

    docker compose exec db mysql -u app -papp-password course INSERT INTO `users` (`email`, `name`, `phone`) VALUES ('alice@example.com', 'Alice', '555-0100'); SELECT * FROM `migrations`;

    Type exit. Now, it turns out, the phone column was a mistake. Don't edit or delete the migration that added it: it has already run, here and, in real life, on every other database. Undo it going forward, with a new migration. Make it in a later folder:

    Then move it into migrations, the way it would arrive in a pull, and migrate:

    cp later/2026_11_27_1000_drop_phone_from_users.sql migrations/ docker compose run --rm php php migrate.php

    New here:

    When the last thing given to cp is a folder, the copy goes into it, under the same name.

    Only the new one runs. Look at users again, and the phone column is gone, Alice's number with it. That's what undoing it means, and now it's a decision written down in a file, not something a rollback did on its own. The migrations table lists all three, in the order they happened. When you're done, take the copy back out, so the example starts clean next time, and throw the data away:

    rm migrations/2026_11_27_1000_drop_phone_from_users.sql docker compose down -v

    New here:

    Remove a file. There's no trash can; it's gone, so read the name before you press Enter.

    In PHP
  • glob(__DIR__ . '/migrations/*.sql') lists the files, and sort() puts them in order, which is why the names start with the date.
  • $pdo->exec($sql) runs a statement with no values in it, like an ALTER TABLE. A migration is your own file, not input, which is the only reason it can be run without placeholders.
  • Real projects often use a library for this, like Phinx or Doctrine Migrations, or the one that comes with their framework. They do the same thing: a list of files, a table of what's been applied, and a command that applies the rest. You can use them forward only, too: leave down() empty.
    • Gotchas
  • Never edit a migration that has run anywhere else. Every database that already had it skips it, by name, so your edit only reaches new databases, and the two drift apart. Write a new one.
  • One change per file. In MySQL, CREATE, ALTER and DROP commit on their own, so they can't be wrapped in a transaction (that was in Transactions). A file with three changes that fails on the second leaves the first done and the file not recorded. With one change per file, a failure leaves nothing half-done.
  • Big tables take time. An ALTER TABLE on a table with millions of rows can take minutes, and some changes block writes while they run. Try it on a copy of production-sized data before you run it on the real thing.
  • Seeds and test data stay out. Migrations change the shape of every database, including the live one. Sample rows, test users and admin accounts with known passwords don't belong in them.

    • Name migrations with the date and time, like 2026_11_27_1000_..., not 003_.... Two people working on two branches will both write 003, and the order their changes run in comes down to the alphabet. Two people almost never pick the same minute, and the names still sort in the order the changes were written.
