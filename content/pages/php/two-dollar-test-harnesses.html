Two-Dollar Test Harnesses Phillip Harrington

You changed the code that makes the "verify your email" link. Does it still work? One way to find out: start the site, the database and a mail server, fill in the signup form, open the email, click the link. Ten minutes, if nothing else is broken, and you'll do it once and hope. The other way takes a second, and you'll run it every time you save: a short script that loads that one piece and calls it.

What's a Test Harness?

Code whose only job is to run other code and check what it does. It sets up the inputs, calls the piece, and says whether the answer was right. Frameworks like PHPUnit, in the next lesson, are test harnesses with a lot of conveniences. A two-dollar one is the same idea with none: a plain PHP file, a require, a few calls, and ok or FAIL.

When a Piece Is Too Big

The harness is also a test of the code's shape. Here's a signup page that does everything in one place:

$pdo = new PDO($dsn, $user, $password); $stmt = $pdo->prepare('INSERT INTO users (email) VALUES (?)'); $stmt->execute([$_POST['email']]); $sig = hash_hmac('sha256', $_POST['email'] . '|' . (time() + 3600), getenv('LINK_SECRET')); $link = 'https://example.com/verify?email=' . urlencode($_POST['email']) . '&sig=' . $sig; mail($_POST['email'], 'Verify your email', "Click here: {$link}");

The link code is in there, but you can't reach it. To run it, you need a database to insert into, a mail server to send through, a form to post, and the clock to be whatever time it is. If proving one change works means running the whole stack, the mail server included, the piece is too big. Pull it out until it fits in one file.

How It Works
  1. Find the piece you want to prove. Here, making the link and checking it.
  2. Move it into a function, in a file of its own, that takes everything it needs as arguments: the email, the expiry time, the secret. No $_POST, no time(), no getenv() inside.
  3. Have the page call the function, passing in the real values. The page still does the database and the mail; the function only does the link.
  4. Write a harness that requires the function's file, calls it with made-up values, and checks the answers.
  5. Run it after every change.

Step two is the same move as Dependency Injection: anything the piece used to go and get, it's now given. That's what lets the harness hand it a fixed time and a fake secret.

Try It

The link code, pulled out of the signup, in src/verification.php. Two functions: one makes a signed link, the other checks one.

The link will come back to your site in a request, and never trust input: anyone can edit a URL. The signature, made with a secret only the server knows, is what proves the server wrote it. Now the harness, harness.php:

docker run --rm -v "$PWD":/app -w /app php:8.4-cli php harness.php

The link, then five lines of ok: a good link works; a changed email, an expired link, the wrong secret and junk are all refused. No database, no mail server, no browser, and it took about as long as it took you to press Enter.

Now break it on purpose. In src/verification.php, change the expiry check:

if ((int) $expires < $now) { // before if (false) { // after: expired links now work

Run the harness again, then ask for its exit code:

docker run --rm -v "$PWD":/app -w /app php:8.4-cli php harness.php echo $?

New here:

Print the exit code of the command before it: 0 means it worked, anything else means it didn't.

FAIL an expired link is refused, and an exit code of 1 instead of 0. The harness caught the bug the moment it was made. Put the line back.

In PHP
  • require __DIR__ . '/src/verification.php';: load only the piece, nothing else.
  • Pass the time in, as int $now, and let the page call time(). A fixed time makes every run of the harness the same.
  • === for the checks, so null, false and '' don't pass for each other.
  • exit(1) when anything fails. Other tools, and the shell's &&, read the exit code: 0 means it worked.
  • hash_equals() compares secrets in the same time whether they match early or late, so an attacker can't learn the signature a character at a time.
    • Gotchas
  • A harness that needs the database isn't two dollars. If yours needs anything running besides PHP, the piece still has something in it that doesn't belong. Pull that out too, or hand it in.
  • time() inside the function makes it a moving target. An expiry check that reads the clock itself can only be tested by waiting. Pass the time in.
  • Keep harnesses out of the web root. A harness in public/ is a page anyone can run. They belong next to src/, like everything else from Document Root.
  • Keep it, and keep running it. A harness you wrote once and deleted proved the code worked once. Leave it in the project. When there are a lot of them, that's when a framework earns its place.
    • Margaret Hamilton led the team that wrote the onboard flight software for Apollo. She has told how her young daughter, playing in a simulator, picked a prelaunch program in the middle of a simulated flight and crashed it. Hamilton wanted to add a check for that. She was told astronauts were too well trained to make that mistake. On Apollo 8, Jim Lovell made it, and the navigation data had to be sent up again from the ground. The mistake nobody would make is the first one to write a check for.

    Because the harness exits 1 on any failure, you can chain it: php harness.php && git commit. If anything fails, the commit never happens. Or put it in composer.json's scripts, from Autoloading, as composer run check, so there's one command to remember.

    Five checks in an array is fine. Fifty, with setup, failures that show what came back instead, and a report at the end, is a framework. Next: testing.
