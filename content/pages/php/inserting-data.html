Inserting Data Phillip Harrington

The tables are built, with the right types, keys, indexes and character sets. Now they need rows. Most rows in a web app start as something a person typed into a form, which makes INSERT the place where outside data comes to stay. It's the simplest of the four statements, and it has three questions attached: what id did the new row get, how do you add many at once, and what happens when it's already there.

What's INSERT?

The statement that adds rows to a table:

INSERT INTO `subscribers` (`email`, `name`) VALUES ('alice@example.com', 'Alice');

Name the columns, then give the values in the same order. Columns you leave out get their default: the next AUTO_INCREMENT number, the current time, or NULL. Always name the columns. An insert without them depends on the table's column order, and breaks the day someone adds one.

Many Rows

One statement can add many rows, which is much faster than one statement each:

INSERT INTO `subscribers` (`email`, `name`) VALUES ('bo@example.com', 'Bo'), ('cy@example.com', 'Cy'); What's an Upsert?

An insert that turns into an update when the row is already there: "add this subscriber, or if that email has already signed up, update their name." MySQL spells it ON DUPLICATE KEY UPDATE. A duplicate means any primary key or unique index that would be broken.

INSERT INTO `subscribers` (`email`, `name`) VALUES ('alice@example.com', 'Alice Rivera') AS `new` ON DUPLICATE KEY UPDATE `name` = `new`.`name`;

AS `new` names the row you tried to insert, so the update can use its values. (Older code writes VALUES(`name`) for the same thing. It still works in MySQL 8.4, but it's deprecated.)

The United States census of 1890 was the first to be counted by machine. Herman Hollerith's tabulators read answers from punched cards, a hole for each fact. The 1880 census had taken years to count by hand, and the 1890 one went far faster. Every card was still punched by hand, by clerks working from the census forms. Hollerith's company later became part of IBM. How It Works
  1. PHP prepares the INSERT with placeholders, and sends the values separately.
  2. MySQL fills in the defaults, and takes the next AUTO_INCREMENT number for the id.
  3. It checks the row against every rule: types, NOT NULL, foreign keys, unique indexes.
  4. If a unique index is already taken, a plain insert fails, and an upsert updates the row that has it instead.
  5. It answers with the number of rows affected, and the id it made, which PHP can ask for with lastInsertId().

Step two can happen before step three. An id can be used up even when the insert then fails, or turns into an update, and it's never given back. That's why ids have gaps, and why that's fine.

Subscribers #1 and #2. Now Alice signs up again, with her full name, and then once more, the same way:

docker compose run --rm php php subscribe.php alice@example.com 'Alice Rivera' docker compose run --rm php php subscribe.php alice@example.com 'Alice Rivera'

The first updates her name. The second changes nothing, and says so: the row count is 0 when the update has nothing to change. Then a new one:

docker compose run --rm php php subscribe.php cy@example.com Cy

Subscriber #5, not #3. Each of Alice's two upserts took an id before finding her email, and kept it. Look in the table, and there's no 3 or 4:

docker compose exec db mysql -u app -papp-password course SELECT `id`, `email`, `name` FROM `subscribers`;

Type exit. Last, sign up with something that isn't an email address:

docker compose run --rm php php subscribe.php 'nope' Mallory

Refused before it gets anywhere near the table. Handed down, generation to generation: never trust input, least of all input you're about to keep. docker compose down -v when you're done.

In PHP
  • $pdo->prepare('INSERT ... VALUES (?, ?)'), then execute([$email, $name]). Every value from outside goes in as a placeholder. Never trust input, and never glue it into the SQL; SQL Injection shows why.
  • $pdo->lastInsertId() returns the new id, as a string. Call it right after the insert: another statement on the same connection, even an UPDATE, can reset it to 0.
  • $statement->rowCount() after an upsert: 1 if it inserted, 2 if it updated, 0 if the row was already exactly that.
  • filter_var($email, FILTER_VALIDATE_EMAIL), and trim() and a length check on text, before anything is saved.
    • Gotchas
  • Don't count on ids being in a row. Failed inserts, upserts and rolled-back transactions all use up ids. Never use the id to count rows, and never assume the next id is the last one plus one.
  • Don't show your ids to the world if you can help it. An order number of 1042 tells a competitor how many orders you've had, and invites someone to try 1041. Check every id that comes back in a URL; it's input.
  • INSERT IGNORE ignores more than duplicates. It turns errors into warnings: a duplicate is skipped, but so is a value that's out of range, which gets clamped and saved. Use an upsert when you mean "it might already be there."
  • Check first, then insert, is a race. "Is this email taken? No? Insert it" lets two signups in the same instant both pass the check. Let the unique index decide, and handle the duplicate error or use an upsert.
  • Capitals count as the same email. With the default collation, ALICE@EXAMPLE.COM is a duplicate of alice@example.com, and the upsert updates her row. Character Sets and Collation is why.

    • Importing a lot of rows one INSERT at a time is slow mostly because each one is saved to disk on its own. Wrap the loop in $pdo->beginTransaction() and $pdo->commit(), or insert a few hundred rows per statement, and the same import often goes from minutes to seconds.
