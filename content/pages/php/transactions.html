Transactions Phillip Harrington

Deleting Data used one as an undo button. That's the smaller half of what a transaction is for. The bigger half: most real changes take more than one statement. Moving money takes two updates, placing an order takes an insert and a stock change. If the first one runs and the second one doesn't, because of an error, a crash or a bug, the data is left half-changed. A transaction makes the statements one change: all of them happen, or none do.

What's a Transaction?

A group of statements the database treats as one:

START TRANSACTION; UPDATE `accounts` SET `balance_cents` = `balance_cents` - 2500 WHERE `id` = 1; UPDATE `accounts` SET `balance_cents` = `balance_cents` + 2500 WHERE `id` = 2; COMMIT;
  • START TRANSACTION (or BEGIN) opens it.
  • COMMIT makes every change in it permanent, at once.
  • ROLLBACK throws every change in it away, as if none had run.
    •

    Outside a transaction, MySQL commits each statement the moment it finishes. That's called autocommit, and it's the default.

    ACID

    The four promises a transaction makes, by their initials:

  • Atomic: all of it happens, or none of it. No half-transfers.
  • Consistent: it takes the data from one valid state to another, with every rule (types, keys, constraints) still holding.
  • Isolated: other connections don't see its changes until it commits.
  • Durable: once it's committed, it stays committed, even if the server loses power a moment later.
    • Much of how databases do transactions comes from Jim Gray, who worked out how to make them reliable and fast, at IBM, Tandem and later Microsoft, and won the Turing Award for it in 1998. The name ACID came from two German researchers, Theo Härder and Andreas Reuter, in 1983, building on his work. Gray went sailing alone off San Francisco in 2007 and was never found. Thousands of volunteers searched satellite photos online for any sign of his boat. How It Works
    1. Your connection starts a transaction.
    2. Each statement in it changes rows as usual, but the changes are visible only to your connection. The rows you changed are locked: another connection that tries to change them waits.
    3. On COMMIT, the database writes all the changes to its log in one go, and releases the locks. Everyone sees them from then on.
    4. On ROLLBACK, or if the connection drops before committing, the database undoes every change, and releases the locks.

    Step four includes crashes. If PHP dies halfway through, its connection closes, and the database rolls the open transaction back on its own. Half a change never lands.

    It says it transferred, and the total went from 15000 to 12500. The first update took Alice's money. The second matched no account, changed nothing, and didn't fail, so nothing noticed. The money is just gone. Now transfer.php, which checks each step, inside a transaction:

    docker compose run --rm php php transfer.php 1 99 2500 docker compose run --rm php php balances.php

    Nothing transferred. The debit ran, the credit found no account, the script threw, and the rollback put Alice's money back. The total is still 12500 (the naive script's loss is permanent). A real transfer works as you'd expect:

    docker compose run --rm php php transfer.php 2 1 1000 docker compose run --rm php php transfer.php 2 1 999999

    The first moves 10.00 from Bo to Alice. The second asks for more than Bo has, so the debit's WHERE matches nothing, and nothing changes. Last, what other connections see. isolation.php opens two at once:

    docker compose run --rm php php isolation.php

    Inside its transaction, A sees its own change. B, at the same moment, sees the old balance. Only after A commits does B see the new one. docker compose down -v when you're done.

    In PHP
  • $pdo->beginTransaction(), $pdo->commit() and $pdo->rollBack().
  • The pattern: begin, then try every step, commit() at the end of the try, and rollBack() in the catch. Exceptions and Try/Catch has the rest of how try works.
  • Check rowCount() after each step that has to change a row, and throw if it didn't. A statement that matches nothing isn't an error to the database.
  • SELECT ... FOR UPDATE, inside a transaction, reads a row and locks it, so nobody else can change it until you commit. Use it when you have to read a value, decide in PHP, and then write.
  • $pdo->inTransaction() says whether one is open.
  • The amounts and account ids are input. Never trust input: a transfer of -2500 from Bo to Alice is a transfer from Alice to Bo, which is why args.php wants 1 or more.
    • Gotchas
  • A statement that matches nothing isn't a failure. The naive transfer "succeeded." Only your own checks can tell "it ran" from "it did what I meant."
  • Changing the shape of a table commits. CREATE, ALTER, DROP and TRUNCATE commit any open transaction first, then run on their own. A rollback after one of them has nothing to roll back. That matters in the next lesson.
  • Long transactions hold locks. Every row a transaction changes stays locked until it ends, and everyone who wants those rows waits. Keep transactions short.
  • Deadlocks happen. Two transactions each lock a row the other needs, and MySQL breaks the tie by rolling one of them back with error 1213. That's normal under load, not a bug: catch it and run the whole transaction again.
  • The rest of the world doesn't roll back. An email sent, a file written or a payment taken inside a transaction stays done when the transaction is rolled back.

    • Do only database work between beginTransaction() and commit(). Send the confirmation email, call the other API and write the log after the commit has succeeded. The transaction stays short, and nobody ever gets an email about an order that was rolled back.
