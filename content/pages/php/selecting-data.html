Selecting Data Phillip Harrington

Inserting Data put rows in. Almost every page of a web app takes rows out: a list, a profile, an order with its items. SELECT is the statement you'll write most, and it can do a lot more than fetch a table. Done well, one query brings back exactly what a page needs. Done badly, a page asks the database a hundred small questions, and nobody notices until the site is slow.

What's SELECT?

The statement that reads rows. Its clauses always come in this order:

SELECT `books`.`title`, `authors`.`name` FROM `books` INNER JOIN `authors` ON `authors`.`id` = `books`.`author_id` WHERE `books`.`rating` >= 4 ORDER BY `books`.`title` LIMIT 10;
  • SELECT: which columns. Name them, rather than *.
  • FROM and JOIN: which tables, and how they line up.
  • WHERE: which rows.
  • ORDER BY: in what order. Without it, the order isn't promised.
  • LIMIT: how many.
    •  INNER and LEFT Joins

    An INNER JOIN keeps only the rows that match on both sides: books that have an author, and authors that have books. A LEFT JOIN keeps every row from the left table, matched or not, and fills the right side with NULL where there's no match: every author, including the ones with no books yet. Always say which one you mean. A bare JOIN is an inner join, but nobody reading it can tell you meant that.

    NULL

    NULL means "no value": unknown, missing, not rated yet. It isn't zero, and it isn't an empty string. And it isn't equal to anything, itself included: NULL = NULL isn't true, it's NULL. To find it, ask IS NULL or IS NOT NULL.

    Edgar Codd, who invented the relational model, thought one NULL wasn't enough. In 1990 he proposed two: one for "there's a value, but we don't know it," like an unrated book, and one for "there's no value to know," like the middle name of someone who doesn't have one. SQL never adopted the idea. It has one NULL, and you decide what it means, column by column. How It Works

    The clauses are written in one order and, as far as their meaning goes, run in another:

    1. FROM and the joins build one wide set of rows.
    2. WHERE throws out the ones that don't match.
    3. GROUP BY, if there is one, folds them into groups, for counting.
    4. SELECT picks the columns.
    5. ORDER BY sorts what's left.
    6. LIMIT keeps the first few.

    That's why LIMIT 10 with no ORDER BY means "any ten," and why a WHERE on the right side of a LEFT JOIN can quietly turn it back into an inner one. The database is free to do the work in whatever order is fastest, as long as the answer is the same.

    The N+1 Query

    A page lists authors with their books. The natural way to write it: one query for the authors, then, in the loop, one query for each author's books. For 4 authors that's 5 queries. For 200, it's 201. Each one is fast, and each one is a round trip to the database, so the page gets slower with every author, and no single query ever looks slow. That's the N+1 query: one, plus one for each of N rows. The fix is to ask once, with a join, and sort the rows out in PHP.

    Try It

    A reading list. The same compose.yml, Dockerfile and db.php as in SQL, and this init.sql, with one author who has no books yet, and two books with no rating:

    Start the database and open the mysql command:

    docker compose up -d --wait db docker compose exec db mysql -u app -papp-password course

    Every author, and the books they have. With a LEFT JOIN, Toni Morrison is there, with NULL for a title:

    SELECT `authors`.`name`, `books`.`title` FROM `authors` LEFT JOIN `books` ON `books`.`author_id` = `authors`.`id` ORDER BY `authors`.`name`;

    Change it to INNER JOIN, and she's gone. Now look for the unrated books:

    SELECT `title` FROM `books` WHERE `rating` = NULL; SELECT `title` FROM `books` WHERE `rating` IS NULL;

    The first finds nothing, ever. The second finds both. Then the one that catches people out, every book not rated 5:

    SELECT `title`, `rating` FROM `books` WHERE `rating` <> 5;

    Two books, not four. The unrated ones aren't "not 5"; their comparison is NULL, and WHERE only keeps rows where it's true. Last, count each author's books:

    SELECT `authors`.`name`, COUNT(*) AS `rows`, COUNT(`books`.`id`) AS `books` FROM `authors` LEFT JOIN `books` ON `books`.`author_id` = `authors`.`id` GROUP BY `authors`.`id` ORDER BY `authors`.`name`;

    COUNT(*) counts rows, and gives Toni Morrison 1, for her row with no book. COUNT(`books`.`id`) counts values, skips the NULL, and gives her 0, which is right. Type exit.

    Now from PHP. list.php shows the books a page at a time, with LIMIT and OFFSET:

    docker compose run --rm php php list.php 1 docker compose run --rm php php list.php 2

    Three books a page, in title order. Ask for page '2 OR 1' and you get page 1: the page number came from outside, and never trust input, so anything that isn't a whole number is treated as the first page. Then the N+1 query, and its fix, side by side, in n-plus-one.php:

    docker compose run --rm php php n-plus-one.php

    The same list twice, word for word. The first took 5 queries, and would take 201 with 200 authors. The second took 1, and always will. docker compose down -v when you're done.

    In PHP
  • fetch() gets the next row, or false when there are none; fetchAll() gets every row as an array; fetchColumn() gets one value; fetchAll(PDO::FETCH_COLUMN) gets one column as a list.
  • A NULL from the database is a null in PHP. Check for it with === null before you print it.
  • bindValue(1, $limit, PDO::PARAM_INT) for LIMIT and OFFSET, so they're sent as numbers.
  • Every value in a WHERE that came from outside is a placeholder. Never trust input, including the page number, the sort order and the search box. A column name to sort by can't be a placeholder, so pick it from an allow list of your own.
    • Gotchas
  • The N+1 query hides in loops. Any query inside a foreach over rows from another query is a candidate. Fetch the related rows in one query, with a join or with WHERE `author_id` IN (...), before the loop.
  • Nothing equals NULL. = NULL finds nothing, and <> 5 skips every NULL. If a column can be NULL, every comparison on it has to say what to do about that.
  • A WHERE on the right side undoes a LEFT JOIN. WHERE `books`.`rating` > 3 throws away the authors with no books, because their rating is NULL. Put the condition in the ON instead, if you want to keep them.
  • MySQL turns "2abc" into 2. Compare an integer column to a string and MySQL converts the string, reading digits until it hits something else: WHERE `id` = '2abc' finds row 2, with only a warning. Check that an id is a whole number in PHP, before it's a query.
  • NULL sorts first. In MySQL, ORDER BY `rating` puts the NULLs before the lowest rating. Add DESC, and they go last.

    • In development, count the queries each page makes, and show the number in the footer or write it to the log. A page that should take 3 and takes 140 is an N+1 query, found in a second, long before anyone has to tell you the site is slow.

    Reading rows can't hurt them. Changing them can, and the most dangerous part of the statement is the one you forget to write. Next: updating data.
