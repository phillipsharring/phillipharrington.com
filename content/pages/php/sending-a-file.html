Sending a File Phillip Harrington

A web server can hand out any file in the document root by itself. The files that need PHP are the ones it shouldn't hand out to just anyone: a report for logged-in users, an invoice that belongs to one customer, an export built on request. PHP checks who's asking, then sends the file. Content Types showed the headers that turn a response into a download. This lesson sends a real file with them, including one too big to fit in memory.

What's a Download?

An ordinary response, labeled so the browser saves it instead of showing it. Two headers do the labeling:

  • Content-Type: what the file is, like text/csv or application/pdf.
  • Content-Disposition: attachment means "save this," and filename="..." is the name to save it as. inline means "show it if you can."

    • A third, Content-Length, gives the size, so the browser can show a progress bar.

    The Download Name

    The name in Content-Disposition doesn't have to match the file on disk. Usually it shouldn't: on disk the file can be 4f1c9a.csv, and the visitor gets sales-report.csv. A name with characters outside ASCII goes in a second form, filename*, written as UTF-8 and percent-encoded, with a plain filename beside it for old browsers.

    How It Works
    1. A request asks for a file, by some name or id in the query string, like ?file=report.
    2. PHP decides whether to send it: whether the file is one it offers, and whether this visitor may have it.
    3. It sends the headers: the type, the disposition and name, the size.
    4. It sends the file itself, a piece at a time, straight from the disk to the connection.

    Step two is where downloads go wrong. The name in the query string is input, and never trust input. Build a path from it, and someone will ask for ../.env, and get it, because, as the prophecy foretold, the code forgot to never trust input. Look it up in a list of the files you offer instead, and anything not on the list is a 404.

    Step four is where they get slow. Reading the whole file into a string first means holding all of it in memory, for every download running at once. Sending it a piece at a time means each download needs only a few kilobytes.

    Try It

    A folder with a files folder (the files to send, outside the web root) and a public folder (the web root). In files, put any small CSV as report.csv and menu.csv. Then a script to make a big one, make-big-file.php:

    docker run --rm -v "$PWD":/app -w /app php:8.4-cli php make-big-file.php

    Serve public, with PHP's memory limit turned down to 16 MB, so a 40 MB file can't fit:

    docker run --rm -it -p 8000:8000 -v "$PWD":/app -w /app php:8.4-cli php -d memory_limit=16M -S 0.0.0.0:8000 -t public

    As in Errors and the Error Log: PHP's -d sets one setting for this run.

    Open http://localhost:8000/download.php?file=report in a browser: it saves sales-report.csv, though the file on disk is report.csv. Then, from a second terminal, look at the menu's headers:

    curl -I 'http://localhost:8000/download.php?file=menu'

    filename="caf_-menu.csv" for old browsers, and filename*=UTF-8''caf%C3%A9-menu.csv for everything else: the é, as its two UTF-8 bytes. Now the big one, both ways:

    curl -o everyone.csv 'http://localhost:8000/download.php?file=big' curl 'http://localhost:8000/all-at-once.php' | tail -c 300

    New here:

    Save the response to everyone.csv instead of printing it. Show only the last 300 characters of the output (bytes, strictly), where the error will be.

    The first saves all 40 MB, under a 16 MB limit, because readfile() never holds more than a piece of it. The second dies with Allowed memory size of 16777216 bytes exhausted: it tried to hold the whole file at once. Last, go after a file that isn't on the list:

    curl -i 'http://localhost:8000/download.php?file=../.gitignore'

    A 404. The list is the only way in.

    In PHP
  • header('Content-Disposition: attachment; filename="report.csv"'); makes it a download, with a name.
  • readfile($path) sends a file a piece at a time. fpassthru() does the same for a file you've already opened.
  • filesize($path) for the Content-Length header.
  • rawurlencode() builds the percent-encoded filename*.
  • For a file you build as you go, like an export from the database, open php://output with fopen() and write it a row at a time with fputcsv(). The Exporting Data project does this.
  • file_get_contents() is fine for small files you read in your own code. Don't use it to send big ones.
    • Gotchas
  • An open buffer undoes the streaming. If a buffer from Output Buffering is open, everything readfile() sends piles up in it, in memory. That's why the example closes every buffer first.
  • A name from input is a path from input. Never build a path out of what's in the query string. basename() stops ../, but still lets anyone ask for any file in the folder, including other people's. Use a list of what you offer, or ids from your database that you check against the visitor.
  • The download name goes in a header. If it ever comes from a user, like an uploaded file's original name, strip the quotes and anything that isn't a plain character from the filename part. PHP's header() refuses a line break, but a stray quote can still mangle the header.
  • Anything after the file is part of the file. A warning, a blank line after a closing ?>, a footer from an include: it all lands in the download, and the CSV or PDF comes out broken.
  • Big files take time. On Linux, PHP's max_execution_time doesn't count time spent sending, but a proxy in the middle may give up on a slow download. For really big files, let the web server do the sending.
    • HTTP/1.1, published in 1997, added range requests: a client can ask for "bytes from here to there" of a file instead of all of it. In the dial-up years, that's what let a download that died at 90% pick up at 90% instead of starting over. Web servers answer range requests for the files they serve themselves. A PHP script that calls readfile() doesn't, unless you write that part yourself.

    Behind nginx, PHP can check the visitor, then answer with one header, X-Accel-Redirect: /protected/report.csv, and no body. nginx sends the file itself, from a location marked internal that visitors can't ask for directly, with range requests and all. Apache has the same idea as X-Sendfile, through a module.
