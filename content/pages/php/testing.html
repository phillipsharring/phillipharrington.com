Testing Phillip Harrington

The harness in the last lesson had five checks in an array. It works, and it'll keep working until there are fifty, and you want to know which one failed and what came back instead, and run only the ones about links. That's what a testing framework is for. The hard part, getting the code into pieces small enough to test, you've already done. This is the easy part.

What's a Test?

A small method that runs a piece of your code and checks one thing about the result. Each test has the same three parts, often in this order, with a blank line between:

  • Arrange: make what the code needs.
  • Act: call it.
  • Assert: check the result. assertSame($expected, $actual) fails the test if they aren't identical.

    • A test that checks one small piece on its own, with nothing else running, is a unit test. That's most of what you'll write.

    PHPUnit

    The standard testing framework for PHP, installed with Composer. Tests are classes that extend TestCase, in a tests folder; each method whose name starts with test is one test. Pest is a popular alternative, built on top of PHPUnit, with a shorter way of writing the same tests. Learn PHPUnit first, and Pest reads easily.

    Fakes

    A stand-in for a dependency, so a test doesn't need the real thing. The MemoryMailer from Dependency Injection is one: it keeps emails in a list, and the test reads the list. This is where injection pays for itself. A class that makes its own mailer can't be handed a fake.

    In 1996, the first Ariane 5 rocket broke up about 37 seconds after launch. Part of its guidance software was reused from the smaller Ariane 4, where it had worked for years. The new rocket was faster sideways, a number got too big to fit where the code put it, and the guidance system shut down. The inquiry found that this part of the software had not been tested with the new rocket's flight path. It had worked before, so everyone assumed it still did. How It Works
    1. You run vendor/bin/phpunit. It reads phpunit.xml to find the tests folder and the autoloader.
    2. It loads every test class in the folder.
    3. For each test method, it makes a fresh object of the class and calls the method, so no test can leave anything behind for the next one.
    4. An assertion that fails stops that test and records what was expected and what came back. The rest still run.
    5. At the end, it prints a dot for each pass and an F for each failure, the details of every failure, and exits 0 if everything passed, 1 if anything didn't.

    In PHP
  • composer require --dev phpunit/phpunit adds it to a project.
  • assertSame() compares with ===. assertEquals() compares with ==, and lets '1' pass for 1. Use assertSame() unless you mean otherwise.
  • assertNull(), assertTrue(), assertCount(), assertStringContainsString(): the rest of the everyday set.
  • $this->expectException(InvalidArgumentException::class); before the call that should throw.
  • #[DataProvider('tamperedLinks')] runs a test once per row. The provider is a public static method, because PHPUnit requires it: one of the places a library gives you no choice.
  • setUp(), if a class has one, runs before every test in it, for shared arranging.
    • Gotchas
  • A test that has never failed might not test anything. An assertion on the wrong variable, or a test method PHPUnit never ran because of a typo in its name, passes forever. Break the code once and watch the test catch it, as in the Try It.
  • Tests that need the time, the network or a database are slow and flaky. Hand those in, as in the last two lessons, and test the logic on its own. Keep a few bigger tests for the wiring, and run them less often.
  • Statics and globals leak between tests. PHPUnit makes a fresh test object every time, but a static property set in one test is still set in the next, as Constants and Statics warned.
  • Test what it does, not how. A test that checks which private method ran breaks every time you tidy the code, though nothing changed for the caller. Check the result.
  • Passing tests aren't proof. They prove the cases you thought of. The bugs are usually in the ones you didn't, which is why the input tests try links that are edited, empty and the wrong type.

    • When a bug report comes in, write a test that shows the bug before you touch the code. Watch it fail. Then fix the code and watch it pass. You've proved the fix works, and that bug can never quietly come back.
