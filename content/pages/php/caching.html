Caching Phillip Harrington

Output Buffering turned a whole page into a string. A page you can hold, you can keep. If it took a second to make, and it will be the same for the next thousand visitors, there's no reason to make it a thousand times. Keeping it is caching.

What's a Cache?

A copy of an answer, kept somewhere closer or cheaper than the place the answer comes from, so the next person who asks gets the copy instead. A few words come with it:

  • Hit: the copy was there, and it was used. Miss: it wasn't, so the real work happened.
  • Fresh and stale: whether the copy is still young enough to trust. How long it stays fresh is its lifetime, often called its TTL, for "time to live."
  • Invalidation: throwing a copy away because the real answer has changed.

    • A copy is never the truth. The database, the file, the other site: that's the truth, and the cache is a bet that it hasn't changed since you looked.

    "Cache" is French, from cacher, to hide: a hidden store of supplies, kept for later. Computing took the word in the late 1960s, at IBM, for a small, fast memory between the processor and the main memory in the System/360 Model 85. Maurice Wilkes had described the idea a few years before, in a 1965 paper. Where Caches Live The Browser

    The browser keeps copies of what it downloads, and your response headers say what it may keep and for how long. The main one is Cache-Control:

  • max-age=60: the copy is fresh for 60 seconds. Until then, the browser uses it without asking you at all.
  • public: any cache may keep it, including the shared ones in the middle.
  • private: only this person's own browser may keep it. No shared cache.
  • no-cache: keep it if you like, but check with the server before every use.
  • no-store: don't keep it anywhere, at all.
    •

    When a copy goes stale, the browser doesn't have to download it again. If the response came with an ETag, a fingerprint of that version, the browser asks with If-None-Match and the fingerprint it has. If nothing changed, the server answers 304 Not Modified, with no body, and the browser uses its copy for another lifetime. Last-Modified and If-Modified-Since do the same with a date instead of a fingerprint. Both are headers from Request and Response.

    The Middle

    What's in the Middle put a CDN at the front of the chain, keeping copies close to visitors. It reads the same headers the browser does. A public answer with a max-age can be handed out from a server on another continent for that long, and your server never hears about it. Many CDNs also have their own settings that override yours, so check them before you go looking for a bug in your code.

    Your App

    The caches above keep whole responses. Your own code can keep anything expensive: the result of a slow query, an answer from another site's API, a page built from a dozen pieces. Make it once, keep it with a time on it, and hand out the copy until it's too old.

    Where to keep it depends on the size of the site. A file on disk is the simplest place, and needs nothing installed. Memory is faster: APCu is a PHP extension that keeps values in the server's memory between requests, with apcu_store() and apcu_fetch(). It isn't in the php:8.4-cli image, and every server has its own, so it suits a site on one machine. Redis and Memcached are shared caches that several servers can use at once. Each one is a different place to put the copy; the idea doesn't change.

    PHP already caches for you, too. OPcache, which comes with PHP, keeps your scripts in memory already compiled, so PHP doesn't have to read and parse every file on every request.

    Invalidation

    "There are only two hard things in Computer Science: cache invalidation and naming things." The line is usually credited to Phil Karlton. Making the copy is easy. Knowing when it stopped being true is the hard part. There are three ways to handle it:

  • Let it expire. Give every copy a lifetime and accept that it can be that far behind. Simple, and right for most things.
  • Throw it away when the truth changes. When someone edits a post, delete the cached copy of that post. Exact, but every place that changes the data has to remember to do it.
  • Change the name. Put a version in the URL or the key, and a change makes a new copy under a new name. The old one is never asked for again.

    • Once a browser has a copy, only the first and third work: you can't reach into someone's browser and delete it.

    One Person's Page

    A page that says "Hi, Alice," or shows a cart, an order, an account, belongs to one person. If it's cached anywhere shared, the next visitor can get Alice's page. Send Cache-Control: private, no-store on every page like that, and never cache it in your app under a key that's the same for everyone. When in doubt, it's private.

    On Christmas Day in 2015, people visiting Valve's Steam store started seeing other people's account pages. During a flood of traffic, a change to the caching settings let account pages be cached and served to the wrong visitors. Valve later said about 34,000 users' details could have been shown to someone else. Nothing about it was exotic: one person's page, kept somewhere shared. How It Works

    One request, with all three kinds of cache in its way:

    1. The browser looks for its own copy. If it has one that's still fresh, it uses it, and nothing is sent at all.
    2. If its copy is stale, it sends the request with If-None-Match and the ETag it has.
    3. A CDN in the middle may have a fresh copy of its own, and answer from that.
    4. If not, the request reaches PHP. Your code looks in its own cache. On a hit, it skips the slow work.
    5. On a miss, it does the work, and keeps the result for next time.
    6. It works out the ETag for what it's about to send. If that matches the one the browser sent, it answers 304 with no body. If not, it sends the whole thing.

    Every step that answers early is work nobody else has to do. The best request is the one the browser never sends.

    Try It

    A page that's slow on purpose, made fast with a file cache, then made smaller still with an ETag. In a folder, make a public folder and an empty cache folder beside it, so the copies are kept outside the document root. Then public/index.php:

    Serve public:

    docker run --rm -it -p 8000:8000 -v "$PWD":/app -w /app php:8.4-cli php -S 0.0.0.0:8000 -t public

    From a second terminal, ask twice, and time each one:

    curl -i -w '%{time_total}s\n' http://localhost:8000/ curl -i -w '%{time_total}s\n' http://localhost:8000/

    The first says X-Cache: MISS and takes two seconds. The second says HIT, takes a few thousandths of a second, and has the same "Built at" time. That's the file cache. Now copy the ETag from either one, quotes and all, and ask the way a browser with a stale copy would:

    curl -i -H 'If-None-Match: "paste-the-etag-here"' http://localhost:8000/

    304 Not Modified, and no page at all. The browser already has it. Now invalidate: throw the copy away, and ask again with the same ETag.

    rm cache/*.html curl -i -H 'If-None-Match: "paste-the-etag-here"' http://localhost:8000/

    A miss, two seconds, a new "Built at" time, so a new fingerprint, and the whole page comes back with 200. Wait a minute without deleting anything, and the same thing happens on its own: the copy expires.

    If-None-Match is a header, and headers are input. Never trust input. The page only compares it with its own fingerprint, and never uses it for anything else.

    One more file, a page about one person, public/hello.php:

    curl -i 'http://localhost:8000/hello.php?name=Ada'

    Cache-Control: private, no-store: no cache anywhere keeps this one. The name came from the query string, so it's checked and escaped, and the page says it's UTF-8, so a name like Zoë arrives the way it was typed (Text and UTF-8 has why). Ctrl+C stops the server.

    This is the idea, small. The Caching project builds a cache you can use for anything, with keys, lifetimes and a way to clear it all.

    In PHP
  • header('Cache-Control: public, max-age=60'); for a response that's the same for everyone; header('Cache-Control: private, no-store'); for one that isn't.
  • header('ETag: "..."'); with a fingerprint of the body, quotes included. hash('sha256', $body) makes a good one.
  • $_SERVER['HTTP_IF_NONE_MATCH'] is the fingerprint the client says it has. It's input: compare it, don't use it.
  • http_response_code(304); then exit; when they match. A 304 has no body.
  • filemtime() says when a cache file was written, which is all you need to tell fresh from stale. Write with a temporary file and rename(), so no one reads half a file.
  • apcu_store() and apcu_fetch(), when the APCu extension is installed, keep values in memory instead.
  • session_cache_limiter() and the session.cache_limiter setting control the cache headers session_start() sends.
    • Gotchas
  • no-cache doesn't mean "don't cache." It means "check before using." The one that means don't keep it is no-store.
  • Starting a session changes your cache headers. By default, session_start() sends headers that tell every cache not to keep the page, which is right for pages about one person and wasted on pages that aren't. Only start a session where you need one.
  • Cache what you've measured, not what you guess. Every cache is one more place for a stale answer to hide. Time the slow part first, and cache that.
  • A browser may send several ETags. If-None-Match can be a list, separated by commas. The Try It compares the whole header to keep it short; the Caching project splits the list.
  • The ETag has to change when the page does. Make it from the body, or from something that changes whenever the body does. An ETag that stays the same while the page changes tells every browser to keep the old one.

    • In Chrome or Firefox, the developer tools' Network tab has a "Disable cache" checkbox. While the tools are open, the browser fetches everything fresh. Half of "my change didn't work" is a copy the browser kept. Turn it back off when you want to see what visitors see.

    The page you cached was meant to be shown in the browser. Some responses are meant to be saved instead: a report, an invoice, an export. Next: sending a file.
