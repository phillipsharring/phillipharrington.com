Defensive Programming Phillip Harrington

A file that only declares things can be used from anywhere, which means it will be called by code you didn't write, with values you didn't expect. Defensive programming is writing each function so that when it's handed something wrong, it says so right away, instead of quietly working out a wrong answer for someone else to find.

What's Defensive Programming?

Checking your assumptions in code, at the top of a function, before you rely on them. A price can't be negative. A percentage is 0 to 100. An order being shipped has been paid for. Each of those is true in your head; a defensive function makes it true in the program, by refusing to go on when it isn't.

Fail Loudly, Fail Early

A function that gets nonsense has two choices: carry on, or stop. Carrying on looks friendlier, and it's how a negative price ends up on an invoice three steps later, far from the line that caused it. Stopping, with an exception that says what was wrong and what the value was, puts the error next to its cause.

Validating vs. Defending

Two jobs that look alike. Validating happens at the edge, where input arrives: a form, a URL, an API call. Bad input there is normal, and it gets a polite answer for a person. Defending happens inside: a function checking its own arguments. Bad values there mean a bug, and they get an exception for a programmer. You need both. As Sun Tzu wrote in chapter fourteen of The Art of War, never trust input at the edge, and don't let a mistake inside pass in silence.

Minutes before Apollo 11 landed, the guidance computer started raising alarms, 1202 and 1201: it had more work than it could do. The software, written by the MIT team led by Margaret Hamilton, was built for that. It dropped its lowest-priority jobs, kept the ones the landing needed, and carried on. Hamilton is also known for insisting on the term "software engineering," so that the work would be taken as seriously as the rest of the engineering. How It Works
  1. Let the types do what they can. With declare(strict_types=1), an int parameter refuses a string, even '25'.
  2. Check what types can't say, first thing: ranges, empty strings, states that make no sense.
  3. If a check fails, throw, with the name of the thing and the value you got. Don't return false, null or 0 and hope someone checks.
  4. At the edge, validate input before it reaches those functions, and answer the person politely. The function's check is for the mistake you didn't think of.

In PHP
  • declare(strict_types=1) and typed parameters and returns: the cheapest defense there is. A wrong type is a TypeError.
  • InvalidArgumentException for an argument that's the right type and the wrong value; DomainException or your own exception class for a state that shouldn't happen. See Exceptions and Try/Catch.
  • match with no default throws UnhandledMatchError for a case you didn't list, instead of falling through.
  • assert() checks things in development. In production it's normally switched off (zend.assertions = -1), so never use it for anything that has to happen.
    • Gotchas
  • Exceptions aren't for users. A visitor who types a bad code should see "That code isn't one of ours," not a stack trace. Validate at the edge, and let exceptions inside reach your error log, not the page.
  • Returning false on failure is a trap. Somebody will forget to check, and false becomes 0 in the next sum. PHP's older functions do this (file_get_contents(), fopen()); your own functions don't have to.
  • Don't defend everything everywhere. Checking the same value in five functions in a row is clutter, and clutter hides bugs too. Check at the edge, check where a function's own rules begin, and trust the types in between.
  • The checks are input handling too. shop.php checks that code is a string before trimming it: ask for ?code[]=HALF, and PHP hands you an array. Never trust input to be the type you expect.
    • In 1996, the first Ariane 5 rocket broke up less than a minute after launch. Its guidance software had been reused from Ariane 4, and one conversion, from a 64-bit floating-point number to a 16-bit integer, wasn't protected, because on Ariane 4 the value could never get that big. Ariane 5 was faster. The number overflowed, the guidance system shut down, and the backup, running the same code, had already done the same. Repeated side story: the Ariane 5 story is also told in Testing. Keep one, make this a callback, or cut it.

    "Invalid percentage" tells you something went wrong. "percentOff must be 0 to 100, got 150" tells you what, and usually where it came from. Every exception message you write, include the value you were handed. It costs a few characters and saves the hour you'd spend reproducing it.
