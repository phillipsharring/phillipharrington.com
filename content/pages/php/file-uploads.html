File Uploads Phillip Harrington

Secrets Out of Code was about files you should never let out. Uploads are the other direction: files a stranger puts on your server. A profile photo, a PDF, a spreadsheet. Leonardo wrote it in his notebooks, backward, so nobody would steal it: never trust input, and an upload is input all the way through: the bytes, the file's name, and the type the browser says it is. Get it wrong in the worst way, and the stranger can run any command on your server.

What's an Upload?

A form field of type="file", in a form with method="post" and enctype="multipart/form-data". The browser sends the file's bytes in the request body, with two labels that it, or whoever sent the request, chose: a file name and a content type. See Forms and Content Types.

$_FILES

PHP saves the file to a temporary folder and describes it in $_FILES:

  • name: the name the sender gave it. Input.
  • type: the content type the sender claimed. Input.
  • tmp_name: where PHP put it. This one is PHP's.
  • error: UPLOAD_ERR_OK (0) if it arrived whole.
  • size: how many bytes arrived.
    •

    If your code doesn't move the temporary file somewhere, PHP deletes it at the end of the request.

    What's a Web Shell?

    A small script that runs whatever command it's sent, and sends back the result. A few lines of PHP. If someone can get one onto your server, somewhere the web server will run it, they can do anything your app can do: read its files and secrets, reach its database, and use the machine for whatever they like. The Try It below uses a stand-in that only proves it ran, rather than a real shell; the point is the same.

    How It Works
    1. The file arrives. PHP stores it in a temporary file.
    2. Your code checks that it arrived, that it's not too big, and what it really is, from its bytes, with finfo. Never from its name or its claimed type.
    3. If it isn't one of the types you accept, refuse it. An allow list: PNG, JPEG, GIF, say, and nothing else.
    4. Give it a name you make up, with an extension from your own list. Never the name it came with.
    5. Move it to a folder outside the web root, where the web server can't hand it out or run it. See Document Root.
    6. To show it, a PHP script reads it and sends it back, with a content type you chose and X-Content-Type-Options: nosniff, so the browser takes your word for it.

    Steps four and five matter most. A file named with your own extension, stored where nothing runs it, stays a file, even if every other check misses something.

    In PHP
  • $_FILES['photo']['error'] === UPLOAD_ERR_OK first. Other values say why it failed: too big (UPLOAD_ERR_INI_SIZE), only part of it arrived, no file chosen.
  • (new finfo(FILEINFO_MIME_TYPE))->file($tmp) for what the bytes say the file is.
  • getimagesize($tmp) returns false if the file can't be read as an image at all.
  • move_uploaded_file($tmp, $destination), which only moves files PHP received as uploads in this request.
  • bin2hex(random_bytes(16)) for a name nobody can guess.
  • upload_max_filesize and post_max_size in php.ini cap the size before your code runs. The defaults are 2 MB and 8 MB.
    • Gotchas
  • A file can be two things at once. The six bytes GIF89a followed by PHP code is a valid GIF to finfo and getimagesize(), and valid PHP to PHP. Break It uploads one. Type checks aren't enough on their own; your own name and storage outside the web root are what make it harmless.
  • The claimed type is just a label. $_FILES[...]['type'] is whatever the sender wrote. So is the extension in the name. Ignore both.
  • Too big can mean empty. If a request is over post_max_size, PHP throws the whole body away, and $_POST and $_FILES arrive empty, with only a warning in the log. Your form says "choose a photo" to someone who did.
  • Images can carry more than pictures. Photos from phones often include the location they were taken. Re-encoding an image with an image library, like GD or Imagick, drops that and anything else hidden in the file, but the image library is code that reads hostile files, so keep it updated.
  • SVG is not a safe image. An SVG is XML, and it can contain scripts. Served from your site, a script in it runs on your site. Leave SVG off the allow list unless you sanitize it.
    • Break It

    The naive upload keeps the file's own name, in a folder inside the web root. Make public/naive.php, and an empty public/uploads folder:

    Now the attacker's upload, proof.php. A real attacker would send a web shell; this stand-in only reports that it ran, as whom, and what it can see. Put it in an attack folder:

    Upload it:

    curl -F 'photo=@attack/proof.php' http://localhost:8000/naive.php

    New here:

    Send a form the way a file upload form does (multipart/form-data), as a POST. The field is photo, and the @ means "attach this file," rather than send the text after it.

    "Saved. It's at /uploads/proof.php." The accept="image/*" on the form never came into it; curl isn't a browser. Now visit it:

    curl http://localhost:8000/uploads/proof.php This uploaded file just ran on the server. Running as: root It can read your project: README.md, attack, public, storage

    The web server saw a .php file in its web root and ran it, as it would any other, as root (the container runs as root), with your whole project in reach, storage and all. Swap those three lines for a real web shell, and anything your app can read, or do, an attacker can too.

    Fix It

    The fixed page is the one from Try It. Send it the same file, then the same file pretending to be a PNG:

    curl -F 'photo=@attack/proof.php' http://localhost:8000/ curl -F 'photo=@attack/proof.php;type=image/png;filename=cat.png' http://localhost:8000/

    Only the new parts:

    Claim a content type for the file. curl sends whatever you say. Claim a filename, in place of the file's real name.

    Both get "That is not a PNG, JPEG or GIF," with a 422. The name and type were lies, and finfo read the bytes instead: text/x-php. Then the harder one, attack/polyglot.gif: the six bytes GIF89a, then a line of PHP. Make it with:

    printf 'GIF89a<?php echo "This GIF just ran as PHP."; ?>\n' > attack/polyglot.gif curl -F 'photo=@attack/polyglot.gif' http://localhost:8000/

    What's new:

    Print the text in the quotes. The \n at the end becomes a new line. Send what was printed into that file instead of the screen, replacing anything already in it.

    "Saved." It got through: to finfo and getimagesize(), it's a GIF. Now open the address it gave you. You get the file's bytes back, PHP code and all, as an image that won't display, and never the words "This GIF just ran as PHP." Nothing ran. The file is in storage, which the web server doesn't serve, under a name ending in .gif, and image.php only ever reads it. The checks caught the obvious attack; the storage made the clever one harmless.

    In 2016, researchers found that ImageMagick, the image library behind countless upload features, could be made to run shell commands by a specially crafted image file. Sites that did everything right with uploads, and then resized them with ImageMagick, were open to it. The bug got a name, ImageTragick, and a logo. The code that processes uploads is as exposed as the code that receives them.

    Even with uploads outside the web root, tell the web server never to run PHP from any folder that holds user files. In nginx, a location block for the folder with no PHP handler in it; on Apache running PHP as a module, an .htaccess with php_flag engine off. Then a mistake in one place, a misplaced folder or a bad deploy, doesn't become the Break It above.
