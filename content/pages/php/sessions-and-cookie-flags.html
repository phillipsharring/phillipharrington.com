Sessions and Cookie Flags Phillip Harrington

Passwords got someone logged in. From then on, the password doesn't matter. Sessions showed how PHP remembers them: a random id in a cookie, and a file on the server. Whoever has that id is logged in. So the session cookie is the login, and it's worth as much as the password. PHP's defaults don't protect it. This lesson does.

The Flags

Cookies listed the settings that can follow a cookie's value. Three of them are security, and a session cookie needs all three:

Set-Cookie: PHPSESSID=3486811b0a2015badabda8c561951706; path=/; secure; HttpOnly; SameSite=Lax Secure

Only send the cookie over HTTPS. Without it, the browser also sends it with any plain http:// request to your site, and anyone on the same network, like a café's Wi-Fi, can read it off the wire. See HTTP, HTTPS and TLS.

HttpOnly

JavaScript in the page can't read the cookie. The browser still sends it with every request; only document.cookie leaves it out. If an XSS hole ever lets a script onto your page, that script can't simply send your visitors' session ids somewhere else.

SameSite

Whether the cookie goes with requests that another site starts. Lax sends it when someone follows a link to your site, but not with a form another site POSTs to yours, which is most of CSRF. Strict never sends it from another site, even on a link, so people arriving from a link look logged out. None always sends it, and requires Secure.

What's Session Fixation?

An attack on the id itself. Instead of stealing your session id, the attacker picks one, gets your browser to use it, and waits for you to log in. If your site keeps the same id across the login, the attacker's copy is now logged in as you. The way in can be a cookie set from a sibling subdomain, an XSS hole, or a link, on old sites that accepted the id in the URL.

In 2010, Eric Butler released Firesheep, a Firefox add-on. On an open Wi-Fi network, it listened for other people's session cookies from sites like Facebook and Twitter, which used HTTPS for the login page and plain HTTP after it. One click, and you were logged in as the person at the next table. Nothing about the attack was new. Making it one click was, and within a few years the big sites had moved to HTTPS for everything. How It Works
  1. Before session_start(), your code sets the cookie's flags with session_set_cookie_params(), and turns on strict mode.
  2. A visitor arrives with a session id in a cookie. In strict mode, if PHP has no session with that id, it ignores it and makes a new one. Without strict mode, PHP accepts any id it's given and starts a session under it.
  3. They log in. Your code calls session_regenerate_id(true): same session data, new id, old one deleted. Then it records who they are.
  4. The response carries the new id in a Set-Cookie, with all three flags.
  5. When they log out, your code empties the session, destroys it, and tells the browser to delete the cookie.

The new id at login is the part people miss. Whoever knew the id before login, through fixation or anything else, has an id that now leads nowhere.

In PHP
  • session_set_cookie_params(['secure' => true, 'httponly' => true, 'samesite' => 'Lax', ...]), before session_start(). Or the same in php.ini: session.cookie_secure, session.cookie_httponly, session.cookie_samesite.
  • session.use_strict_mode = 1, so PHP refuses ids it didn't make. It's off by default.
  • session_regenerate_id(true) at login, and whenever someone's access changes, like becoming an admin. The true deletes the old session.
  • To log out: $_SESSION = [];, session_destroy();, and a setcookie() with the session's name and a time in the past.
  • setcookie('name', $value, ['secure' => true, 'httponly' => true, 'samesite' => 'Lax']) for any other cookie that matters.
    • Gotchas
  • Don't decide Secure from the request. Code like 'secure' => isset($_SERVER['HTTPS']) looks right, and goes wrong the day there's a CDN or proxy in front, because the last hop to PHP is plain HTTP. See What's in the Middle. Turn it on in configuration, and leave it on.
  • Secure on localhost. Chrome and Firefox treat http://localhost as secure and accept the cookie anyway, so it works while you develop. Other browsers may not. That's a reason to develop on HTTPS, not a reason to turn the flag off.
  • Flags must be set before the session starts. session_set_cookie_params() after session_start() does nothing for this request, and PHP warns.
  • The session id is input. It arrives in a cookie, so anyone can send any id. Strict mode and a new id at login are how you never trust input here: don't let the visitor choose it.
  • Sessions end late by default. PHP cleans up idle sessions after session.gc_maxlifetime (1440 seconds), but only now and then, and a cookie with no lifetime lasts until the browser closes, which on many phones is never. If a login should expire, store the time it started in the session and check it yourself.
    • One of my apps sent its login cookies without the Secure flag for months. The code set the flag only when $_SERVER['HTTPS'] was on, and behind the CDN it never was: the CDN talked HTTPS to visitors and plain HTTP to the server. Nothing looked wrong, because everything worked. The fix was to stop asking the request and set the flag in configuration. Break It

    Session fixation, against your own copy. You'll play both parts with curl, using the -b flag to send a cookie. First, the attacker picks an id and gets the victim's browser to use it. Then the victim logs in with it, as usual:

    curl -b 'PHPSESSID=attacker-picked-1' --data-urlencode 'email=alice@example.com' \ --data-urlencode 'password=correct horse battery staple' http://localhost:8000/naive.php

    Logged in as alice@example.com. Now the attacker, who never knew the password, visits with the id they picked:

    curl -b 'PHPSESSID=attacker-picked-1' http://localhost:8000/naive.php

    Logged in as alice@example.com. PHP accepted an id it had never made, and the login didn't change it, so the attacker's id became Alice's login.

    Then the same attack, with a fresh id, against the fixed page:

    curl -b 'PHPSESSID=attacker-picked-2' --data-urlencode 'email=alice@example.com' \ --data-urlencode 'password=correct horse battery staple' http://localhost:8000/ curl -b 'PHPSESSID=attacker-picked-2' http://localhost:8000/

    Alice is logged in, and the attacker gets Not logged in. Strict mode refused the made-up id, and the login moved Alice to a brand-new one that only her browser has. In the browser, log in on http://localhost:8000/ and try document.cookie again: the session id isn't there.

    After any deploy that touches login, run curl -sI https://your-site/login | grep -i set-cookie against the real site, through the CDN, the way visitors reach it. If secure, HttpOnly and SameSite aren't all there, something in the chain is deciding for you.

    Your login now holds up once someone's in. Getting in is still a form anyone can submit as many times as they like, with a new guess at the password each time. Next: rate limiting.
