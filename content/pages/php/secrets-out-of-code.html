Secrets Out of Code Phillip Harrington

Rate Limiting ended with a database password sitting in compose.yml. On your own computer, for a pretend database, that's fine. Anywhere real, a password in a file you commit is a password you've given to everyone who will ever see the repository, and to everyone they share it with. Configuration and the Environment said secrets never go in git. This lesson is what happens when one does, and where they go instead.

What's a Secret?

Anything that lets someone act as your app: database passwords, API keys for payments and email, the key that signs your cookies or tokens, cloud credentials. If a stranger with a copy could use it to read your data or spend your money, it's a secret.

Things that aren't secrets, like the name of the database or which features are turned on, can live in the code. The test is simple: would you paste it in a public chat?

What's the Environment?

Every running program gets a set of named values from whatever started it: environment variables. PHP reads them with getenv(). Docker sets them with -e NAME=value or --env-file, and on a server, a secrets manager or the deploy can. The code only knows the names. The values come from outside the repository, and can be different on every machine.

What's Rotation?

Replacing a secret with a new one, and turning the old one off. Every service that issues keys lets you make a new one and revoke the old. Once a secret has leaked, rotation is the only fix there is.

How It Works
  1. The code asks for each secret by name, like getenv('PAYMENT_API_KEY'), and stops at once if one is missing.
  2. The repository has a .env.example with every name and no values, so the next person knows what to fill in.
  3. On your computer, a .env file holds pretend or test values, and .gitignore keeps it out of git.
  4. On a server, the values come from a secrets manager (every cloud has one), read into memory when the app starts. Not a file on disk if you can help it.
  5. Each environment gets its own secrets. Test keys on your computer, live keys only in production, so a leaked laptop isn't a leaked business.

In PHP
  • getenv('NAME') returns the value, or false if it isn't set. Check for both false and ''.
  • throw new RuntimeException(...) when one is missing. Never a default value: a default secret is a secret in the code.
  • substr($key, -4) when you need to show which key is loaded. Never the whole thing, anywhere.
  • phpinfo() prints every environment variable, secrets included. Another reason it never stays on a server; see PHP Files, Escaping into PHP, and phpinfo().
    • Gotchas
  • Docker's --env-file doesn't remove quotes. KEY="abc" sets the value to "abc", quotes and all. Write KEY=abc. (Other tools that read .env files do strip them, which is why this one catches people.)
  • A key in the browser is public. Anything in your JavaScript, your HTML or your app's download can be read by anyone who uses it. Keys that must stay secret stay on the server, and the browser asks your server.
  • Secrets leak into logs. An error that dumps the config, a debug line that prints the request headers, an exception with a connection string in it. Search your logs for the last four characters of a key now and then.
  • Temporary files are files. A script that writes the secrets to /tmp "for a moment" leaves them readable by anyone on the machine, and there after a crash. If you must, use mktemp, which makes a file only you can read, and delete it on exit.
  • Default credentials are secrets in code. A seed script that creates admin@example.com with the password password is handy on your computer. One of my apps ran its seeds on production deploys, until that was stopped. Seeds are for development; production accounts are made by hand, with real passwords.
    • Repeated side story: the seed admin story (admin@example.com / password on production) is also told in Configuration and the Environment. Keep one, make this a callback, or cut it. One of my apps kept its production secrets in .env files on the servers' disks. They moved into a secrets manager, loaded into memory when the app starts, and every secret was rotated, because there was no telling who had read those files over the years. Along the way, a deploy script turned out to leave a copy of the production .env in /tmp, readable by anyone on the machine.     In a new, empty folder, copy it in as config.php, and commit it, the way it happens on a busy afternoon:

    git init git add config.php git commit -m "Add config" New here: Stage the file: mark it to go into the next commit. Save everything staged as a commit, one permanent step in the history. The commit's message, saying what changed. Without it, git opens an editor to ask you.

    Then someone notices. Copy the fixed config.php from Try It over it, and commit the fix:

    git commit -am "Move the key out of the code" Only the new part: Stage every file git already tracks that has changed, then commit. It saves a separate git add. (-am is -a and -m together.)

    The key isn't in the code anymore. Open config.php and it's gone. Now ask git:

    git log -p | grep pretend-live-key - 'payment_api_key' => 'pretend-live-key-8f3a9c2e7d41', + 'payment_api_key' => 'pretend-live-key-8f3a9c2e7d41', What's new: List the commits, newest first. Show each commit's changes too, line by line: - for a line taken out, + for a line put in.

    There it is, twice: added in the first commit, removed in the second. Git keeps every version of every file. Anyone who clones the repository, today or in five years, gets the key. So does every fork, every copy on every laptop, and every backup. Automated scanners read public repositories for keys like this within minutes of a push.

    Fix It

    The fix comes in an order, and the first step is the one that counts:

    1. Rotate the key. Make a new one in the service's dashboard, put it where the app reads it, and revoke the old one. Now the leaked key is worthless, wherever it went.
    2. Move the code to the environment, as in Try It: config.php with getenv(), .env in .gitignore, and .env.example committed.
    3. Optionally, rewrite the history with a tool like git filter-repo. It tidies the repository, but it can't reach the copies already made, so it never replaces step one.
    In 2016, attackers got into a private GitHub repository used by Uber's engineers and found credentials for the company's cloud storage. With them, they downloaded data on about 57 million riders and drivers. The repository was private. The keys being in it was the problem.

    Before pushing a new repository, or one you've been careless with, search all of its history at once: git log -p --all | grep -iE "key|secret|password|token". It's noisy, and it's a few minutes. GitHub also scans pushes for known key formats and can block them; turn on secret scanning for your repositories, and treat a hit as "rotate now," not "delete the commit."
