Configuration and the Environment Phillip Harrington

PHP-FPM runs on settings: how many workers, whether to show errors, whether to say which version it is. Your app has settings too: the database password, an API key, whether it's on your computer or the live server. The same code runs in both places, with different settings, and some of those settings are secrets. None of them belong in the code.

What's Configuration?

Anything that changes between the places your code runs: where the database is and its password, keys for other services, the site's address, whether errors are shown. The code is the same everywhere. The configuration is what makes this copy yours, or the live one.

A good test: could you publish your code right now, for anyone to read, without giving away a single password? If not, some configuration is still in the code.

In 2011, developers at the hosting company Heroku published "The Twelve-Factor App," a short list of rules for building apps that run well on servers you don't control. The third factor is "store config in the environment." The publish-it-now test above is theirs. A lot of what's normal now, like the .env file, grew up around it. What's the Environment?

The word means two things here, and they meet.

Environment Variables

Named values every program gets from whatever started it: APP_ENV=production, DB_HOST=db. Your terminal has dozens. Docker, the server's setup, or a hosting panel can set them for PHP, and PHP reads them with getenv(). They're the usual way to hand a program its settings, because they're nowhere in the code.

Development and Production

The other meaning is the place the code is running. Development is your computer. Production is the live site, with real visitors. Many teams have staging in between, a copy of production for trying things first. Apps usually learn which one they're in from an environment variable, often called APP_ENV, and behave accordingly: show errors in development, never in production.

One of my apps had seed scripts: small programs that fill a fresh database with test data, including an admin account at admin@example.com with the password password. Handy in development. They also ran on production deploys, until we stopped them. A setting that says "this is production" is only useful if the code asks it. What's a .env File?

A text file of settings, one NAME=value per line, that something loads into the environment before your code runs. Docker reads one with --env-file, and Compose with env_file:. PHP libraries can read one too, once you have Composer.

The file with the real values is called .env, and it never goes in git. Next to it, in git, is .env.example: the same names, with blank or harmless values. It tells the next person, or you in a year, which settings the app needs.

PHP's Own Settings

PHP reads its settings, like display_errors, from a file called php.ini. php --ini says which one it loaded. In the official Docker images, the answer is none: they come with two samples, php.ini-development and php.ini-production, and you copy the one you want into place. For one run, php -d name=value sets a setting on the command line, as Access and Error Logs did. In code, ini_set() changes some of them while the script runs.

How It Works
  1. Something puts the values in the environment: Docker from a .env file, the server's setup, or a secrets manager.
  2. The web server or PHP-FPM starts, and inherits them.
  3. Your code reads each one with getenv().
  4. At the start, it checks the ones it can't live without, and stops with a clear error if any is missing.

On your computer, the .env file is fine. On a live server, a file full of secrets sitting on the disk is one more thing to steal. Better is a secrets manager, a service that holds them and hands them to the app when it starts, so they live only in memory. Secrets Out of Code, in Security, goes further.

One of my apps kept its production secrets in .env files on the servers' disks. We moved them into a secrets manager, loaded into memory when the app starts, and then rotated every one: changed each password and key, so the copies that had sat on disk were worth nothing. Try It

In PHP
  • getenv('NAME') reads an environment variable. It gives back false when there isn't one, so getenv('NAME') ?: 'default' handles both missing and empty.
  • $_ENV holds them too, but only when PHP's variables_order setting includes E. php.ini-production leaves it out, so $_ENV is often empty. getenv() works either way.
  • ini_get('display_errors') reads one of PHP's settings.
  • ini_set('display_errors', '0') changes it, for this script only.
  • php_ini_loaded_file() says which php.ini PHP loaded, if any.
    • Gotchas
  • A secret committed once is in git forever. Deleting the file in the next commit leaves it in the history, for anyone with a copy. If a secret ever goes in, change the secret.
  • Copies of secrets leak. One of my apps had a deploy script that left a copy of the production .env in /tmp, readable by anyone on the machine, until it was fixed to use a private temporary file, deleted when the script finished. Every copy is another place to lose it.
  • .env formats aren't all the same. Docker's --env-file keeps quotes as part of the value, so APP_NAME="Shirt Shop" comes out with the quote marks in it. Many PHP libraries strip them. Check what yours does.
  • PHP-FPM can hide the environment. Its clear_env setting is on by default, which empties the environment before your code sees it. The official Docker image turns it off; on other servers, turn it off, or pass each variable in the pool settings.
  • Secrets in the environment show up in phpinfo(). It prints every environment variable. Never leave it on a live server; the next lesson says more.
  • Missing should mean safe. When APP_ENV isn't set, the example assumes production, so a forgotten setting hides errors rather than showing them to the world.

    • When you change a key, you'll want to know whether the app picked up the new one. Have it log or show only the last four characters, like the example. That's enough to tell two keys apart, and not enough to use either.
