Relating Tables: Keys and Foreign Keys Phillip Harrington

The books in SQL kept the author's name in every row, typed out again for each book. A real catalog keeps authors in a table of their own, and each book points at its author. The pointing is done with keys, and the database can hold you to it: no book can point at an author who isn't there.

What's a Primary Key?

The column that tells one row from every other, like id in Creating Tables. Every table gets one. It never repeats, it's never NULL, and once a row has one, it shouldn't change, because other rows are using it to find this one.

Natural and Surrogate Keys

A natural key is something real that's already unique: an email address, an ISBN. A surrogate key is a number the database makes up, with AUTO_INCREMENT, that means nothing outside it. Use the surrogate. Real things change (people change email addresses) and turn out not to be unique after all (old books have no ISBN, and some share one by mistake). Keep the real value in its own column, with a UNIQUE rule if it has to be unique.

What's a Foreign Key?

A column that holds another table's primary key. books.author_id holds an authors.id. Declared as a foreign key, it's also a rule: the database won't let it hold an id that doesn't exist.

CONSTRAINT `books_author_id_fk` FOREIGN KEY (`author_id`) REFERENCES `authors` (`id`) One to Many

One author, many books: the foreign key goes on the "many" side. Each book names one author. The author doesn't list her books; you find them by asking which books point at her.

Many to Many

A book has many tags, and a tag has many books. Neither table can hold the other's key, so a third one does: book_tags, with one row per pairing, a book_id and a tag_id. Its primary key is both columns together, so the same pair can't be added twice.

Before relational databases, records were linked by pointers: a program found an author, then followed a stored link to her first book, then from that book to the next. Charles Bachman designed one of the first of these databases, and called his 1973 Turing Award lecture "The Programmer as Navigator." Edgar Codd's relational model, in 1970, replaced the pointers with values. A book holds its author's id, and any query can follow it, in either direction. Codd got his own Turing Award in 1981. How It Works
  1. You make the parent table first (authors), then the child that points at it (books).
  2. On every insert or update of a book, the database looks up its author_id in authors. No such author, no row.
  3. On every delete of an author, it looks for books that point at her. If there are any, by default, the delete is refused.
  4. To read across the link, a query joins the tables, matching each book's author_id to an author's id.

Step three can do other things instead, like deleting the books along with the author. That's in Deleting Data.

Try It

Authors, books and tags, linked. The same compose.yml, Dockerfile and db.php as in SQL, and a new init.sql:

Start the database and open the mysql command:

docker compose up -d --wait db docker compose exec db mysql -u app -papp-password course

Ask for each book with its author's name. INNER JOIN pairs each book with the author its author_id points at:

SELECT `books`.`title`, `authors`.`name` FROM `books` INNER JOIN `authors` ON `authors`.`id` = `books`.`author_id` ORDER BY `books`.`year`;

And across the many-to-many, every book tagged science fiction:

SELECT `books`.`title` FROM `books` INNER JOIN `book_tags` ON `book_tags`.`book_id` = `books`.`id` INNER JOIN `tags` ON `tags`.`id` = `book_tags`.`tag_id` WHERE `tags`.`name` = 'science fiction' ORDER BY `books`.`title`;

Now try to break the links. A book by an author who doesn't exist:

INSERT INTO `books` (`author_id`, `title`, `year`) VALUES (99, 'Nobody', 2000);

Refused: a foreign key constraint fails, and the message names the rule, books_author_id_fk. Then delete an author who still has books:

DELETE FROM `authors` WHERE `id` = 1;

Refused again: Cannot delete or update a parent row. Mary Shelley stays, and Frankenstein still has an author. Type exit. From PHP, the same rule catches a bad id. Make add-book.php:

Add a book for an author who exists, then one who doesn't:

docker compose run --rm php php add-book.php 2 'Dawn' 1987 docker compose run --rm php php add-book.php 99 'Nobody' 2000

The first is added. The second is a perfectly good number, so it passes the script's own checks, and the foreign key refuses it. Never trust input: an id from a form or a URL is only a number someone sent you. The script checks that it's a number; the database checks that it's real. docker compose down -v when you're done.

In PHP
  • $pdo->lastInsertId() gets the id the database just made, so you can use it as the foreign key in the next insert: an author, then her books.
  • $e->errorInfo[1] on a PDOException is MySQL's own error number: 1452 for a child row with no parent, 1451 for a parent that still has children, 1062 for a duplicate key.
  • filter_var($id, FILTER_VALIDATE_INT, ['options' => ['min_range' => 1]]) before any id goes near a query. Ids start at 1.
    • Gotchas
  • Both sides of a key must be the same type. An INT pointing at an INT UNSIGNED is refused when you create the table: Referencing column and referenced column are incompatible. Copy the type exactly.
  • Order matters, both ways. Create parents before children, and drop children before parents. A table can't point at one that isn't there yet.
  • Only InnoDB enforces foreign keys. InnoDB is MySQL's default engine, and the one to use. An old table on MyISAM accepts the foreign key in its definition and then ignores it, quietly.
  • An id that exists isn't an id that's theirs. The foreign key proves the author is real. It doesn't prove the person asking may change her books. Check that the row belongs to whoever is asking, every time. Never trust input, even when it's a valid id.

    • Call every primary key id, and every foreign key the singular of its table plus _id: author_id, book_id. Then `authors`.`id` = `books`.`author_id` is the only way a join can be written, and a wrong one looks wrong. Name the constraints too, like books_author_id_fk, so the error tells you which link broke.

    Moving the authors into their own table wasn't only tidier. It means each author's name is written down once, so it can't be spelled two ways. That idea has a name. Next: normalization.
