Single Point of Entry Phillip Harrington

MVC ended with two entry points, index.php and item.php, that repeated the same setup line for line. Two is annoying. Twenty is a security problem, because the setup is where the login check lives, and one of the twenty will forget it. The fix is to have one entry point, and send every request through it.

What's a Single Point of Entry?

One PHP file, usually public/index.php, that every request goes to, whatever its URL. It's also called a front controller. It does the setup once, looks the path up in a list of routes, checks whether this visitor may see it, and only then runs the code for that page. The pages themselves move out of the web root, where no URL can reach them directly.

Routes

The list that maps a URL, like /account, to the code that handles it, and often to who may use it. Because the list is yours, the URL can only ever pick one of your rows. It never gets to name a file.

Martin Fowler gave "Front Controller" its name in Patterns of Enterprise Application Architecture, in 2002, alongside many of the other patterns in this section. PHP sites were mostly a file per page then. The PHP frameworks that arrived over the next few years, like Symfony, CakePHP and CodeIgniter, sent everything through one index.php. How It Works
  1. The web server is told: if the URL is a real file in public/, like a stylesheet, send it; otherwise, run index.php.
  2. index.php does the setup every page needs: settings, autoloader, user.
  3. It looks up the path in the routes. No route, 404.
  4. It checks the route's rules against the visitor: logged in, the right role. One check, for every page, written once.
  5. It runs the page's code, often a controller method, and sends the result.

A stranger gets 404. So does Alice, who is logged in but isn't an admin: from Expressive HTTP Response Codes, a page you can't have doesn't admit it exists. Only Ada, the admin, gets in. /account asks for a login, /admin.php is a 404 because there's no such route, and /style.css comes back as a stylesheet. A new page is a row in routes.php, and it can't forget its check, because it never had one of its own.

In PHP
  • php -S 0.0.0.0:8000 -t public public/index.php: a router script for the built-in server. Returning false from it tells the server to send the file itself.
  • In nginx: try_files $uri /index.php?$query_string;. In Apache: FallbackResource /index.php. Both mean "the file if it exists, otherwise the front door."
  • parse_url($_SERVER['REQUEST_URI'], PHP_URL_PATH) gets the path without the query string, ready to look up.
  • Real routers, like nikic/fast-route through Composer, add placeholders (/notes/{id}) and methods. The idea is the same table.
    • Gotchas
  • Never let the URL name the file. require "pages/{$_GET['page']}.php" looks like a shortcut to the same thing, and it lets a visitor pick any file on the server, with ../ to climb out. That's called local file inclusion. Say it with me: never trust input. The URL picks a row in your table, and your table names the file.
  • The "is it a real file" check is input handling too. The path in it came from the visitor. index.php resolves it with realpath() and makes sure it's still inside public/ before it hands anything to the server.
  • Old pages left in the web root still answer. Moving to a front controller means deleting the old admin.php, not just no longer linking to it. A forgotten file is a second door.
  • The 404 has to come from you. With every unknown URL sent to index.php, nothing else will send one. Make sure "no route" really answers 404, or every typo is a 200.

    • Keep the routes in one file you can read top to bottom, with who may see each one on the same line. Every so often, read the whole list. It's the map of your app's doors, and it's the fastest way to spot the one that's missing its lock.
