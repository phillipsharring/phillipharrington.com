DNS Phillip Harrington

In Client/Server, the server had to be easy to find. Computers find each other by number, the IP address, but people use names. DNS, the Domain Name System, is how a name like phillipharrington.com turns into a number a client can connect to. It happens before every new connection, usually in a few milliseconds, and you only notice it when it breaks.

What's an IP Address?

The number a computer is reached at, like a phone number. The older kind, IPv4, is four numbers from 0 to 255 with dots between them: 203.0.113.7. The newer kind, IPv6, is much longer and written in hexadecimal with colons. Both are still in use, side by side.

What's a Domain Name?

The name people type instead of the number. It reads right to left, from general to specific: in www.phillipharrington.com, com is the top-level domain, phillipharrington is the name someone registered under it, and www is a subdomain the owner made up. The owner can make as many of those as they like.

What's a DNS Record?

A domain's DNS is a short list of records, each one a fact about the name. The ones you'll meet:

  • A: this name is at this IPv4 address.
  • AAAA: the same, for an IPv6 address.
  • CNAME: a name for another record; go look that one up instead.
  • MX: mail for this name goes to this server.
  • TXT: a note, usually proof to some service that you own the domain, or rules about who may send its email.
  • NS: these servers are in charge of this name's records.
    •

    Every record also has a TTL, "time to live": how many seconds anyone who looks it up may remember the answer before asking again.

    Before DNS, every computer on the early internet kept a copy of one file, HOSTS.TXT, listing every machine's name and number. It was maintained by hand at a single office at the Stanford Research Institute, and you got updates by downloading it again. By the early 1980s it was changing faster than anyone could copy it, so in 1983 Paul Mockapetris designed DNS to replace it. How It Works

    When your browser needs the address for a name, it goes something like this:

    1. The browser checks whether it looked this name up recently.
    2. If not, your computer checks its own memory, and a small file called the hosts file, where you can pin names to addresses yourself.
    3. If not, it asks a resolver: a DNS server run by your internet provider, or a public one like Cloudflare's 1.1.1.1 or Google's 8.8.8.8.
    4. If the resolver doesn't know either, it starts at the top. It asks a root server, "who's in charge of .com?" Then it asks the .com servers, "who's in charge of phillipharrington.com?" Then it asks that domain's own servers for the record itself.
    5. The answer comes back down the chain, and every step remembers it for as long as the TTL allows.

    That memory is why DNS is fast: almost every lookup is answered from step one, two or three. It's also why DNS changes are slow. Change a record, and the old answer lives on in caches all over the world until their TTLs run out.

    Notice the resolver is a server to you and a client to the root, the .com servers and the domain's servers. Same relationship as last time, more links in the chain.

    Step back and it's remarkable. Nobody runs DNS. Thousands of separate organizations, the root operators, every top-level domain's registry, every company and person with a domain, each run their own small piece of it, and they cooperate on nothing but an agreed set of rules. It was designed in 1983 for a few thousand computers, and the same design now answers for billions of them, all day, mostly without anyone noticing. It's one of the great pieces of engineering of the last century, and also one of the great examples of the world agreeing to work together.

    There are thirteen root server names, a.root-servers.net through m.root-servers.net, run by twelve different organizations. But each name is many actual machines around the world sharing one address, well over a thousand in all, and you're answered by whichever is closest. Try It

    PHP can do DNS lookups itself, so start there. In a folder, make a file called dns.php:

    <?php $host = $argv[1] ?? 'phillipharrington.com'; echo gethostbyname($host), "\n"; print_r(dns_get_record($host, DNS_A)); print_r(dns_get_record($host, DNS_MX));

    Run it in a container, the same way as last time, giving it a name to look up:

    docker run --rm -v "$PWD":/app -w /app php:8.4-cli php dns.php phillipharrington.com

    The first line is one address: gethostbyname() asks the question the way a browser would and takes the first answer. Then dns_get_record() shows the actual A records, several of them, each with its TTL. This site sits behind a CDN, so the name points at a handful of the CDN's servers.

    The MX records are where its email goes: five of Google's mail servers, each with a priority number (pri). Senders try the lowest number first and work up the list if it doesn't answer. Try another name, and the mail setup is different:

    docker run --rm -v "$PWD":/app -w /app php:8.4-cli php dns.php reuselists.com

    One MX record this time. Then ask a different client, the one that comes with every operating system:

    nslookup phillipharrington.com

    Same answer, different client. It also tells you which resolver answered, at the top.

    In PHP

    Most of the time PHP does DNS for you without asking: connecting to a database by name, or fetching a URL, starts with a lookup. When you need one yourself, three functions cover it:

  • gethostbyname(): one IPv4 address for a name.
  • dns_get_record(): the records themselves, any type.
  • checkdnsrr(): does a record of this type exist? The classic use is a signup form: checkdnsrr($domain, 'MX') tells you whether an email address's domain accepts mail at all, before you try to send to it.
    • Gotchas
  • "I changed it, but I still see the old site." The old answer is cached somewhere between you and the domain's servers. It goes away when the TTL runs out. Waiting is the fix; so is the $2 tip below, next time.
  • gethostbyname() doesn't fail like you'd expect. When a name doesn't exist, it returns the name you gave it, unchanged, not false. Check whether what came back is an address.
  • The hosts file wins. A name pinned in your hosts file never reaches DNS at all. That's how local development names like myapp.test work, and why a forgotten line in it can make one computer see a different site from everyone else.
    • Operations people have a haiku about outages: "It's not DNS. There's no way it's DNS. It was DNS." Funny because it's true: when everything is broken at once, DNS is the first thing to check.

    Moving a site to a new server? A day before, lower the TTL on its records to five minutes. Then, when you switch, the old address only lingers for five minutes instead of a day. Once it's settled, turn the TTL back up.

    Now the client has an address, and can open a connection. Next: the language they speak once they're connected, HTTP.
