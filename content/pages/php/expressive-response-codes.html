Expressive HTTP Response Codes, and When Not to Be Phillip Harrington

Every response starts with a status code, from Request and Response. It's the first thing a browser, a script or a CDN reads, and often the only thing. A good one tells the client exactly what happened, so it knows what to do next. Then there's the other half of the lesson: some clients are attackers, and some exact answers are exactly what they came for.

What's an Expressive Code?

The most specific code that's true. Not 200 with {"error": "..."} in the body, and not 400 for every kind of mistake. The ones you'll use most:

  • 200 OK: here's what you asked for.
  • 201 Created: it's made, and the Location header says where.
  • 204 No Content: done, and there's nothing to send back.
  • 400 Bad Request: the request itself is broken, like JSON that won't parse.
  • 401 Unauthorized: who are you? Not logged in, or the credentials didn't work. Despite the name, it's about authentication.
  • 403 Forbidden: I know who you are, and you can't do this.
  • 404 Not Found: there's nothing here.
  • 405 Method Not Allowed: this URL exists, but not for that method. The Allow header lists the ones that work.
  • 409 Conflict: it clashes with what's there, like a username that's taken.
  • 422 Unprocessable Content: well-formed, but the values are wrong. The usual answer to a form that doesn't validate.
  • 429 Too Many Requests: slow down. Retry-After says for how long; see Rate Limiting.
  • 500 Internal Server Error: our fault. 503 Service Unavailable: our fault, and temporary.
    • When Not to Be

    An exact answer helps whoever asked, and you don't choose who asks. Anything that tells a stranger whether an account or a record exists is information they can collect, one request at a time. So for those, and only those, be vague on purpose:

  • A failed login says "Wrong email or password," never which one. "No account with that email" turns your login form into a free tool for checking which addresses are your customers. Then they only have to guess passwords for the ones that are.
  • Something that isn't yours is a 404, not a 403. A 403 on /notes/2 confirms note 2 exists. A 404 is the same answer a note that never existed gets, so it gives nothing away.
  • A password reset says "If that address has an account, we've sent a link," whether it does or not.

    • Expressive to your users, vague to your attackers. A real user who mistyped their password knows which half they're unsure of. Only someone fishing needs the difference.

    418 I'm a teapot comes from RFC 2324, an April Fools' standard from 1998 for controlling coffee pots over HTTP. A teapot asked to brew coffee answers 418. It was never meant to be used, and it's in plenty of software anyway, and when a proposal came up to remove it, enough people objected that the code was reserved instead. Repeated side story: the I'm a Teapot story is also told in Request and Response. Keep one, make this a callback, or cut it. How It Works
    1. The client reads the code first. Scripts, browsers, CDNs and monitoring all decide what to do from it: retry, redirect, show an error, cache or not.
    2. The body explains, for a person, if there's a person.
    3. Headers that go with the code finish the answer: Location with 201 and redirects, Allow with 405, Retry-After with 429 and 503, WWW-Authenticate with 401.
    4. For anything an attacker could learn from, the code, the body and the time it takes are the same for "doesn't exist" and "not for you."

    From a second terminal, be an attacker with a list of addresses:

    curl -i -d 'email=nobody@example.com&password=x' http://localhost:8000/login curl -i -d 'email=alice@example.com&password=x' http://localhost:8000/login

    The first says "No account with that email." The second says "Wrong password." You've learned that Alice is a customer without knowing anything about her. Time them, and they leak it again:

    curl -s -o /dev/null -w '%{time_total}\n' -d 'email=nobody@example.com&password=x' http://localhost:8000/login curl -s -o /dev/null -w '%{time_total}\n' -d 'email=alice@example.com&password=x' http://localhost:8000/login All seen before: -s keeps curl quiet, -o /dev/null throws the page away, and -w '%{time_total}\n' prints how long it took.

    The stranger's answer comes back in a few milliseconds. Alice's takes a fraction of a second, because only a real account gets its password checked, and password_verify() is slow on purpose. Now log in as Alice (her token is alice-token), and ask for a note that isn't hers, then one that doesn't exist:

    curl -i -H 'Authorization: Bearer alice-token' http://localhost:8000/notes/2 curl -i -H 'Authorization: Bearer alice-token' http://localhost:8000/notes/9

    403, "That note belongs to someone else," then 404. Count up from 1, and the 403s map every note in the system. Stop the server, and make after.php:

    Start it the same way, with after.php at the end:

    docker run --rm -it -p 8000:8000 -v "$PWD":/app -w /app php:8.4-cli php -S 0.0.0.0:8000 after.php

    Ask the same four questions. Both logins get the same 401 and "Wrong email or password," in about the same time: when there's no account, it checks the password against a dummy hash anyway. Both notes get the same 404. Then the honest mistakes, which get as specific as they like:

    curl -i -H 'Authorization: Bearer alice-token' -d 'text=Hello' http://localhost:8000/notes curl -i -H 'Authorization: Bearer alice-token' -d 'text=' http://localhost:8000/notes curl -i http://localhost:8000/login

    201 Created with a Location; 422 with what a note should be; 405 with Allow: POST. Every one of those tells a real client what to do next, and none of them tells an attacker anything about anyone.

    In PHP
  • http_response_code(404) sets the code. Call it before any output, like header().
  • header('Location: /notes/3'), header('Allow: POST') and the rest for the headers that go with a code.
  • A never return type on a function that always ends in exit, like respond(), so PHP and your editor know nothing runs after it.
  • password_verify() against a dummy hash when the account doesn't exist, so both answers take the same time. See Passwords.
  • $_SERVER['HTTP_AUTHORIZATION'] and every field in $_POST are input. You know the drill. Never trust input: check that a token is one you issued, and that text is a string before you measure it.
    • Gotchas
  • A 200 with an error in the body is a lie. Caches keep it, monitoring counts it as success, and every client has to read the body to find out something went wrong.
  • A 500 should say nothing. "Something went wrong" for the user, and the stack trace for your error log. A trace on the page shows file paths, queries and sometimes secrets. See Errors and the Error Log.
  • Signup forms leak too. "That email is already registered" answers the same question the login form now refuses to. You can't always avoid it, but you can rate-limit it, or send the "you already have an account" news by email instead of on the page.
  • Vague isn't the same as wrong. Don't answer a failed login with 200 to hide it, or a missing page with a redirect home. Use the honest code, and keep the details out of it.
  • Something in the middle can change your code's answer. A CDN or proxy can swap your error responses for its own pages. Test your error codes through the whole chain, not only on your laptop.
    • One of my apps sat behind a CDN that was set to replace every 403 and 404 with its own friendly error page. That's fine for a website. It applied to the API too, so the app's JavaScript, expecting a small JSON error, got a whole HTML page and fell over. The status codes were right; something in the middle had rewritten the answer.

    curl -s -o /dev/null -w '%{http_code}\n' URL prints the status code and nothing else. Put a handful of those in a script, with the code you expect next to each, and you have a check of every answer your app gives, honest and vague, that runs in a second.
