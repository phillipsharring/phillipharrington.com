REST Phillip Harrington

CRUD answered a browser, with forms, HTML and redirects. When the client is a program, a phone app or JavaScript using fetch(), it wants JSON, and it can use every HTTP method, not just the two forms know. REST is the set of conventions most of those APIs follow, so that a developer who has used one can guess how yours works.

What's REST?

Representational State Transfer: a way of designing an API around the web's own parts. In practice, for a PHP API, it comes down to three rules.

  • URLs name resources. Nouns, not verbs. /notes is the collection; /notes/3 is one note. Not /getNote?id=3 or /deleteNote.
  • Methods say what to do. GET reads, POST to a collection creates, PUT replaces, PATCH changes part, DELETE deletes.
  • Status codes say how it went. 201 for created, 204 for done with nothing to say, 404, 422 and the rest from Expressive HTTP Response Codes.
    • Stateless

    Each request carries everything the server needs to answer it, including who's asking, usually as a token in the Authorization header. The server doesn't remember the last request. That's what lets an API run on many servers behind a load balancer, from What's in the Middle: any of them can answer any request.

    Safe and Idempotent

    GET is safe: it changes nothing. GET, PUT and DELETE are idempotent: sending one twice leaves things the same as sending it once. Replace note 3 with "Buy beans" twice, and it says "Buy beans." POST isn't: post twice, and you have two notes. Clients, proxies and browsers rely on this when they decide what's safe to retry.

    REST comes from Roy Fielding's doctoral dissertation, finished at UC Irvine in 2000. Fielding was one of the authors of the HTTP/1.1 specification and a co-founder of the Apache project, and the dissertation described the style the web had been built in. Most APIs that call themselves RESTful today follow only part of it, and that's mostly fine. How It Works

    The whole API for notes, in five lines:

  • GET /notes: 200, and the list.
  • POST /notes, with JSON: 201, the new note, and Location: /notes/3.
  • GET /notes/3: 200 and the note, or 404.
  • PUT /notes/3, with JSON: 200 and the replaced note.
  • DELETE /notes/3: 204, and no body.

    • Anything else gets an honest refusal: 405 with an Allow header for a method the URL doesn't take, 415 for a body that isn't JSON, 400 for JSON that won't parse, 422 for JSON that parses but makes no sense.

    The same curl flags as before: -X picks the method, -H adds a header, -d sends the body, and -i shows the response's headers.

    200, 201 with a Location, 200, 200, 204, and finally 404: the note is gone. Send a PUT twice, and the second one changes nothing. Send the POST twice, and you get two new notes. Then send what a careless or hostile client might:

    curl -i -d 'body=Buy beans' http://localhost:8000/notes curl -i -H 'Content-Type: application/json' -d '{nope' http://localhost:8000/notes curl -i -H 'Content-Type: application/json' -d '{"body":["x"]}' http://localhost:8000/notes curl -i -X PATCH http://localhost:8000/notes/1

    415, 400, 422, and 405 with Allow: GET, PUT, DELETE. Each says exactly what was wrong, so the developer on the other end can fix their code without asking you.     In PHP
  • file_get_contents('php://input') reads the raw request body. $_POST is only filled in for form posts, never for JSON.
  • json_decode($raw, true, 8, JSON_THROW_ON_ERROR): arrays instead of objects, a depth limit, and an exception for bad JSON instead of a quiet null.
  • json_encode($data, JSON_UNESCAPED_UNICODE | JSON_THROW_ON_ERROR) sends "café" as UTF-8 rather than café. Both are valid JSON; one is readable. See Text and UTF-8.
  • $_SERVER['CONTENT_TYPE'] says what the client claims it sent. It's a claim, so check the body too.
  • Content-Type: application/json; charset=utf-8 on every JSON response.
    • Gotchas
  • 200 with {"error": ...} isn't REST. It's the most common way APIs break the rules, and it makes every client read every body to find out whether it worked.
  • PUT replaces; PATCH changes part. A PUT without a field means "this field is now empty." If you want "change only what I sent," that's PATCH, and it's a separate route to write.
  • This API has no login. Anyone can delete anything. A real one checks a token on every request, and answers 404 for notes that aren't yours. The REST API project builds that.
  • Version it from the start. Once a phone app in the wild depends on /notes, you can't change what it returns. Many APIs put the version in the path, /v1/notes, so a /v2 can live beside it.

    • Next to the API, keep a plain text file with one curl -i for every route, good and bad. It's documentation, a test you can run by pasting, and the first thing you'll want when someone says "the API is broken."
