Singletons Phillip Harrington

Some things an app should have only one of: one database connection, one mailer, one set of settings. The middleware app made one of each in index.php and handed them out. The singleton is the other way to do it, and you'll find it in a lot of PHP code. It's worth knowing exactly how it works, and exactly why I don't use it.

What's a Singleton?

A class that makes sure there's only ever one of itself. Three parts:

  • A private constructor, so new Mailer() fails anywhere outside the class.
  • A static property that holds the one instance, once it exists.
  • A static method, usually getInstance(), that makes the instance the first time it's called and returns the same one every time after.

    • Any code, anywhere, can write Mailer::getInstance() and get it. That's the appeal, and it's the problem.

    What It Costs
  • Hidden dependencies. A class that calls Mailer::getInstance() inside a method needs a mailer, and nothing about its constructor says so. You find out by reading every line.
  • State that outlives you. The instance lives as long as the process. Whatever one piece of code left in it, the next piece finds, including the next test.
  • No swapping. The class names its own mailer. A test can't hand it a fake one, and a different part of the app can't hand it a different one.

    • It's a global variable with a class around it. That's why I inject dependencies instead, and keep statics out of my classes.

    The singleton is one of the 23 patterns in Design Patterns, the 1994 book by Erich Gamma, Richard Helm, Ralph Johnson and John Vlissides, known as the Gang of Four. In a 2009 interview about which patterns they'd change, Gamma said he was in favor of dropping Singleton, because using it is almost always a sign of a design problem. How It Works
    1. Code calls Mailer::getInstance().
    2. The static property is empty, so the method makes a Mailer with the private constructor, stores it, and returns it.
    3. Every later call finds it stored and returns the same object.
    4. It stays until the PHP process ends: the end of the request on a web server, or the end of the script on the command line.

    The alternative needs no pattern at all. Make one mailer in the place that builds the app, and pass it to each class that needs it, through the constructor. There's still only one. It's just not reachable from everywhere.

    In PHP
  • private function __construct(), private static ?self $instance, and return self::$instance ??= new self();: the whole pattern in three lines.
  • A thorough singleton also makes __clone() private, and throws in __wakeup(), so nobody gets a second copy by cloning or unserializing.
  • Every PHP request starts with nothing. A singleton on a web server lives for one request, not for the life of the server, which surprises people coming from other languages.
  • The alternative is Dependency Injection: constructor parameters, and one place that builds everything. A container can do the building for you once the app is big.
    • Gotchas
  • Tests that pass alone and fail together. That's the Try It, and it's the classic sign of a singleton or other static state somewhere underneath.
  • Static methods are the same problem, smaller. A class full of Thing::doIt() calls has the same hidden dependencies, even with no instance. See Constants, Static Variables and Functions.
  • "Only one" is the app's decision, not the class's. Today there's one database. Next year there's a primary and a replica, and a class that insisted on one instance has to be rewritten.
  • You'll still meet them. Older code, and some libraries, use singletons. Wrap one behind an interface and inject the wrapper, and the rest of your code never has to know.

    • In a codebase you've just inherited, search for ::getInstance( and static $. Every hit is a dependency some class is hiding. Make a list; it's the list of things that will surprise you, and the order to pull them out into constructors.
