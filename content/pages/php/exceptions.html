Exceptions and Try/Catch Phillip Harrington

Some failures can't be handled where they happen. A function that splits a bill can tell that "zero people" is nonsense, but it has no idea whether it's running in a web page, a command, or a test, so it can't decide what to show anyone. It needs a way to stop and hand the problem to whoever called it. That's an exception. Errors and the Error Log introduced them; this lesson is what to do with one.

What's an Exception?

An object that describes what went wrong: a message, the file and line it came from, and the stack trace, the list of function calls that led there. You make one with new, like any object, and throw it.

Try and Catch

try marks a block of code. catch says which kinds of exception you're ready to handle if that block throws one. finally, if you add it, runs either way, for cleanup like closing a file.

The Family Tree

Everything you can throw implements Throwable, in two branches:

  • Exception: things that can go wrong in a working program. A file that isn't there, bad input, a database that's down. Its children include RuntimeException, InvalidArgumentException and JsonException.
  • Error: mistakes in the code itself, thrown by PHP. Calling a function that doesn't exist, a class that isn't found, a TypeError from strict types, DivisionByZeroError.

    • Catching a class catches its children too, so catch (RuntimeException $e) also catches your own BadRequest if it extends RuntimeException.

    How It Works
    1. Code runs throw new BadRequest('...'). It stops on that line.
    2. PHP looks for the nearest try around it, in this function, then in the function that called this one, and so on up.
    3. At each try, it checks the catch blocks in order. The first one that matches the exception's class runs, and the program carries on after it.
    4. Any finally blocks on the way run as it passes.
    5. If nothing catches it, the exception handler runs, if you set one. Then the script ends. On a web page, that's a 500.

    So catch an exception where you can actually do something about it, and let the rest go up. A web app usually has very few catch blocks: one around anything that's the visitor's fault, which becomes a 400 with a helpful message, and one handler at the top for everything else, which becomes a 500 with an unhelpful one.

    In PHP
  • throw new InvalidArgumentException('...'); throws one. throw works as an expression too: $x ?? throw new ....
  • try { ... } catch (BadRequest $e) { ... } finally { ... }; and catch (A | B $e) catches either.
  • $e->getMessage(), getFile(), getLine(), getTraceAsString(), and (string) $e for all of it at once.
  • class BadRequest extends RuntimeException {} makes your own kind, so you can catch exactly that.
  • set_exception_handler() sets the handler of last resort.
  • json_decode($json, true, 512, JSON_THROW_ON_ERROR): some functions only throw if you ask. Ask.
    • Gotchas
  • An empty catch hides the problem. catch (Exception $e) {} makes the error go away and the bug stay. If you catch it, handle it, or at least log it.
  • catch (Exception $e) doesn't catch an Error. A TypeError sails right past it. The top-level handler takes a Throwable for that reason.
  • The details are for you, not the visitor. A stack trace shows file paths, function names, sometimes the values passed in. With display_errors on and no handler, PHP prints all of it on the page. Log it, and show a plain message.
  • Not every failure throws. Plenty of PHP's older functions return false and raise a warning instead: file_get_contents(), fopen(). Check what they return.
  • Exceptions aren't for the normal path. "No results" is an answer, not a failure. Return an empty array. Throw when the function truly can't do its job.
    • Exceptions aren't the only way. Go, released by Google in 2009, has none for ordinary failures: a function that can fail returns its result and an error side by side, and the caller checks the error right there. Rust does something similar with a Result type. Both choices were on purpose: a failure you can see in the code is harder to forget about than one that might fly past from somewhere below.

    When you catch one exception and throw your own, pass the first one along as the third argument: throw new ReportFailed('Sales report failed.', 0, $e);. The new message says what your code was trying to do, and (string) $e in the log still shows the original, underneath it.
