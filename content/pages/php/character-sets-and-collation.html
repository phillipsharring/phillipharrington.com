Character Sets and Collation Phillip Harrington

At the end of Indexes, an email address in capitals found the same customer as one in lowercase. The database decided those were equal, and it could have decided otherwise. Text in a database comes with two settings: how its characters are stored as bytes, and how they're compared. Get the first wrong and names come back mangled. Get the second wrong and "Cafe" and "café" are the same username.

What's a Character Set?

The rule for turning characters into bytes and back. Text and UTF-8 has the full story; the short version is that UTF-8 can store every character there is, using one to four bytes each, and it's the only one you should use. In MySQL, that's called utf8mb4.

MySQL's utf8 Isn't

MySQL also has a character set called utf8, and it isn't UTF-8. It stores at most three bytes per character, which covers most of the world's writing, and not emoji, some rarer Chinese characters, or anything else that takes four. Its real name is utf8mb3, and utf8 is an old alias for it. Try to store an emoji in it, and in strict mode it's refused; with strict mode off, the emoji is quietly stored as a question mark. utf8mb4, "up to four bytes," is the real thing. MySQL 8 uses it by default, but older tables, and older tutorials, still say utf8.

What's a Collation?

The rules for comparing and sorting text: whether a equals A, whether e equals é, and which comes first. Every character set has several. Their names say what they do:

  • utf8mb4_0900_ai_ci, MySQL 8's default: Unicode's rules (version 9.0.0), accent insensitive, case insensitive. cafe, Cafe and café are all equal.
  • utf8mb4_0900_as_cs: accent sensitive, case sensitive. All three are different.
  • utf8mb4_bin: compares the bytes. Exact, and it sorts by byte value, so every capital comes before every lowercase letter, and accented letters come after z.

    • The default is right for most text people search for, like names and email addresses: "alice@example.com" should find "Alice@Example.com". Pick a different one, column by column, when equal has to mean identical.

    Unicode began, in 1991, as a 16-bit code: room for 65,536 characters, which was meant to be enough for every script in use. Characters that fit in 16 bits take at most three bytes in UTF-8. Unicode outgrew 16 bits in 1996, but when MySQL added its utf8, in version 4.1, it stopped at three. Real four-byte UTF-8 arrived as utf8mb4 in MySQL 5.5.3, in 2010, the same year emoji joined Unicode. It became the default in MySQL 8.0. How It Works

    Text passes through three character sets on its way into a table:

    1. The connection's. When PHP connects, it tells MySQL which character set its bytes are in: charset=utf8mb4 in the connection string.
    2. The column's. MySQL converts the text from the connection's character set to the column's, if they differ. A character the column's can't hold is refused.
    3. Back out. On the way out, MySQL converts from the column's character set to the connection's again.

    The conversions are only right if each side tells the truth. If PHP sends UTF-8 but says it's latin1, MySQL "converts" bytes that were already right, and stores something else. Every comparison, WHERE, ORDER BY, UNIQUE or join, uses the column's collation.

    Now lie about the connection. wrong-charset.php saves "café" over a connection that says latin1, then reads it back both ways:

    docker compose run --rm php php wrong-charset.php

    Read back through the same wrong connection, it says café, and looks fine. Read through a correct one, it says cafÃ©. The bytes on disk are C383C2A9 where é should be C3A9: MySQL converted the UTF-8 bytes as if they were latin1 characters, and stored those. Mangled text like this has a name, mojibake, and it's very hard to undo once a table is full of it.

    Then open the mysql command, and compare:

    docker compose exec db mysql -u app -papp-password course SELECT 'cafe' = 'café', 'Cafe' = 'cafe'; SELECT 'cafe' = 'café' COLLATE utf8mb4_0900_as_cs;

    Equal, equal, and then not equal, once the collation cares about accents. Sort the words, the default way and then by bytes:

    SELECT `word` FROM `words` ORDER BY `word`; SELECT `word` FROM `words` ORDER BY `word` COLLATE utf8mb4_bin;

    The default puts them where a person would: apple, éclair, Émile, zebra, Zoë. By bytes, it's Zoë, apple, zebra, Émile, éclair. Last, sign up two users:

    INSERT INTO `users` (`username`) VALUES ('Cafe'); INSERT INTO `users` (`username`) VALUES ('café');

    The second is refused as a Duplicate entry. To this collation, they're the same name, which is usually what you want for usernames: nobody gets to pretend to be someone by adding an accent. docker compose down -v when you're done.

    In PHP
  • charset=utf8mb4 in the PDO connection string, always. It's the one setting that makes everything else work.
  • mb_check_encoding($text, 'UTF-8') before saving text that came from outside. Never trust input, including its bytes: a form, a file or an API can send something that isn't UTF-8 at all.
  • mb_strlen() to check a length against a VARCHAR, which counts characters. strlen('café') is 5, and MySQL's CHAR_LENGTH('café') is 4.
  • <meta charset="utf-8"> on every page, so the browser sends forms back in UTF-8 too. The database is only one of the boundaries.
    • Gotchas
  • Wrong both ways looks right. Text saved and read through the same wrong connection comes back looking fine, for years, until something else (a report, a new app, a correct connection) reads the table and finds mojibake. If you take over an old app, check with HEX() what's really stored.
  • Old collations think all emoji are the same. utf8mb4_general_ci and utf8mb4_unicode_ci, common on older tables, give every emoji the same weight, so '🐘' = '🐬' is true, and a unique column can only hold one of them. The 0900 collations tell them apart.
  • The table's setting isn't the column's. A table's DEFAULT CHARSET only applies to columns made after it's set. Changing it later leaves the existing columns as they were. SHOW CREATE TABLE shows each column's real character set when it differs from the table's.
  • Comparing across collations can fail. Join two columns with different collations, and MySQL may refuse with Illegal mix of collations. Pick one collation for the whole database and stick to it.

    • When text looks wrong, don't trust what the screen shows: every layer between the table and your eyes can convert it again. SELECT HEX(`body`) shows the bytes that are actually stored. C3A9 is a correct é. C383C2A9 is one that was converted twice, and now you know where to look.
