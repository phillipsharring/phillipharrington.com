Working with Files Phillip Harrington

Includes read a PHP file and ran it. Most files aren't code: logs, exports, settings, uploads, a cache. PHP reads and writes them with a few functions, and the functions are the easy part. The hard parts are where the file lives, who else can read it, and what happens when a visitor gets to choose its name.

What's a File, to PHP?

A named row of bytes on disk, at a path. PHP reads them into strings and writes strings out to them. It doesn't care whether the bytes are text, JSON or a photo. If they're text, they should be UTF-8, like everything else (Text and UTF-8).

Whole Files at Once
  • file_get_contents($path): the whole file, as one string.
  • file_put_contents($path, $data): write a string to a file, replacing what was there. Add FILE_APPEND to add to the end instead, and LOCK_EX so two requests writing at once don't mix their lines.
  • file($path): the whole file, as an array of lines.
    •

    Each returns false when it fails, with a warning. Check for it.

    A Line at a Time

    For a file too big to hold in memory, open it and read it a piece at a time: fopen() gives you a handle, fgets() reads the next line from it, and fclose() closes it. A 2 GB log read this way uses about as much memory as its longest line.

    Permissions

    Every file has an owner, and settings for who can read and write it. PHP runs as some user, often one called www-data on a server, and can only touch what that user is allowed to. "Permission denied" means the file is there and PHP's user can't have it.

    One of my apps had a deploy script that wrote a copy of the production .env to /tmp while it worked, and left it there. On that machine, /tmp could be read by every user, so every secret the app had was sitting in a file anyone logged in could open. The fix was a private temp file, readable only by the script's own user, and deleted when the script ended, however it ended. How It Works
    1. You build a path, from __DIR__, to a folder outside the web root that's meant for the app's data.
    2. If any part of the path came from outside, you check that it still points inside that folder.
    3. PHP asks the operating system for the file, as PHP's user.
    4. The operating system checks the permissions, and hands it over or refuses.
    5. PHP reads or writes, then closes the file. With LOCK_EX, other writers wait their turn.

    Step two is the one that matters. A file name from a form, a query string or a command line is input, and ../ climbs out of any folder you put in front of it. It's an ancient proverb: never trust input, least of all in a path.

    Try It

    A notes file you add to and read back. In a folder, make notes.php:

    docker run --rm -v "$PWD":/app -w /app php:8.4-cli php notes.php add "Buy milk" docker run --rm -v "$PWD":/app -w /app php:8.4-cli php notes.php add "Call the café about the order" docker run --rm -v "$PWD":/app -w /app php:8.4-cli php notes.php list

    New here:

    The first argument to the script: what to do. The second. The quotes make the two words one argument; without them, Buy and milk would arrive separately.

    There's a data/notes.txt in your folder now, one note per line. Try adding a note that's only spaces, and it's refused. Each note is checked before it's written, and any new line inside it becomes a space, so nobody can sneak in a second line.

    Now read a file line by line. Make search.php:

    docker run --rm -v "$PWD":/app -w /app php:8.4-cli php search.php notes.txt milk docker run --rm -v "$PWD":/app -w /app php:8.4-cli php search.php ../notes.php php docker run --rm -v "$PWD":/app -w /app php:8.4-cli php search.php /etc/passwd root

    The first finds the milk. The other two try to climb out of data/, and are refused. realpath() works out where a path really points, every ../ followed, and the script only goes on if that's still inside data/. Without that check, the second would print your source code and the third the server's list of users.

    In PHP
  • file_get_contents(), file_put_contents(), file(): whole files.
  • fopen(), fgets(), fwrite(), fclose(): a piece at a time.
  • FILE_APPEND | LOCK_EX: add to a file safely.
  • is_file(), is_dir(), file_exists(), is_readable(), is_writable(): ask before you act.
  • mkdir(), rename(), unlink() (delete), scandir(), glob().
  • realpath() and str_starts_with(): is this path really inside that folder? basename() strips a name down to its last part.
  • tmpfile() and tempnam(): temp files with names nobody else picked.
  • fgetcsv() and fputcsv(): spreadsheets, in CSV.
    • Gotchas
  • A file name from input can go anywhere. 'data/' . $_GET['file'] with ../../.env is your secrets. Use an allow list, or realpath() and check the folder, as search.php does.
  • A file name from input can be a URL. file_get_contents() opens http:// addresses too, and special ones like php://. Code that reads "a file" a visitor named can be made to fetch things from your own network.
  • Don't write into the web root. Anything PHP writes inside public/ can be downloaded, or run, if it ends in .php. Keep data, logs and uploads outside it, like Document Root said.
  • Never fix "Permission denied" with chmod 777. It means every user on the machine can read and change the file. Give PHP's user what it needs, and nobody else.
  • A half-written file is a broken file. If two requests replace the same file at once, or the script dies mid-write, readers get a mess. Lock it, or use the tip below.
  • Windows line endings. A file made on Windows ends its lines with \r\n, and the \r stays on the end of every line you read. rtrim($line, "\r\n") takes off both.

    • To replace a file safely, write the new version to a temp file in the same folder, then rename() it over the old one. On the same disk, the rename happens all at once: anyone reading the file gets the old version or the new one, never half of each. If the script dies partway, the old file is still there, untouched.
