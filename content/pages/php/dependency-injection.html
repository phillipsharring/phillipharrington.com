Dependency Injection Phillip Harrington

In Constants, Static Variables and Functions, a greeting that reached out for the clock could only ever tell you the time right now, and the same greeting, handed the hour, could tell you any time you liked. That's the whole idea, and it has a long name: dependency injection. Give an object what it needs, instead of letting it go and get it.

What's a Dependency?

Anything a class needs from outside itself to do its job. A class that sends a welcome email depends on something that sends email. A class that saves orders depends on a database connection.

What's Injection?

Handing the dependency in, rather than having the class make it or look it up. The usual way is the constructor: the class lists what it needs as parameters, and whoever makes the object passes them in. That's constructor injection, and it's the only kind this course uses.

Here's the version without it. The class makes its own mailer, so it can only ever use that one, with those settings:

final class Welcome { public function send(string $email, string $name): void { $mailer = new SmtpMailer('smtp.example.com', 587); $mailer->send($email, 'Welcome to Example', "Hi {$name}..."); } }

To try this class out, you need a mail server. To change the server, you edit this class, and every other class that made one the same way. A static Mail::send() has the same problem, as Constants and Statics showed.

The Interface Is the Type

Ask for an interface, not a class: Mailer $mailer, not SmtpMailer $mailer. Then the class works with any mailer: the real one in production, one that prints to the screen while you build, one that just keeps a list in a test.

What's a Container?

With a few classes, wiring them by hand is a few lines of new. With a hundred, each needing others, it's a chore. A container does it for you. Ask it for a Welcome, and it reads the constructor, sees a Mailer, makes one, and passes it in, all the way down. That reading is called autowiring. You only tell it what it can't work out, like which class to use for an interface.

How It Works

With a container, a request goes like this:

  1. At the very start, in one place, you build the container and tell it your definitions: "a Mailer is a ScreenMailer."
  2. You ask it for the one object you need first, like a page's controller.
  3. It reads that class's constructor, and for each parameter, gets one of those: from your definitions, or by reading that class's constructor in turn.
  4. It makes every object in order and hands you the finished one.
  5. From there, nothing calls the container again. Each object just uses what it was given.

Step five is the rule that matters. The container is only ever touched at the top. If classes ask it for things themselves, the dependencies are hidden again.

Katherine's email. Nobody wrote new Welcome or new ScreenMailer: the container read the constructor and worked it out. Change the one definition line to a real mailer, and every class that needs a Mailer gets the real one.

In PHP
  • public function __construct(private Mailer $mailer) {}: constructor promotion, from Modern PHP, makes injection one line per dependency.
  • Type the parameter as an interface. Make the property private, and readonly if you like.
  • What the class needs to exist goes in the constructor. What changes on every call, like the email address, goes in the method's arguments.
  • new DI\ContainerBuilder(), addDefinitions(), build(), then $container->get(Welcome::class), once, at the top. Other containers work the same way: Symfony's and Laravel's are both built on this idea.
  • DI\autowire(ScreenMailer::class) says "use this class, and autowire its own constructor."
    • Gotchas
  • Passing the container around isn't injection. A class that takes the container and calls get() inside is looking things up, just with extra steps. That's called a service locator, and it hides the dependencies the same way a static call does.
  • A long constructor is a message. A class that needs eight things is probably doing three jobs. Split it.
  • Autowiring can't guess an interface. Ask for a Mailer without a definition, and the container stops: it can't make an interface. Each interface needs one line saying which class.
  • Settings aren't classes. A mail server's host name or a database password can't be autowired. Define them in the container from your configuration, and keep the secrets out of the code.
    • The name comes from a 2004 article by Martin Fowler, "Inversion of Control Containers and the Dependency Injection pattern." The older name for the idea, inversion of control, had been around for years, along with its nickname: the Hollywood Principle, "Don't call us, we'll call you." Fowler thought "inversion of control" was too broad to say what these containers actually did, and picked a name that did.

    Put every container definition in one file, and every new for a service in there too. When you want to know what a Mailer really is in production, there's one place to look, and when you want to swap it, one line to change.
