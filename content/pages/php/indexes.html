Indexes Phillip Harrington

Every table so far has had a handful of rows, and every query has been instant. Real tables grow. A login form that looks up an email address among a million customers will, unless you've told the database otherwise, read all million to find one. It works on your laptop, with ten rows, and falls over in production, a year in. The fix is usually one line.

What's an Index?

A sorted copy of one or more columns, with a pointer from each value back to its row. It works like the index at the back of a book: to find "foreign keys," you don't read every page, you look it up under F and turn to the page it gives you. Without an index, the database reads every row and checks each one. That's called a full table scan.

The primary key is always indexed. Foreign keys get one too, in MySQL. Anything else you search by, sort by, or join on needs one of its own.

CREATE INDEX `customers_city_index` ON `customers` (`city`); Unique Indexes

An index that also refuses duplicates. An email address that has to belong to one customer gets a UNIQUE index, and then it's fast to look up and impossible to sign up with twice, even if two signups arrive in the same instant.

Indexes on More Than One Column

An index can cover several columns, sorted by the first, then the second, like a phone book sorted by last name, then first name. An index on (`city`, `created_at`) helps a search by city, and by city and date together. It doesn't help a search by date alone, any more than a phone book helps you find everyone named Maria. The database can use the columns from the left, and stops at the first one your query skips.

The kind of index MySQL uses is a B-tree, a structure Rudolf Bayer and Edward McCreight described in 1970, while working at Boeing's research labs. It keeps values sorted in a shallow tree, so finding one among millions takes a few steps. Neither of them ever settled what the B stands for. Boeing, balanced and Bayer have all been suggested. How It Works
  1. A query arrives: WHERE `email` = 'user123456@example.com'.
  2. The database looks at the indexes on the table, and its statistics about them, and plans the cheapest way to find the rows.
  3. With an index on email, it walks the tree straight to that value and reads one row. Without one, it reads them all.
  4. On every insert, update and delete, it updates the indexes too, so they always match the table.

Step four is the cost. Every index makes writes a little slower and takes space on disk. That's almost always worth it for a column you search by, and never worth it for one you don't.

Try It

Two hundred thousand customers, and no index on their email addresses. The same compose.yml, Dockerfile and db.php as in SQL, and an init.sql that makes up the customers:

Then find.php, which looks one up by email and times the query:

Start the database, and find someone:

docker compose up -d --wait db docker compose run --rm php php find.php user123456@example.com

Found, in some tens of milliseconds, depending on your computer. That sounds fine until you multiply it by every login, on every server. Ask the database how it found her. Open the mysql command and put EXPLAIN in front of the query:

docker compose exec db mysql -u app -papp-password course EXPLAIN SELECT `id`, `name` FROM `customers` WHERE `email` = 'user123456@example.com';

Two columns matter. type is ALL: a full table scan. rows is about 200,000: how many it expects to read, to find one. Now add the index. Email addresses here have to be unique, so make it a unique one:

CREATE UNIQUE INDEX `customers_email_unique` ON `customers` (`email`);

Run the same EXPLAIN. Now type is const, key names your index, and rows is 1. Type exit, and run find.php again: a fraction of a millisecond. Same query, same data, a hundred times faster or more, and the gap grows with the table.

Back in mysql, two ways to throw the index away again without dropping it. EXPLAIN each:

EXPLAIN SELECT `id`, `name` FROM `customers` WHERE LOWER(`email`) = 'user123456@example.com'; EXPLAIN SELECT `id`, `name` FROM `customers` WHERE `email` LIKE '%123456@example.com';

Both are back to ALL. The index is sorted by email, not by LOWER(`email`), and a search that starts with a wildcard has nowhere in the sorted list to start. docker compose down -v when you're done.

In PHP
  • Indexes live in the database, not in PHP. Your code doesn't change; the query just gets faster.
  • hrtime(true) gives a time in nanoseconds, for measuring how long something took. Measure before and after, not by feel.
  • A unique index turns a duplicate into a PDOException with MySQL error 1062, which is the reliable way to catch "that email is taken": checking first and then inserting leaves a gap for a second signup to slip through.
  • filter_var($email, FILTER_VALIDATE_EMAIL) before the lookup. Never trust input, even when the only thing it can do is ask.
    • Gotchas
  • Wrapping a column in a function hides it from its index. LOWER(`email`), YEAR(`created_at`), DATE(...): each one makes the database work out the value for every row. Compare the bare column instead: `created_at` >= '2026-01-01'. For case, you usually don't need LOWER() at all. Character Sets and Collation explains why.
  • A leading wildcard can't use an index. LIKE 'user12%' can; LIKE '%12' can't. Searching inside text takes a different tool, like MySQL's full-text indexes.
  • Small tables lie. With a hundred rows, a full scan is instant, and you won't notice the missing index until there's real data. Test with a realistic number of rows, the way init.sql does.
  • Indexes aren't free. Each one slows every write a little. Index what you search, sort and join on, and leave the rest alone.

    • MySQL can log every query that takes longer than a limit you set: turn on slow_query_log, and set long_query_time to, say, half a second. Then read the log once a week, and EXPLAIN whatever shows up. The database already knows which of your queries are slow. All you have to do is ask.
