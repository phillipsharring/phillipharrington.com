Forms Phillip Harrington

Query strings send data you type into the address bar. Forms send data people type into a page: a search box, a signup, a comment, a checkout. A form is plain HTML. The browser already knows how to show it, check it, and send it, with no JavaScript at all. Your job is the other end: reading what arrives, and deciding whether to believe it.

This lesson has no jokes. Forms are no laughing matter.

What's a Form? <form action="/order" method="post"> <label>Name <input name="name" required></label> <button type="submit">Order</button> </form>
  • action: where to send it. Leave it off, and the form sends to the page it's on.
  • method: get puts the fields in a query string; post puts them in the request body. The default is get.
  • name, on each field: the name its value is sent under. A field without a name isn't sent at all.
  • label: the field's visible name. Clicking it puts you in the field, and screen readers read it aloud.
  • button, with type="submit": sends the form. A button with no type inside a form submits it anyway, but it's clearer to say so, and type="button" is how you make one that doesn't.

    • get and post are HTTP methods, the same ones from Request and Response, and they're the only two a form can use on its own. Each field's name is the name in its name=value pair, which is why a field without one goes nowhere. And give every field a label, either wrapped around it, as here, or pointing at it with for= and the field's id. Then clicking the words works like clicking the field, which matters most for a checkbox, whose own target is tiny.

    Fields

    input does most of the work, changing with its type. The ones you'll use most:

    type= For
    text a line of text
    email an email address; the browser checks for an @, and phones show an @ key
    number a number, with up and down arrows
    password text that shows as dots while you type
    checkbox on or off; sent only when checked
    radio one choice from a group that shares a name
    date a date, with a calendar to pick from
    hidden sent, never shown, and still input

    Then select for a list to pick from, and textarea for writing more than a line.

    The browser can check some things before it sends: required, type="email", min and max, maxlength. Use them. They save people a round trip to the server just to find out they missed something. But they're a courtesy to honest visitors, not a defense, as Try It will show.

    In 1995, Rasmus Lerdorf released a set of tools he'd written for his own home page and called it PHP/FI: Personal Home Page / Forms Interpreter. Reading what people typed into forms was half the original point. The language grew from there, and the name got reinterpreted as "PHP: Hypertext Preprocessor." How It Works
    1. Someone fills in the form and presses the button.
    2. The browser runs its checks. If any fail, it says so and sends nothing.
    3. It collects every named field as name=value. A checkbox is sent only if it's checked, and a disabled field isn't sent at all.
    4. If the form's method is get, those pairs become the query string. If it's post, they go in the body, labeled application/x-www-form-urlencoded (or multipart/form-data, when the form uploads a file).
    5. PHP puts them in $_GET or $_POST.

    Use get for forms that look something up, like a search, so the result has a URL you can share. Use post for forms that change something: signups, comments, orders.

    Then the part that matters most. Never trust input. Step two only happens in a browser that behaves. Anyone can delete required in their developer tools, send whatever they like with curl, or post to your form from a page of their own (which is how CSRF works, in Security). Every check that matters must be run again on the server.

    Try It

    A shirt order that checks everything twice: once in the browser, for courtesy, and once on the server, for real. In a folder, make index.php.

    This is the biggest example yet, about forty lines, and that's fine. Half of it is HTML you already know. The PHP at the top does three things: reads the fields, checks them, and decides what to say. The HTML at the bottom shows the answer and the form. Read it top to bottom once, then we'll poke at it.

    Start it the usual way:

    docker run --rm -it -p 8000:8000 -v "$PWD":/app -w /app php:8.4-cli php -S 0.0.0.0:8000

    Open http://localhost:8000 and press Order with nothing filled in: the browser stops you. That's required.

    Fill it in properly, and it thanks you.

    Now go around the browser, the way a script would, with a size that isn't on the list:

    curl -d 'name=&size=huge' http://localhost:8000

    The browser's checks never ran, and the server caught both problems anyway. One more: send a name with HTML in it.

    curl --data-urlencode 'name=<b>hi</b>' -d 'size=large' http://localhost:8000 Only the new part: Like -d, but curl encodes the value for you first, so characters like < and & arrive as text instead of breaking the form data.

    Look at the HTML that comes back: &lt;b&gt;hi&lt;/b&gt;. htmlspecialchars() turned the tags into harmless text, in the message and in the box. Every time you put user input back into a page, escape it like that. The XSS lesson, in Security, is why.

    In PHP
  • $_POST holds the fields of a post form, decoded. Every value is input: check its type, trim it, and test it against what you'll accept.
  • $_SERVER['REQUEST_METHOD'] === 'POST' tells "showing the form" apart from "it was submitted."
  • isset($_POST['wrap']) is how you read a checkbox: checked means present, unchecked means missing.
  • in_array($value, $allowed, true) keeps a select honest: the value has to be one of yours.
  • htmlspecialchars() on anything you echo back into the page.
    •  Gotchas
  • An unchecked checkbox sends nothing. Not "off," not empty: nothing. Test whether it's there.
  • A select isn't an allow list. The browser only offers your options, but anyone can send any value. Check it against the list on the server.
  • Reloading resubmits a POST. Submit the shirt order, then reload, and the browser asks whether to send it again. Real forms answer a successful POST with a redirect: Post/Redirect/Get, from Request and Response. The example skips it to stay short.
  • Disabled and read-only fields can both be changed. A disabled field isn't sent, and a readonly one is. Either way, anyone can edit them in their developer tools, or send a value of their own, so never trust input.
    • JavaScript Makes It Weird

    Everything above is an HTML form on its own. Add JavaScript and the rules loosen. A script can read a field that has no name, by its id or any other way it can find it, and send it anyway. It can send PUT, PATCH or DELETE, which a plain form can't. It can submit without anyone pressing the button, or send JSON instead of name=value pairs. None of it changes the server's side: whatever arrives, however it got there, is still input.

    PHP at the Top, Form at the Bottom

    This example uses the most common shape there is for a PHP form, and you'll write it a hundred times. One file does both jobs. The PHP at the top asks whether this request is a POST ($posted), and only then reads the fields, checks them, and decides what to say. The HTML at the bottom shows any message, then the form, which posts back to the same file.

    The key: every variable gets a value before the HTML starts, either what came in or a default, like an empty string. So the HTML never has to ask whether anything exists. It just prints $name, with no isset() in sight, and the form shows up empty the first time and filled in after. It's a common pattern, not the only one: frameworks and bigger apps split these jobs across files, and you'll meet some of those ways later.

    type="email" gives phones a keyboard with an @ on it. type="tel" brings up a number pad, and inputmode="numeric" does the same for PINs and quantities. One attribute, and every phone user types less and gets it wrong less.
