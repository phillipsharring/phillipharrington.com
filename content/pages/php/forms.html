Forms Phillip Harrington

Query strings send data you type into the address bar. Forms send data people type into a page: a search box, a signup, a comment, a checkout. A form is plain HTML. The browser already knows how to show it, check it, and send it, with no JavaScript at all. Your job is the other end: reading what arrives, and deciding whether to believe it.

What's a Form? <form action="/order" method="post"> <label>Name <input name="name" required></label> <button type="submit">Order</button> </form>
  • action: where to send it. Leave it off, and it goes back to the page it's on.
  • method: get puts the fields in a query string; post puts them in the request body. The default is get.
  • name, on each field: the name it's sent under. A field without a name isn't sent at all.
  • label: the field's visible name. Clicking it puts you in the field, and screen readers read it aloud.
  • button, with type="submit": sends the form. A button with no type inside a form submits it anyway, but say so. It's clearer, and type="button" is how you make one that doesn't.
    • Fields

    input does most of the work, changing with its type: text, email, number, password, checkbox, radio, date, hidden and more. Then select for a list to pick from, and textarea for writing more than a line.

    The browser can check some things before it sends: required, type="email", min and max, maxlength. Use them. They save people a round trip. But they're a courtesy to honest visitors, not a defense, as Try It will show.

    In 1995, Rasmus Lerdorf released a set of tools he'd written for his own home page and called it PHP/FI: Personal Home Page / Forms Interpreter. Reading what people typed into forms was half the original point. The language grew from there, and the name got reinterpreted as "PHP: Hypertext Preprocessor." How It Works
    1. Someone fills in the form and presses the button.
    2. The browser runs its checks. If any fail, it says so and sends nothing.
    3. It collects every named field as name=value. A checkbox is sent only if it's checked, and a disabled field isn't sent at all.
    4. For get, those pairs become the query string. For post, they go in the body, labeled application/x-www-form-urlencoded (or multipart/form-data, when the form uploads a file).
    5. PHP puts them in $_GET or $_POST.

    Use get for forms that look something up, like a search, so the result has a URL you can share. Use post for forms that change something: signups, comments, orders.

    Then the part that matters most. Never trust input. Step two only happens in a browser that behaves. Anyone can delete required in their developer tools, or skip the page entirely and send whatever they like with curl. Every check that matters runs again on the server.

    Try It

    A shirt order that checks everything twice: once in the browser, for courtesy, and once on the server, for real. In a folder, make index.php:

    Start it the usual way:

    docker run --rm -it -p 8000:8000 -v "$PWD":/app -w /app php:8.4-cli php -S 0.0.0.0:8000

    Open http://localhost:8000 and press Order with nothing filled in: the browser stops you. That's required. Fill it in properly, and it thanks you.

    Now go around the browser, the way a script would, with a size that isn't on the list:

    curl -d 'name=&size=huge' http://localhost:8000

    The browser's checks never ran, and the server caught both problems anyway. One more: send a name with HTML in it.

    curl --data-urlencode 'name=<b>hi</b>' -d 'size=large' http://localhost:8000 Only the new part: Like -d, but curl encodes the value for you first, so characters like < and & arrive as text instead of breaking the form data.

    Look at the HTML that comes back: &lt;b&gt;hi&lt;/b&gt;. htmlspecialchars() turned the tags into harmless text, in the message and in the box. Every time you put input back into a page, escape it like that. The XSS lesson, in Security, is why.

    In PHP
  • $_POST holds the fields of a post form, decoded. Every value is input: check its type, trim it, and test it against what you'll accept.
  • $_SERVER['REQUEST_METHOD'] === 'POST' tells "showing the form" apart from "it was submitted."
  • isset($_POST['wrap']) is how you read a checkbox: checked means present, unchecked means missing.
  • in_array($value, $allowed, true) keeps a select honest: the value has to be one of yours.
  • htmlspecialchars() on anything you echo back into the page.
    •  Gotchas
  • An unchecked checkbox sends nothing. Not "off," not empty: nothing. Test whether it's there.
  • A select isn't an allow list. The browser only offers your options, but anyone can send any value. Check it against the list on the server.
  • Reloading resubmits a POST. Submit the shirt order, then reload, and the browser asks whether to send it again. Real forms answer a successful POST with a redirect: Post/Redirect/Get, from Request and Response. The example skips it to stay short.
  • Disabled and read-only fields can both be changed. A disabled field isn't sent, and a readonly one is. Either way, anyone can edit them in their developer tools, or send a value of their own, so never trust input.

    • type="email" gives phones a keyboard with an @ on it. type="tel" brings up a number pad, and inputmode="numeric" does the same for PINs and quantities. One attribute, and every phone user types less and gets it wrong less.
