Updating Data Phillip Harrington

Selecting Data read rows and left them alone. UPDATE changes them: a new price, a new email address, one fewer in stock. It's the statement with the most famous mistake in SQL, and the mistake is a missing line. Leave off the WHERE, and it changes every row in the table, instantly, with no question asked.

What's UPDATE?

The statement that changes rows already in a table:

UPDATE `products` SET `price_cents` = 1800 WHERE `id` = 2;
  • UPDATE: which table.
  • SET: which columns get which values. Several can change at once, separated by commas.
  • WHERE: which rows. The same WHERE as in a SELECT, and the same rules. Leave it off, and the answer is "all of them."
    • Changing a Value Relative to Itself

    SET can use the row's current values: SET `stock` = `stock` - 1. The database reads and writes the row in one step, so two sales at the same moment take two off the stock, not one. Add a condition to the WHERE, like AND `stock` > 0, and the check and the change happen together too.

    The mysql command has an option, --safe-updates, that refuses any UPDATE or DELETE whose WHERE doesn't use a key, and so refuses the ones with no WHERE at all. It has had a second name for decades, and it's still in the manual: --i-am-a-dummy. How It Works
    1. The database finds the rows that match the WHERE, using an index if it can.
    2. It works out each row's new values from the SET.
    3. It checks them against the table's rules, the same ones an insert has to pass, and writes the rows whose values actually changed.
    4. It answers with two numbers: rows matched, and rows changed. PHP's rowCount() gets the second.

    So a rowCount() of 0 means one of two things: no row matched, or the row matched and already had those values. If the difference matters to you, you have to ask.

    Changed, then "nothing changed," then "no such product." The second and third both had a rowCount() of 0. Now sell.php, which takes one off the stock in a single statement:

    docker compose run --rm php php sell.php 2 docker compose run --rm php php sell.php 2

    There was one T-shirt. The first sale takes it. The second matches no row, because the stock is no longer above 0, and says sold out. No two customers can buy the last one.

    Now the famous mistake, with the safety on. Open the mysql command with --safe-updates, and forget the WHERE:

    docker compose exec db mysql --safe-updates -u app -papp-password course

    Only the new part:

    Refuse any UPDATE or DELETE that doesn't say which rows, with a key in its WHERE or a LIMIT. UPDATE `products` SET `price_cents` = 0;

    Refused: You are using safe update mode. Type exit, and open it again without the option. This time, start a transaction first, which holds the change until you say otherwise (Transactions has the details):

    docker compose exec db mysql -u app -papp-password course START TRANSACTION; UPDATE `products` SET `price_cents` = 0; SELECT `name`, `price_cents` FROM `products`;

    3 rows affected, and everything in the shop is free. That's the mistake, exactly as it happens on a live site. Undo it:

    ROLLBACK; SELECT `name`, `price_cents` FROM `products`;

    The prices are back. On a live site, without the transaction, they wouldn't be. Type exit, and docker compose down -v when you're done.

    In PHP
  • $statement->rowCount() after an UPDATE is the number of rows changed, not matched. Connect with PDO::MYSQL_ATTR_FOUND_ROWS => true if you'd rather have the number matched.
  • Put the id in the WHERE as a placeholder, like every other value, and check it first. I believe it was Hypatia who said to never trust input, and an id is input. Then check that the row belongs to whoever is asking, by adding it to the WHERE: AND `owner_id` = ?.
  • Do arithmetic in the SQL, SET `stock` = `stock` - 1, not in PHP.
    •  Gotchas
  • An UPDATE without a WHERE changes every row. No warning, no undo. In PHP it's usually a WHERE that was built in pieces and came out empty. Never let code build an UPDATE that can lose its WHERE.
  • Read, change, write loses updates. Two requests read a stock of 5, each subtracts one in PHP, and each writes 4. Two sold, one counted. Let the database do it in one statement, as sell.php does.
  • 0 rows doesn't mean not found. It can mean "already that value." Treating it as an error turns a harmless double-click into a failure page.
  • Strict mode catches some bad ids, and not others. An UPDATE ... WHERE `id` = '2abc' is refused in strict mode, but the same WHERE in a SELECT quietly finds row 2. Don't count on either. Check the id in PHP.

    • Before you run an UPDATE by hand, write it as a SELECT with the same WHERE, and run that. If it shows the three rows you meant, change SELECT ... FROM to UPDATE ... SET and leave the WHERE exactly as it is. If it shows three thousand, you've just saved your afternoon.

    Changing every row by mistake is bad. There's one statement that's worse, because the rows don't come back changed. They don't come back at all. Next: deleting data.
