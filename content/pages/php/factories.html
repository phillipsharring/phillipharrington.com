Factories Phillip Harrington

Singletons ended with one place that builds the app and hands out what it built. That place had it easy: there was one kind of mailer. Real apps pick: log the emails in development, send them in production, drop them in tests. Picking, and building what was picked, is a job, and a factory is an object that does it.

What's a Factory?

A class whose method returns a new object. The caller asks for "a Mailer" and gets one, without knowing or caring which class it is. The factory knows the classes, reads the settings, checks them, and builds the right one with the right arguments.

It works because of an interface (see Interfaces). LogMailer, SmtpMailer and NullMailer all implement Mailer, so the code that sends email only ever needs to know that one name.

The Kinds You'll Hear Of
  • A simple factory: one class with a create() method, like the one in this lesson. By far the most common.
  • Factory Method: a method a subclass overrides to decide what gets made. From the Gang of Four's book.
  • Abstract Factory: a factory for a family of related objects, like a mailer, a queue and a cache that all have to match one environment.
    • Joseph Marie Jacquard's loom, from 1804, wove patterns read from a chain of punched cards: change the cards, and the same machine made different cloth. Charles Babbage planned to feed his Analytical Engine with cards the same way. Ada Lovelace, whose notes on the Engine in 1843 included what's often called the first published program, wrote that it "weaves algebraical patterns just as the Jacquard-loom weaves flowers and leaves." How It Works
    1. The app starts, and makes the factory with the settings.
    2. It asks the factory for a Mailer.
    3. The factory reads which kind is wanted, checks that it's a kind it knows, and checks the settings that kind needs.
    4. If anything is wrong, it throws, and the app stops at startup, with a message that says what to fix.
    5. If not, it builds the mailer and returns it, and the app passes it to whatever needs one, as in Dependency Injection.

A mistake in the settings is found in the first second of a deploy, not by a customer a week later. Settings come from outside the code, and the same rule applies to them as to anything else: never trust input.

    In PHP
  • match with a default that throws: every kind listed, and anything else an error. Since PHP 8, throw works as an expression, so it fits right in the match.
  • getenv() with no argument returns every environment variable as an array, which is what the factory gets here. See Configuration and the Environment.
  • filter_var($value, FILTER_VALIDATE_INT, ['options' => [...]]) turns a setting into a real integer in range, or false.
  • The factory itself is an ordinary object, made with new and passed its settings. A test can make one with an array, and check what it builds.
    • Gotchas
  • A silent default is a bug waiting. else { use the log mailer } feels safe and is the opposite: it turns every typo into a quiet failure. List what you accept, and refuse the rest.
  • Static factory methods are everywhere. PHP's own DateTimeImmutable::createFromFormat() is one, and many libraries offer Thing::fromArray(). They're fine to call. In your own code, a factory you can inject is easier to swap and to test.
  • Not everything needs a factory. If there's one kind of thing and it's simple to make, new is the factory. Reach for one when there's a choice to make, or the building takes more than a line.
  • Never let a request pick the class. new $_GET['type']() lets a visitor build any class your app can load. The factory's list is the allow list.

    • Have the app ask its factories for everything it needs as it starts, not lazily on the first email. Then a bad setting fails the deploy, in front of the person doing it, instead of failing the first customer to sign up.
