XSS and Escaping Output Phillip Harrington

SQL Injection was input pasted into a query, where the database ran it. XSS is input pasted into a page, where the visitor's browser runs it. The attacker's code runs on your site, as your site, for whoever is looking at the page. It can read what they see, act as them, and send it all somewhere else.

What's XSS?

Cross-site scripting. Your page prints something that came from input, and that input contains HTML. The browser can't tell your HTML from theirs; it gets one page and draws all of it. If theirs has a <script> in it, the script runs, with everything your own scripts can do.

Stored and Reflected
  • Reflected: the input comes in the request and goes straight back out, like a search page that says "You searched for ...". The attacker sends the victim a link with the script in it.
  • Stored: the input is saved, a comment or a profile name, and shown to everyone who visits. The attacker posts once, and the page attacks every reader. The Guestbook project does this one.
    • What's Escaping?

    Writing a character so it means itself instead of its job. In HTML, < starts a tag; &lt; is a less-than sign that the browser shows and never runs. htmlspecialchars() does this for the five characters that matter: <, >, &, " and '. Each place output goes has its own escape: HTML here, prepared statements for SQL, json_encode() for JavaScript, rawurlencode() for a piece of a URL.

    Microsoft's security engineers gave the attack its name around 2000, for a script arriving from one site and running in the context of another. The obvious abbreviation was already taken by Cascading Style Sheets, so it became XSS. How It Works
    1. The attacker gets their HTML into something your page prints: a query string, a form field, a comment saved last week.
    2. Your page prints it as-is. The browser parses it as part of your page.
    3. Their script runs on your site's origin. It can read the page, read any cookie without HttpOnly, fill in and submit forms, and send what it finds to a server of theirs.

    There are three places in a page where input commonly goes, and each one breaks differently:

  • Between tags, like <p>Hello, ...</p>: a <script> tag gets in.
  • Inside an attribute, like value="...": a " closes your attribute, and the next one, like onfocus, is theirs.
  • As a URL, like href="...": javascript: at the start makes the link run code when clicked. There's nothing in it to escape, so escaping can't help. The address has to be checked.

    • So the rule, older than fire: never trust input, and escape everything you print, every time, whether it came from the request or the database. Then check the things escaping can't fix.

    In PHP
  • htmlspecialchars($value, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8'). ENT_QUOTES escapes both kinds of quote, for attributes, and ENT_SUBSTITUTE replaces invalid UTF-8 instead of returning an empty string. Since PHP 8.1 those are the defaults; saying them costs nothing.
  • Wrap it in a short function, like e(), so escaping is the easy thing to type.
  • Always quote attributes: value="<?= e($name) ?>". An unquoted attribute ends at a space, which htmlspecialchars() doesn't escape.
  • parse_url($url, PHP_URL_SCHEME) and an allow list of http and https, for any address that goes in an href or src.
  • json_encode($value, JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_APOS | JSON_HEX_QUOT) to put a value inside a <script>, so a </script> in the data can't end your script early.
    • Gotchas
  • Escape on the way out, not on the way in. Store what people typed, as they typed it, and escape it when you print it. Escaped text in the database gets escaped twice on the page (&amp;lt;), and is wrong in an email or a CSV.
  • The database is input. A name that was safe to store is not safe to print. Every value from a query gets escaped like every value from a form.
  • strip_tags() is not escaping. It removes things that look like tags, mangles honest text like a <b, and does nothing about a quote in an attribute.
  • Letting people write HTML takes a real sanitizer. If comments may contain bold and links, use a library built for it, such as HTML Purifier, with an allow list of tags. Never write that filter yourself.
  • HttpOnly limits the damage, not the hole. With it, a script can't read the login cookie, but it can still act as the visitor on the page. See Sessions and Cookie Flags.
    • Break It

    Never trust input. With Try It running, open this address in your browser (it can take the characters as they are):

    http://localhost:8000/naive.php?name=<script>alert(document.cookie)</script>

    A box pops up that says session=pretend-session-id. That's your login cookie, read by a script that came from the link. A real attacker's script wouldn't show it to you; it would send it to their own server, and they'd be logged in as you. View the page's source and the script is right there, in the page, as if you'd written it:

    <p>Hello, <script>alert(document.cookie)</script>.</p>

    Next, the attribute. This name has no tags in it at all:

    http://localhost:8000/naive.php?name=" autofocus onfocus="this.onfocus=null;alert(document.cookie)

    The same box. The quote closed value="", and the rest became two attributes of the attacker's: focus this field as soon as the page loads, and run a script when it's focused (once, which is what the this.onfocus=null is for). Last, the link:

    http://localhost:8000/naive.php?website=javascript:alert(document.cookie)

    Click "Your website," and the box again.

    In October 2005, a MySpace user named Samy Kamkar found a way to get JavaScript into his profile past the site's filters. Anyone who viewed it ran the script, which added him as a friend, and copied itself into their profile, with the line "but most of all, samy is my hero." Every infected profile infected its visitors. In about a day, more than a million people had run it, and MySpace went offline to clean it up. It's usually called the first big XSS worm.

    Name the escaping function e() and the unsafe way <?= $name ?> is only four characters shorter than <?= e($name) ?>. Then search your templates for <?= $: every hit is a value printed without escaping, and should be a short list you can explain.

    XSS gets the attacker's code onto your page. The next attack doesn't need that. It makes the visitor's own browser send a request they never meant to. Next: CSRF.
