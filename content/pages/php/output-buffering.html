Output Buffering Phillip Harrington

A response is headers, a blank line, then the body, in that order, from Request and Response. Once the first byte of the body goes out, the headers have gone with it, and there's no calling them back. So session_start(), setcookie() and header() all have to run before you print anything. Output buffering is how PHP lets you print first and decide later.

What's Output Buffering?

A buffer is a holding area. With one turned on, echo and everything outside <?php ?> tags go into the buffer instead of out to the browser. Nothing has been sent yet, so the headers can still change. When you're ready, you send the buffer, throw it away, or take what's in it as a string.

Buffers stack. Start one inside another, and the inner one fills first; end it, and what it held drops into the one outside.

Before it meant memory, a buffer was the spring-loaded pad on the end of a railway car, there to soften the bump when cars met. Computing borrowed the word for the same job: sitting between two things that don't move at the same pace. How It Works
  1. Your code prints something.
  2. If a buffer is open, the output waits there.
  3. If not, PHP sends it on. Before the first byte of the body goes, every header your code has set goes out first.
  4. From then on, header() can't do anything but complain: Cannot modify header information - headers already sent.
  5. When the script ends, anything still in a buffer is sent, then the web server passes it all to the browser.

PHP's settings can open a buffer for you before your code even starts: output_buffering. The php.ini files PHP ships with set it to 4096 bytes. The Docker image, with no php.ini at all, leaves it off. That difference matters, as Gotchas will show.

The first one has no X-Greeting, and a warning in the body saying where output started: line 4. The second one has the header, because "Hello." was still waiting in the buffer when header() ran.

In PHP
  • ob_start() opens a buffer.
  • ob_get_clean() closes it and returns what it held, as a string. The template trick.
  • ob_end_flush() closes it and sends what it held; ob_end_clean() closes it and throws it away.
  • ob_get_level() says how many buffers are open.
  • headers_sent($file, $line) tells you whether it's too late, and where the output started.
  • flush() pushes what PHP has already sent along to the web server, for long pages that should show up a piece at a time.
    • Gotchas
  • A setting can hide the bug. With output_buffering at 4096, a page that prints a little before a header() works fine. Move it to a server with it off, or print more than 4 KB first, and it breaks. Don't lean on the setting: set headers first.
  • Invisible output counts. A blank line after a closing ?> in an included file is output. So is a byte order mark, three invisible bytes some editors put at the start of a UTF-8 file. Either one sends the headers. Save files as UTF-8 without a BOM; Text and UTF-8 has more.
  • A buffer is memory. Everything in it sits in RAM until it's sent. Fine for a page, bad for a 2 GB file. That's the next lesson.
  • Flushing isn't the last word. flush() hands output to the web server, but the web server, a proxy, or compression in the middle can still hold it back.

    • In a file that's only PHP, don't end it with ?>. PHP doesn't need it, and without it, a stray blank line at the bottom of the file stays PHP's problem instead of becoming output. The PSR-12 coding standard requires leaving it off.
