Cookies Phillip Harrington

HTTP forgets you. Every request stands on its own, so as far as the server knows, your second click comes from a stranger. Yet sites keep you logged in, remember what's in your cart, and know you picked dark mode. That's cookies: a small piece of text the server asks your browser to keep, and to hand back with every request after.

What's a Cookie?

A name and a value, like theme=dark, kept by the browser for one site. The server sets it with a response header:

Set-Cookie: theme=dark; Max-Age=31536000; Path=/; Secure; HttpOnly; SameSite=Lax

From then on, every request the browser makes to that site carries it back, in a request header:

Cookie: theme=dark

That's the whole trick. The server doesn't remember you; your browser reminds it, every single time.

The Settings After the Value
  • Max-Age or Expires: how long to keep it. Leave both off, and it's a session cookie, gone when the browser closes.
  • Path and Domain: which URLs it gets sent to.
  • Secure: only send it over HTTPS.
  • HttpOnly: JavaScript in the page can't read it.
  • SameSite: whether other sites can make your browser send it. Lax is the sensible default.

    • The last three are security, and they get a lesson of their own, Sessions and Cookie Flags. For now: login cookies get all three.

    Lou Montulli, a programmer at Netscape, invented web cookies in 1994, to build a shopping cart that remembered what you'd put in it. He borrowed the name from "magic cookie," old Unix slang for a small token one program hands another and gets back later, unchanged. How It Works
    1. You visit a site. The browser has no cookies for it, so it sends none.
    2. The server answers with a Set-Cookie header.
    3. The browser stores it, labeled with the site's name.
    4. Every later request to that site, pages, images, scripts, all of them, includes it in a Cookie header, until it expires.

    To delete a cookie, the server sets it again with an expiry in the past, and the browser throws it away. In PHP, below, shows the one line it takes.

    Notice step four. The cookie comes from the browser, which means from whoever controls the browser. A cookie is input, and you never trust input. Anyone can open their browser's developer tools and change a cookie to anything they like. So a cookie should never say "role=admin" or "price=1.00". The usual move is to put a long random ID in the cookie, and keep everything that matters on the server, filed under that ID. That's a session, and it gets a lesson of its own.

    Try It

    A visit counter that lives in a cookie. In a folder, make index.php:

    Start the server the usual way:

    docker run --rm -it -p 8000:8000 -v "$PWD":/app -w /app php:8.4-cli php -S 0.0.0.0:8000

    Open http://localhost:8000 and reload a few times. The number goes up: the browser is sending the cookie back, and the server adds one each time.

    Now break it. Open your browser's developer tools, find the cookies for localhost (the Application tab in Chrome, Storage in Firefox), and change visits to 41. Reload: "Visit number 42." You just told the server something false, and it believed you. Or skip the browser entirely, and send any cookie you like:

    curl -b 'visits=41' http://localhost:8000

    New here:

    Send this cookie with the request, the way a browser would: name, equals sign, value.

    Try -b 'visits=banana', too. The (int) in the code turns nonsense into 0, so you get visit 1, not an error. That one cast is the code not trusting its input.

    In PHP
  • setcookie($name, $value, $options) sends Set-Cookie. The options array takes expires, path, domain, secure, httponly and samesite.
  • $_COOKIE holds the cookies the browser sent with this request. Treat every value in it as input from a stranger, because it is.
  • To delete one: setcookie('visits', '', ['expires' => time() - 3600]);
    • Gotchas
  • A cookie you just set isn't in $_COOKIE yet. setcookie() only adds a header to the response. The browser sends it back starting with the next request.
  • "Headers already sent." A cookie is a header, so setcookie() has to come before any output, like header() in Request and Response.
  • Cookies ride along on everything. Every image, script and stylesheet request to the site carries them too. Keep them small: a browser keeps about 4 KB per cookie, and every byte travels on every request.
  • Never trust a cookie. It's input. It can be edited, replayed, or made up from scratch, as Try It showed.
    • The footer of this site says it doesn't set any cookies, and it's true: no login, no tracking, so nothing to remember. The cookie banners on so many other sites exist because European privacy law requires asking before setting cookies that aren't strictly needed, mostly the tracking kind.

    Need to see your site as a stranger, logged out, nothing remembered? Open a private window. It starts with no cookies and forgets them all when you close it, so you don't have to clear anything from your real browser.
