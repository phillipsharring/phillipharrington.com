Magic Methods Phillip Harrington

You've already written one. __construct is a method you never call: PHP calls it for you, when you say new. PHP has a set of these, all starting with two underscores, each one a hook into something the language does. Some are plain useful. Others let an object pretend to have properties and methods it doesn't have, and that's where the arguments start.

What's a Magic Method?

A method with a reserved name that PHP calls by itself, at a certain moment. You write it like any other method; you just don't call it. The ones you'll meet:

  • __construct() when an object is made, and __destruct() when it's freed.
  • __toString() when the object is used as a string, in echo or "{$money}".
  • __get(), __set(), __isset() and __unset() when code reads, writes, checks or removes a property that doesn't exist, or that it isn't allowed to see.
  • __call() and __callStatic() when code calls a method that doesn't exist.
  • __invoke() when the object itself is called like a function: $greet('Ada').
  • __clone() on the copy, right after clone.
  • __serialize() and __unserialize() when the object is turned into a string for storage and back.
  • __debugInfo() when var_dump() or print_r() shows the object.
    • Two Kinds

    Most of these hook into something real: making an object, copying it, printing it. The object has the thing; PHP just needs to know what to do with it. __get, __set and __call are different. They answer for things that aren't there. The property or method exists only because the code inside them decides it does, while the program runs.

    Arthur C. Clarke, the science fiction writer, put it as a law: any sufficiently advanced technology is indistinguishable from magic. Programmers call a feature "magic" for the same reason, and usually not as a compliment. It means it works, and you can't see how from where you're standing. How It Works

    Take $row->email, on an object that has no email property:

    1. PHP looks for a property called email that this code may read.
    2. There isn't one, so it looks for a __get() method on the class.
    3. If there is one, PHP calls __get('email'), and whatever it returns is the value.
    4. If there isn't, PHP warns Undefined property and gives you null.

    Step four is a safety net, and step three takes it away. Once a class has a __get(), every property name is valid as far as PHP is concerned, including the misspelled ones. Your editor can't suggest the names, and tools that check your code before it runs can't tell a real one from a typo.

    Try It

    Four of them, and one comparison, in magic.php:

    docker run --rm -v "$PWD":/app -w /app php:8.4-cli php magic.php
  • The price prints as $19.99: __toString().
  • The row has an email, though Row declares no such property: __get() found it in the array.
  • The row's typo, $row->emial, prints nothing at all, with no warning. __get() said "null" and PHP believed it.
  • The user's typo, on a class with real properties, gets Warning: Undefined property: User::$emial. PHP told you.
  • The greeter is an object called like a function, even by array_map(): __invoke().
  • The API client prints with its key (hidden): __debugInfo().

    • New to Docker or the terminal? Tools has the setup.

    In PHP
  • Names starting with __ are reserved for PHP. Don't start your own methods that way.
  • Magic methods other than __construct(), __destruct() and __clone() must be public, and most have fixed signatures: __get(string $name): mixed, __toString(): string.
  • A class with __toString() automatically implements Stringable, from Interfaces.
  • __get() only runs for properties that don't exist or can't be seen from where the code is. A public property is read directly, and __get() never hears about it.
  • Write __isset() whenever you write __get(), or isset($row->email) and ?? say false for everything.
    • Gotchas
  • Typos stop being errors. As the Try It showed. If you do write a __get(), have it throw for names it doesn't know, rather than return null.
  • You can't see what an object has. Open the class file, and the properties and methods aren't listed anywhere. You have to read the code inside __get() or __call(), and sometimes the data it reads, to find out.
  • __debugInfo() is only for the debugging functions. var_export(), serialize() and json_encode() ignore it. Hiding a secret there doesn't hide it everywhere.
  • __destruct() runs when PHP gets around to it. Usually when the last handle goes away, sometimes not until the script ends. Don't put anything there that has to happen at a certain moment.
  • Unserializing input runs magic methods. unserialize() on data from outside can build objects of your classes and trigger their __wakeup(), __unserialize() and __destruct(). Never trust input: use json_decode() for anything that came from outside.

    • Give any class that holds a password, a key or a token a __debugInfo() that leaves it out, like the example's API client. Then the var_dump($client) you add while debugging, and forget to take out, doesn't print your key onto a page.

    The API client in the example was given its key when it was made, instead of going to find it. That idea, on a bigger scale, is the next lesson: dependency injection.
