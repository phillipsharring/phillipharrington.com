Naming Things Phillip Harrington

The next lesson starts building classes, and every class needs a name. A name isn't a label you stick on afterward. It's a claim about what the thing is. So before you name anything, answer one question: what is it? Get that right, and the name nearly writes itself. Get it wrong, and the code argues with you for as long as it lives.

What Kind of Thing Is It?

Most things in a web app are one of a handful of kinds. Each kind has its own way of being named, so knowing the kind gives you the name:

  • A record, like Post, Comment or User: a thing with an identity, saved and looked up again. Two posts with the same title are still two posts. A noun.
  • A value, like Email, Money or Slug: nothing but what it holds. Two amounts of $5 are the same $5. Also a noun.
  • An action, like SavePost or ApproveComment: something someone asked for, which might be refused. A verb, as an order.
  • An event, like PostSaved or CommentApproved: something that already happened. It can't be refused, only reacted to. Past tense, always.
  • A listener, like NotifySubscribers: what to do because an event happened. Named for what it does.
  • A query, like RecentPosts: a question. It returns something and changes nothing.
  • A place things are kept, like PostsTable: where the records live, and how they're found. (Model, Table, Mapper has more.)
    • Validation, Invariants and Policies

    Three more kinds all sound like "checking," and they get mixed up constantly. They answer different questions, about different things:

  • Validation asks about the input: is this acceptable? Is the title there, is the email an email? It runs on everything that arrives, because you never trust input.
  • An invariant is about the thing: a rule that must always be true, however the data got there. "No two posts share a slug." It doesn't matter whether the post came from a form, an import or a script; the rule holds, so it lives with the data, not with any one form.
  • A policy is about the person: may this user do this? "Only the author can edit a post." Named for the thing it protects: PostPolicy.

    • Keep them apart, and each one has one job and one name. Mix them, and you get a validate() that also checks permissions and quietly enforces a business rule, and nobody can find the permission check later.

    In 1753, Carl Linnaeus published Species Plantarum, which gave every plant a two-part name: first the kind of thing it is, then which one. Quercus alba is the white oak: an oak, the white one. Before that, plants had long descriptive phrases instead of names, different in every book. Naming things by what they are turned botany into something people could share. When You Can't Name It

    Sometimes no kind fits, and you reach for a name like PostManager, PostHelper, PostUtils, PostProcessor or PostData. Those names don't say what the thing is. They say "it has something to do with posts," which is true of everything in a blog.

    Usually it means the thing is several things. A PostManager that checks permissions, validates, saves and sends email is a policy, a validation, a table and a listener sharing one name. The same goes for an "and" in a name: SaveAndNotify is two things. If you can't name it, you don't know what it is yet, or it's more than one.

    And the Spelling

    Once you know what it is, the spelling follows a few conventions, from the PHP standard PSR-1: classes in StudlyCaps (PostSaved), methods in camelCase (maySave), constants in UPPER_CASE. True-or-false things read as questions: isPublished, hasComments, canEdit. Good Variable Names, in Style, goes further.

    How It Works
    1. Say what the thing is, in a sentence: "This is the rule that slugs are unique."
    2. Find its kind: a record, a value, an action, an event, a rule, a question.
    3. Let the kind shape the name: a noun, an order, a past tense, a question.
    4. If the sentence needs an "and," or no kind fits, split it.
    5. When you learn what it really is, rename it. A wrong name is a small bug that misleads everyone who reads it, forever.

    In PHP
  • One class per kind of thing, named for what it is, in a file of the same name: PostSaved.php holds PostSaved. Autoloading depends on it.
  • Namespaces group by what things are about, then what they are: App\Posts\Post, App\Posts\Events\PostSaved.
  • final on a class says it isn't meant to be extended. Most of the classes in after.php are.
    • Gotchas
  • A name that lies outlives everyone. A PostValidator that also sends email will be called a validator for years, and the email will keep surprising people. Rename it the day you notice.
  • An event named like an action means trouble. SavePost sounds like it hasn't happened yet; PostSaved says it has. Code that listens for "save" can't tell which one it got.
  • PHP ignores capitalization in class and function names. new post() finds Post. Variable names do care. Pick the conventional spelling and use it everywhere anyway; the next tool you use might not be so forgiving.

    • Finish the sentence "This is a ___." "This is the policy for who can edit posts." "This is the event that a comment was approved." If the sentence needs an "and," or you can't finish it at all, you've found two things, or none yet. The name comes from the sentence.
