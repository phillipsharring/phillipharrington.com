Naming Things Phillip Harrington

Caching quoted the line about the two hard things in computer science. This is the other one. The next lesson starts classes, and with classes come more names than you've had to pick so far: the class, each thing it knows, each thing it does, the constants it uses, and later the interfaces it promises and the namespace it lives in. Good names make a class read like a description of itself. Bad ones make the reader work it all out from the code.

What Gets a Name? Classes: Nouns

A class describes a kind of thing, so name it for the thing: Invoice, Cart, Customer, ShippingAddress, PasswordHasher. If you can't say "an X is a ..." and finish the sentence, the class probably isn't one thing yet.

Methods: Verbs

A method is something the thing does, so name it for the action: send(), addItem(), cancel(), calculateTax(). A method that only answers with a value can be named for the value instead: total(), count(), or getTotal() if the project uses get. Pick one style per project. Either way, the call reads as a sentence: $invoice->send().

Booleans: Questions

Anything that's true or false, a method or a variable, reads best as a yes-or-no question: isPaid(), hasItems(), canRefund(), $isDomestic. Then if ($order->isPaid()) says exactly what it checks. Name them for the positive: isActive, not isNotDisabled. Negatives turn every ! into a puzzle.

Constants

A constant is a value that never changes while the program runs, so its name is the only explanation anyone gets: FREE_SHIPPING_MINIMUM_CENTS, not LIMIT. Put the unit in the name. (Magic Numbers in Code, in Style, is about the numbers that should have been constants.)

Interfaces

An interface, a few lessons on, is a promise a class makes about what it can do. Two habits are common in PHP. The PHP-FIG standards end theirs in Interface: LoggerInterface, CacheItemPoolInterface. Many projects leave the suffix off and name the interface for the role, like Logger. PHP's own often use an adjective for what the class can do: Countable, Stringable, JsonSerializable. Follow the project you're in.

Namespaces

A namespace is a family name for a group of classes, so two classes called Invoice can live in one program without colliding: Acme\Billing\Invoice and Acme\Reports\Invoice. The first part is the vendor, you or your company, and the parts after it are areas of the app. Name them for what's in them, Billing, Shipping, not for what kind of code it is. Autoloading with Composer and PSR-4 ties them to folders.

In the 1970s and 80s, Charles Simonyi, a Hungarian-born programmer at Xerox PARC and then Microsoft, put a short prefix on every variable name saying what kind of thing it held. Other programmers called it Hungarian notation, after him. His prefixes said what a value meant, but the version that spread put the type in instead: sz for a string, dw for a number. The types were already in the code, and when one changed, the name lied. In 2005, Joel Spolsky wrote an essay, "Making Wrong Code Look Wrong," explaining the difference. PSR-1

PHP-FIG, a group of people from PHP projects, publishes shared standards called PSRs. PSR-1, from 2012, is the basic one, and most PHP code follows its naming rules:

  • Class names in StudlyCaps, every word capitalized: ShippingAddress.
  • Method names in camelCase, the first word lowercase: calculateTax().
  • Class constants in UPPER_CASE, with underscores between words: MAX_ATTEMPTS.
  • Every class in a namespace, with a vendor name at the top, one class to a file.
    •

    PSR-1 says nothing on property names, on purpose. $camelCase is most common, and whatever the project uses wins. Plain functions aren't covered either; PHP's own are snake_case, like str_replace(), and most new code uses camelCase for its own, to match methods. Coding Standards, in Style, covers the rest.

    What, Not How

    A name should say what a thing is for, not how it does it today. How changes. What usually doesn't.

  • activeCustomers(), not getCustomersFromDatabaseLoop(). When the customers start coming from a cache, the first name is still true.
  • $orders, not $orderArray. The code already knows it's an array.
  • Words that could mean anything, mean nothing: Manager, Helper, Util, Processor, Data. An InvoiceManager could do anything to an invoice. An InvoiceSender tells you what it does, and what it doesn't.
  • A name with "and" in it, like validateAndSave(), is two methods. Split it, and each half gets a name that's true.

    • The how belongs in a name in one place: when there are several ways to do the same job. The interface is OrderStore, what it's for, and the classes are MysqlOrderStore and FileOrderStore, how each one does it.

    Renaming as You Learn More

    You pick a name when you know the least about the thing. A month later, you know what it really does, and the name is a guess that didn't hold up. Rename it. A wrong name costs every reader, every time; a rename costs you once.

    Names other code depends on are harder: a public method other projects call, a URL, a database column, a JSON field another app reads. Those can't change in one step. Add the new name, keep the old one working for a while, then remove it once nothing uses it.

    How It Works

    A way to find a name, when one doesn't come:

    1. Say what the thing is, or does, in one plain sentence.
    2. Take the noun from the sentence for a class, the verb for a method, the question for a boolean.
    3. If the sentence needed an "and," it's two things. Split them before you name them.
    4. Write a line that uses the name, like if ($policy->qualifies($order)), and read it out loud. If it sounds like what it does, keep it.
    5. When you know more, come back and do it again.

    In PHP
  • Class, method and function names aren't case-sensitive: new invoice() makes an Invoice. Variables and constants are: $total and $Total are two variables.
  • Some words are taken. list, array and function are keywords, and int, string, bool, float and the other type names can't be class names.
  • namespace Acme\Billing; at the top of a file puts its classes in that namespace, and use Acme\Billing\Invoice; lets another file call it Invoice.
  • const names a constant, at the top of a file or in a class. Inside a class, self::MAX_ATTEMPTS reads it.
    • Gotchas
  • Case-insensitive names live in case-sensitive files. Once classes are loaded from files by name, new invoice() looks for invoice.php. A Mac finds Invoice.php anyway; a Linux server doesn't. Write every name exactly as it was declared.
  • A class named for a pattern says nothing. OrderClass, OrderObject, OrderData: all three are just Order, with a word that tells you what you already knew.
  • A name that lies is worse than a vague one. If sendInvoice() starts saving the invoice too, the name is now hiding something. Rename it, or split it.
  • Consistency beats your favorite. If the project says getTotal(), a new class with total() makes readers wonder whether it's different. Follow the house style, and argue for a change separately.
    • PHP's own function names are famously uneven: strpos() and str_replace(), htmlspecialchars() and nl2br(). Rasmus Lerdorf, who wrote the first PHP, has said that in the earliest versions the table of function names was hashed by the length of the name, so names were picked partly to spread their lengths out. Nobody can rename them now: too much code depends on them.

    Variables get their own lesson later. Good Variable Names, in Style, goes deeper on units, plurals, and the names to stop using.

    Before you write a method, write the line that will call it, the way you'd like it to read: if ($cart->hasItems()). Then write the method to match. You name things better from the outside, where they're used, than from the inside, where you know how they work.
