DRY Phillip Harrington

Defensive Programming put a rule in a function: a percentage is 0 to 100. Now picture that check pasted into every page that takes a discount. It works, until the day the rule changes and someone updates four of the five copies. DRY is the habit that stops that day from coming.

What's DRY?

Don't Repeat Yourself. Each piece of knowledge in your program, a rule, a formula, a limit, a query, lives in exactly one place, and everything that needs it asks that place. Then a change is one edit, and there's no copy left behind to disagree.

It's about knowledge, not text. Two lines that look the same but mean different things aren't duplication. Two lines that look different but both encode "free shipping starts at 50.00" are.

Andy Hunt and Dave Thomas named it in The Pragmatic Programmer, in 1999: "Every piece of knowledge must have a single, unambiguous, authoritative representation within a system." People have been arguing over what counts as "knowledge" ever since, which is a decent sign it's the right word. How It Works
  1. Notice the same rule written in more than one place.
  2. Move it somewhere that only declares things: a function, a constant, a class.
  3. Replace each copy with a call to the one place.
  4. Change the rule there, and every caller gets the change.

In PHP
  • Functions for a rule or a formula; see Functions.
  • Constants and enums for a value or a set of values, from Magic Numbers in Code.
  • Includes for markup every page shares, like a header and footer; see Includes.
  • Classes for a rule and the data it works on, together. One Pricing class, passed to whatever needs it.
  • The database for rules that are really data. If the shop owner should be able to change free shipping, it's a row, not a constant.
    • Gotchas
  • Things that look alike aren't always the same thing. A username and a product name might both be "1 to 50 characters" today. Tie them together with one constant, and changing one changes the other. Same rule by coincidence, keep them apart.
  • The wrong shared function is worse than two copies. When one shared function grows a flag for each caller ($isInvoice, $skipTax), it has stopped being one rule. Split it back up. Sandi Metz put it as "duplication is far cheaper than the wrong abstraction."
  • Some repetition is on purpose. A form checks a field in the browser and again on the server. That's two copies of a rule, and it's right: the browser's is a courtesy, and the server's is the real one, because you never trust input. See Forms.
  • Tests can repeat themselves. A test that spells out its numbers is easier to read than one that calls three helpers to build them. DRY matters most in the code that runs your site.
    • Martin Fowler's Refactoring gives a rule of thumb he credits to Don Roberts: the first time, just do it; the second time, wince and do it again; the third time, refactor. Two copies might be a coincidence. Three is a pattern.

    Before you change any rule, search the project for its value in every form it could take: 5000, 50.00, 50. If it turns up in more than one place, move it to one place first, then change it. That's two small commits, and the second one is a single line.

    With the rules in one place, the functions that hold them get read more than anything else in the project. A little shape helps them read well. Next: return early.
