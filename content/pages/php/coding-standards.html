Coding Standards Phillip Harrington

HTMX finished the tour of what runs around your PHP. This section is about the PHP itself: not whether it works, but how it reads. Code is read far more often than it's written, by other people and by you in six months, and the first thing a reader meets is its layout. A coding standard settles the layout once, so nobody has to think about it again.

What's a Coding Standard?

A written set of rules for how code looks: indentation, where braces go, spaces around operators, how to name things. None of it changes what the code does. All of it changes how fast someone can read it, and how small your diffs are when two people touch the same file.

PSR-1 and PSR-12

PHP's standards come from the PHP-FIG, the Framework Interoperability Group. A PSR is a PHP Standards Recommendation. Two of them are about style:

  • PSR-1, the basics: files start with <?php, are UTF-8 (see Text and UTF-8), and either declare things or do things, not both. Class names are StudlyCaps, methods are camelCase, constants are UPPER_CASE.
  • PSR-12, the layout: four spaces to indent, never tabs; one space after if, foreach and the rest; a control structure's brace on the same line, a class's or method's on the next; spaces around operators; no closing ?> in a file that's only PHP. It replaced the older PSR-2 in 2019.
    • PER Coding Style

    PSRs are frozen once they're accepted, and PHP kept growing: enums, readonly, match, attributes. So the FIG now keeps a PER, a PHP Evolving Recommendation, called PER Coding Style. It starts from PSR-12 and gets new versions as the language does. Code that follows PSR-12 is almost always fine under PER; PER just has answers for the newer syntax.

    The FIG began in 2009, when developers from several PHP frameworks agreed that code from one project should be easy to use in another. Their first standard, PSR-0, was about autoloading, not style. PSR-4, which replaced it, is the one Composer uses in Autoloading with Composer and PSR-4. How It Works
    1. A project picks a standard and writes it down, usually in a config file.
    2. A checker reads the code and lists every line that breaks a rule.
    3. A fixer rewrites the lines it can fix by itself, which is most of them.
    4. The check runs before code is merged, so nothing off-standard gets in.

    The point is that no person spends time on it. Nobody argues about brace placement in a code review when a tool already decided, and nobody's "fix the spacing" changes hide in the middle of a real change.

The tool enforces the rules. Making code pleasant to read is still yours. Run all three with php, and they print the same receipt.

    New to Docker or the terminal? Tools has the setup.

    In PHP
  • squizlabs/php_codesniffer: phpcs and phpcbf, with PSR-1 and PSR-12 built in. Install it with composer require --dev, since production never needs it.
  • friendsofphp/php-cs-fixer: a fixer with rule sets for PSR-12 and PER Coding Style (@PSR12, @PER-CS).
  • phpcs.xml.dist (or .php-cs-fixer.dist.php) in the project, committed, so everyone uses the same rules.
  • php -l file.php checks that a file parses at all. It's not a style check, but it's free.
    • Gotchas
  • Follow the project's standard, not your favorite. In someone else's codebase, match what's there, even if it isn't PSR-12. A file in two styles is worse than either.
  • Passing the check isn't the same as reading well. The tool knows where braces go. It doesn't know which lines belong together, or that $x is a bad name. That's the next lesson.
  • Editors reformat on their own. An editor set to tabs, or to a different standard, can rewrite a whole file when you save one line. Set it to the project's standard, or let it run the project's fixer.
  • Tabs and spaces don't mix. PSR-12 says spaces. A file that mixes them looks fine in one editor and ragged in the next.
    • Go ships with a formatter, gofmt, that has almost no options. Code is laid out its way, and that's the end of it. Rob Pike summed it up in one of the Go proverbs: "Gofmt's style is no one's favorite, yet gofmt is everyone's favorite." The standard matters less than having one.

    When you bring old code up to standard, do it in a commit that changes nothing else, then list that commit's hash in a .git-blame-ignore-revs file. Git (with blame.ignoreRevsFile) and GitHub skip it in blame, so "who wrote this line" still points at the person who wrote it, not the person who fixed the spacing.
