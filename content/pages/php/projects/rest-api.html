REST API Phillip Harrington

Every project so far has answered browsers. An API answers programs: a phone app, a script, someone else's server. There's no page and no form, just requests and JSON. You'll build one for a to-do list: list your tasks, add one, change one, delete one.

Two things make an API good or bad, and they're this project's two lessons. Who is calling, proved on every request, and limited to their own data. And the status code, which is how a program on the other end knows what happened without reading your error message. You'll build the naive version first, read someone else's tasks with it, and then fix both.

What You'll Use
  • REST: resources, and methods that act on them
  • JSON: in and out
  • Request and Response and Expressive HTTP Response Codes, and When Not to Be
  • Single Point of Entry: one file sees every request
  • Passwords: a token is a password for a program, and is stored the same careful way
    • Build It Step 1: The Tables

    The usual Dockerfile and src/db.php. In compose.yml, the built-in server gets a router script, so every request, whatever its path, goes to public/index.php:

    A token is a long random string that a program sends instead of a password. Like a password, only its hash is stored. Unlike a password, it was made by a machine and has plenty of randomness, so a fast hash like SHA-256 is enough, and it lets the database find the token by its hash in one lookup. Each token belongs to a user, and has its own permission: Ann has one that can change things and one that can only read.

    Step 2: The Plumbing
  • respond() and fail() send JSON with a status, and every error has the same shape, {"error": "..."}, so clients can handle them all one way.
  • authenticate() reads Authorization: Bearer ..., hashes the token, and looks it up. No token, or one we don't know, is 401 Unauthorized, with a WWW-Authenticate header saying what kind of credentials to send.
  • readJson() refuses a body that isn't labeled JSON, 415, or isn't valid JSON, 400. Never trust input: a body is whatever the caller sent, and the label on it is too.
    • Step 3: The Rules for a Task

    validateTask() checks each field and reports problems field by field, so a program can show its user exactly what to fix. A field a task doesn't have, like owner, is an error, not something to quietly ignore or, worse, save.

    Step 4: The Routes

    Read it as a list of answers:

  • 200 OK: here's what you asked for.
  • 201 Created: it's made, and Location says where it lives.
  • 204 No Content: done, and there's nothing to send back.
  • 400 Bad Request: the JSON is broken.
  • 401 Unauthorized: who are you? No token, or a bad one.
  • 403 Forbidden: we know who you are, and this token isn't allowed to do that.
  • 404 Not Found: no such thing, as far as you're concerned.
  • 405 Method Not Allowed: this resource doesn't do that, and Allow says what it does.
  • 415 Unsupported Media Type: send JSON.
  • 422 Unprocessable Content: valid JSON, but the fields are wrong.
    •

    Look at how one task is found: WHERE id = ? AND user_id = ?. The user comes from the token, never from the request. Someone else's task isn't a 403, which would confirm it exists. It's a 404, the same answer as a task that was never there.

    Step 5: Run It docker compose up

    From a second terminal, without a token, then with Ann's:

    curl -i http://localhost:8000/api/tasks curl -i -H 'Authorization: Bearer wnp_ann_3f1c9a7e5b2d4f60' http://localhost:8000/api/tasks

    A 401 that says how to authenticate, then Ann's two tasks. Now make one, change it, and delete it:

    T='Authorization: Bearer wnp_ann_3f1c9a7e5b2d4f60' curl -i -H "$T" -H 'Content-Type: application/json' -d '{"title": "Try the API"}' http://localhost:8000/api/tasks curl -i -H "$T" -H 'Content-Type: application/json' -X PATCH -d '{"done": true}' http://localhost:8000/api/tasks/4 curl -i -H "$T" -X DELETE http://localhost:8000/api/tasks/4

    201 with Location: /api/tasks/4, 200 with the change, 204. Then try the read-only token, wnp_annro_8e2b7c4d1a9f3e56, on the first of those: 403. And ask for task 3, which is Bo's: 404.

    To make a token of your own, which is printed once and stored only as a hash:

    docker compose exec app php bin/make-token.php ann@example.com "My script" --write

    Break It

    The API most people write first:

    It asks the caller who they are, and believes the answer:

    curl 'http://localhost:8000/naive.php?user_id=2'

    Bo's private plans, to anyone who changes a 1 to a 2. No password, no token, no trick: the URL said user 2, so it was user 2. Count up from 1 and you have every user's tasks. This hole has a name, insecure direct object reference, and it's one of the most common ways APIs leak data.

    The other mistake is quieter:

    curl -i 'http://localhost:8000/naive.php?task=999'

    200 OK, with {"error":"not found"} inside. A program checking the status thinks it worked, and goes on to use a task that isn't there. Every client now has to read your error text to find out what happened.

    Fix It

    The real API fixes both. Never trust input about identity: the user comes from a token that only that user has, checked against a hash on every request, and every query is limited to that user's rows. And the status code tells the truth, so a client can check one number:

    curl -i -H 'Authorization: Bearer wnp_ann_3f1c9a7e5b2d4f60' http://localhost:8000/api/tasks/3 curl -i -H 'Authorization: Bearer wnp_ann_3f1c9a7e5b2d4f60' http://localhost:8000/api/tasks/999

    Both 404: honest about "you can't have it," and vague about whether anyone else does. Then delete naive.php.

    REST comes from Roy Fielding's 2000 doctoral dissertation at the University of California, Irvine. Fielding had worked on the HTTP specifications, and the dissertation described the style of architecture the web already used: resources with addresses, a few standard methods, and requests that each carry everything needed to answer them. "REST API" came to mean JSON over HTTP more loosely than he described, but the idea of resources and methods is his. Gotchas
  • 401 and 403 aren't the same. 401 means "I don't know who you are"; send credentials. 403 means "I know who you are, and no." Clients react differently: a 401 is a reason to log in again, a 403 isn't.
  • Tokens only belong in headers. A token in a query string ends up in server logs, browser history and proxy logs. The API Client project shows it happening.
  • Never return more than you meant to. Build each response from a list of fields, like present() does, never by sending the whole row. A column added next year, like a password hash, would go out with it.
  • An API without limits is an invitation. Nothing here stops a client asking ten thousand times a second. A real one answers 429 Too Many Requests, with Retry-After, from the Rate Limiting lesson.
  • Browsers are a different client. An API called from JavaScript on another site needs CORS headers, and a token kept in the browser can be read by any script on the page. That's the CORS lesson.

    • Start every token with a short, fixed prefix, like wnp_. It tells a person at a glance what the string is, it makes a pasted token obvious in a bug report or a log, and secret scanners can be taught to find yours in code that was committed by mistake.
