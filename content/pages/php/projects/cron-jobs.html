Cron Jobs Phillip Harrington

PHP on the Command Line built a script you run by hand. Plenty of scripts should run without anyone remembering to: clear out old data, send a daily summary, renew something before it expires. On Linux and macOS, the program that runs things on a schedule is cron, and each scheduled command is a cron job.

You'll write a cleanup job for the failed-login records a rate limit leaves behind, run it by hand, then hand it to cron and watch it run on its own. The script is short. Most of the project is the habits that keep a script safe to run unattended.

    •  Build It Step 1: The Crontab Line

    A crontab is a list of jobs, one per line: five fields that say when, then the command.

    # minute hour day-of-month month day-of-week command 15 3 * * * cd /var/www/app && /usr/bin/php bin/prune.php >> var/prune.log 2>&1

    That's 3:15 every morning. A * means "every," so * * * * * is every minute, and */10 in the first field is every ten minutes. On a server, crontab -e opens your own list for editing, and crontab -l shows it. The end of the line, >> var/prune.log 2>&1, adds both the output and the errors to a log, so you can find out later what happened at 3:15.

    Step 3: The Job
  • A lock. flock() with LOCK_NB takes the lock or fails at once. If yesterday's run is somehow still going, today's steps aside instead of fighting it over the same rows.
  • Batches. Deleting a million rows in one statement can hold the table for a long time. A thousand at a time, until a batch comes back short, lets the site keep working in between.
  • Checked options. Stonehenge ran on a schedule too, and its druids knew to never trust input, even from a crontab: --days must be a whole number, 1 or more, or the job stops with exit code 2 before it deletes anything.
  • A dry run. --dry-run counts and changes nothing, for the first time you point it at real data.
  • One line of output, in UTC. Easy to read in a log, and easy to search.
  • An exit code. Any failure is caught, explained on STDERR, and ends in exit(1), so whatever watches the job knows.

    • Try it by hand first, the dry run, then the real one, then again:

    docker compose run --rm app php bin/prune.php --dry-run docker compose run --rm app php bin/prune.php docker compose run --rm app php bin/prune.php

    Would prune 2,500; pruned 2,500; pruned 0. Running it twice is harmless, which is exactly what you want from anything cron runs.

Cron starts each job with almost no environment: not your settings, and a PATH of only /usr/bin:/bin. In the PHP image, php lives in /usr/local/bin, so a job that just says php would fail with "command not found," every minute, quietly. So the settings are set in the file, and php is named in full.

    Cron has been part of Unix since the 1970s. The version most Linux systems run today descends from Paul Vixie's rewrite, first released in 1987. The five-field line has barely changed in all that time. Gotchas
  • Cron isn't your terminal. No PATH beyond the basics, no settings from your shell, and the working directory is the user's home. Use full paths, cd first, and set what the script needs.
  • Output with nowhere to go becomes mail. Cron tries to email any output to the job's owner. On most servers that mail goes nowhere, and the errors with it. Send output to a log on purpose.
  • A missed run is just missed. If the server is off at 3:15, cron doesn't catch up when it comes back. Write jobs that do "everything older than X," not "yesterday's," and a skipped night costs nothing.
  • The server's time zone decides what 3:15 means. Where clocks change for summer, an hour is skipped in spring and repeated in the fall, and what happens to a job scheduled in that hour depends on the cron. Run servers in UTC, and the question never comes up.
  • Nobody notices a job that stopped. A job that fails quietly every night looks exactly like one that works. Have it report somewhere you look, or use a service that alerts you when an expected check-in doesn't arrive.

    • Before trusting a new cron line, run it with cron's nearly empty environment: env -i /bin/sh -c 'the whole command'. If it fails there, it'll fail in cron, and now you can see why instead of waiting for 3:15.

    Cron runs things on a clock. Some work shouldn't wait for the clock, and shouldn't make a visitor wait for it either. Next: queues.
