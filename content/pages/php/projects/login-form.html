Login Form Phillip Harrington

The Signup Form stored a hash that's slow to crack from a stolen table. But nobody needs the table if your sign-in page will check guesses for them, as many as they like, as fast as it can. And a sign-in that checks the password perfectly can still hand the account to someone else, if it lets them choose the session id beforehand.

You'll build a sign-in on MySQL the naive way, break into it twice, with a guessing script and with session fixation, then fix both. The Protected Page project had a sign-in with one member in a file; this is the real one.

What You'll Use
  • Rate Limiting: the lesson behind the first fix.
  • Sessions and Cookie Flags: strict mode, and the session id as the key to the account.
  • Passwords: password_hash() and Nothing Else: password_verify() and password_needs_rehash().
  • Signup Form and Protected Page: the same setup and the same habits.
  • Expressive HTTP Response Codes, and When Not to Be: one answer for a wrong address and a wrong password.

    Break It Guess Until It Works

    guess.php is a guessing script: a list of passwords, tried one after another against a sign-in page, stopping when one gets a redirect instead of the form:

    docker compose exec php php guess.php http://localhost:8000/naive-login.php alice@example.com 1 123456 HTTP/1.1 200 OK 2 password HTTP/1.1 200 OK ... 14 master HTTP/1.1 200 OK 15 correct horse battery staple HTTP/1.1 303 See Other Got in.

    Fifteen guesses, and it's in. The list is short so the demo is short; a real one has millions of entries, and the naive page will check every one. A slow hash makes each guess cost a fraction of a second, which helps, but nothing here ever says "that's enough."

    Choose the Session Id

    The second attack doesn't guess anything. The attacker picks a session id, gets the victim's browser to use it, and waits for them to sign in. Getting the id into the browser is the hard part, and there are ways: a sign-in on a shared computer that the attacker used first, a cookie set by a page on a sibling subdomain, or a site that accepts session ids in links. Here, curl plays the victim:

    curl -b 'PHPSESSID=attacker-chosen-1' --data-urlencode 'password=correct horse battery staple' -d 'email=alice@example.com' http://localhost:8000/naive-login.php

    Same as before: -b sends a cookie with the request, here one the attacker made up.

    The naive page starts its session with PHP's defaults, so it accepted attacker-chosen-1, an id it never made, and signed Alice in under it. Now the attacker, who knows the id because they made it up, asks for the account page:

    curl -b 'PHPSESSID=attacker-chosen-1' http://localhost:8000/account.php

    "Signed in as alice@example.com." No password, no guessing. The session id is the key to the account, and the attacker chose the key.

    Fix It Count the Failures

    src/LoginLimiter.php counts failed sign-ins in the last fifteen minutes, by address and by IP:

    Two limits, because there are two kinds of attack. Ten failures for one address stops someone guessing at one account. Fifty from one IP, across any addresses, stops someone trying one common password against every account they can think of. The database is given to the class, not looked up inside it, so a test can hand it any connection it likes. The times come from MySQL's own clock, NOW(), for both the writing and the counting, so the two can't disagree.

    The Fixed Sign-In

    public/login.php:

  • The limit comes first. Over it, the answer is 429, before the password is even looked at, so the right password gets turned away too. If it didn't, the attacker would just keep going until the right one came back different.
  • Strict mode. start_session() refuses an id the server didn't make, and sends a fresh one instead.
  • A new id at sign-in. session_regenerate_id(true) swaps the id for a brand new one, and the true deletes the old session. Even an id that got past strict mode, or one an attacker read before sign-in, is worthless after it.
  • Every failure looks the same. Wrong address or wrong password: same words, and about the same time, because a password is checked against a dummy hash when there's no such user. Without that, a fast "no" would mean "no such account."
  • password_needs_rehash(). When PHP's default gets stronger, the hash is upgraded the next time the person signs in, the only moment you have their password.

    • Never trust input, as always: the address and password are checked for type before they go anywhere. Now run both attacks again. The guessing script:

    docker compose exec php php guess.php http://localhost:8000/login.php alice@example.com

    Ten 200s, then 429 Too Many Requests for the rest, the right password included: "Didn't get in." And for the next fifteen minutes, Alice's account turns away everyone, which is the trade a limit makes. Then the chosen id:

    curl -si -b 'PHPSESSID=attacker-chosen-2' --data-urlencode 'password=correct horse battery staple' -d 'email=alice@example.com' http://localhost:8000/login.php curl -b 'PHPSESSID=attacker-chosen-2' http://localhost:8000/account.php

    Wait fifteen minutes first, or docker compose down -v and up again, since Alice is still locked out. Then the sign-in works, but the Set-Cookie in the answer has an id the server made, and the attacker's id gets "Not signed in."

    Gotchas
  • A lockout is a weapon too. Anyone who knows Alice's address can keep her locked out by failing ten times every fifteen minutes. Keep the window short, tell her by email when it happens, and consider limits that slow down rather than stop.
  • The IP is whatever your server sees. Behind a proxy, it's the proxy, and fifty failures locks out the whole world. Here, even Docker shows it: the guessing script runs inside the container and arrives from 127.0.0.1, while your browser arrives from Docker's own network, so they're counted apart. See What's in the Middle.
  • The failures table grows. Delete rows older than the window on a schedule, as in the Cron Jobs project.
  • Regenerate at every change of privilege. Signing in, signing out, becoming an admin: each one gets a new session id.
    • One of my apps went live with a sign-in that could be guessed at forever. The limits came later, after the fact: ten failures per address and fifty per IP, in fifteen minutes. They're the same numbers this project uses.

    Keep a script like guess.php next to your tests and run it against every sign-in, reset and signup form you build. If it ever says "Got in," or never sees a 429, a limit is missing. It's the cheapest pen test you'll ever buy.

    Alice can sign in, safely. The first thing she'll want is to change something about herself, and that form is the next thing an attacker will aim at. Next: a profile page.
