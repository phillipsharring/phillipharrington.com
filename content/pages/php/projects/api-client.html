API Client Phillip Harrington

The REST API answered programs. This is the program on the other end: PHP code that calls someone else's API, for a payment, a map, a list of tasks, with a token that proves it's allowed to. You'll build a small client that does it carefully, and a pretend API to call, so it all runs on your machine.

The token is the whole story. It's a password, often for something that costs money or holds other people's data, and the easiest place to put it is right in the code. You'll do that first, then find it two ways without any access to the code's author: in the repository, and in the API's own log.

    • Build It Step 1: Somewhere to Keep the Token

    The token goes in a file called .env, next to the code, and .gitignore keeps that file out of the repository. What goes in git is an example with no real values, so the next person knows what to fill in:

    Copy .env.example to .env and put a long random token in it. php -r 'echo bin2hex(random_bytes(20));' makes one.

    Two containers: the pretend API, and one to run the client in. Compose reads .env by itself and passes the token into each as an environment variable, so it's never written in compose.yml either:

    Step 2: The Pretend API

    api/index.php stands in for someone else's service. It wants the token, and it misbehaves on purpose at a few addresses: /flaky is busy twice before it answers, /slow takes ten seconds, and /broken sends HTML where JSON should be.

    Step 3: The Client
  • It's handed the token. The class never reads a file or the environment. Whoever builds it decides where the token comes from, which makes it easy to test and impossible to hard-code by accident.
  • The token goes in a header, Authorization: Bearer ..., and only to HTTPS addresses, or to this machine's own containers.
  • #[\SensitiveParameter] tells PHP to hide the token in stack traces, which otherwise print every argument and are exactly the kind of thing that ends up in a log.
  • Timeouts. Without them, a slow API makes your code wait as long as it likes. Five seconds, then give up.
  • Retries, politely. A 429 or 503 means "not now." It waits as long as Retry-After asks, within a limit, and tries up to three times.
  • The answer is checked. Never trust input, and an API's response is input. It has to be JSON, and an object, or it's an error.
    • Step 4: The Script

    bin/tasks.php is where the token comes in: from the environment, and nowhere else. If it's missing, the script says so and stops.

    It also checks each task's shape before printing it. The API is someone else's code, and it can change without telling you.

    Step 5: Run It docker compose up -d api docker compose run --rm client php bin/tasks.php [x] 1 Write the API [ ] 2 Write the client [ ] 3 <script>alert(1)</script>

    In a terminal, that third title is harmless text. Put it in a web page, and it's the XSS from Comments: data from an API gets escaped like any other. Then the misbehaving addresses:

    docker compose run --rm client php bin/tasks.php /flaky docker compose run --rm client php bin/tasks.php /slow docker compose run --rm client php bin/tasks.php /broken

    The first succeeds on the third try. The second gives up after five seconds instead of ten. The third says the answer wasn't JSON. None of them print the token.

    Break It

    The client most people write first:

    For this part, set API_TOKEN in .env to the token in naive.php, as if someone had pasted the real one into the code, and restart the API with docker compose up -d api. It works:

    docker compose run --rm client php bin/naive.php

    Now be someone who has a copy of the repository: a new hire, a contractor, anyone the repository is ever shared with, or everyone, if it's public:

    grep -rn 'wnp_' .

    What's new:

    Search every file in every folder, not just one file. Show the line number of each match. Start in the folder you're in.

    There's the token, with a file name and line number. Committed once, it stays in the history even after it's deleted from the file. Automated scanners search public repositories for keys around the clock, and often find new ones within minutes of a push.

    Now be someone who can read the API's logs:

    docker compose logs api | grep api_key api-1 | [Fri Nov 27 20:38:06 2026] 172.19.0.3:47076 [200]: GET /tasks?api_key=wnp_live_7d3f9a2c8e1b4f6a

    Web servers log every URL, query string and all. So do proxies, CDNs and load balancers along the way. A token in a URL is a token in all of their logs.

    Fix It

    The real client fixes both. The token lives in .env, which never goes in git, and travels in a header, which servers don't log by default. Search for it:

    grep -rn 'wnp_' src bin/tasks.php docker compose logs api | grep -c "$(grep API_TOKEN .env | cut -d= -f2)"

    Only the new parts:

    Split each line at the = and keep the second piece: the token, without the API_TOKEN= in front. Run the command inside first, and put its output here, so grep -c counts the log lines with the real token in them.

    Nothing in the code, and the only log lines with the token are the naive client's. Then delete naive.php, and, because the token was in code and in a log, treat it as stolen: make a new one, and switch the old one off. With a real API, that's the only fix that counts.

    In 2016, attackers found login credentials for Uber's Amazon Web Services account in a private GitHub repository that Uber's engineers used. With them, they downloaded data on 57 million riders and drivers. A private repository is still a copy of your secrets on someone else's servers, readable by everyone who can read the code. Gotchas
  • Deleting a secret from git doesn't remove it. It's in the history, in every clone, and in every fork. Rotate it: make a new one and revoke the old.
  • A token in the browser is a public token. Anything in your JavaScript can be read by anyone who opens developer tools. Calls that need a secret go through your server, which keeps the secret and makes the call.
  • Debugging leaks secrets. var_dump($client), curl's verbose mode, a stack trace with arguments: each prints the token. Mark it #[\SensitiveParameter], and never log whole requests.
  • .env files are a start, not the finish. On a server, the file sits on disk, readable by anything that can read the folder. Bigger setups keep secrets in a secrets manager and load them into memory when the app starts.
  • Give each token the least it needs. A read-only token for a dashboard, a separate one for each program. When one leaks, you revoke one, and nothing else stops working.
    • One of my own apps kept its production secrets in .env files on the server's disk. We moved them into a secrets manager, loaded into memory when the app starts, and then rotated every one of them, because a secret that has sat in a file has to be assumed copied. Repeated side story: the secrets-off-the-disk story is also told in Configuration and the Environment. Keep one, make this a callback, or cut it.

    Run a secret scanner, like gitleaks, on your repository before you push, or in a git hook so it runs every time. It knows the shapes of hundreds of kinds of keys, and it's much cheaper to find one on your own machine than in someone else's scanner's results.
