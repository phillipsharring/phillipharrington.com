Checkout Phillip Harrington

The cart knows what someone wants. Checkout makes it an order: a fixed record of what was bought, at what price, by whom, that will still be true next year when the prices and the products have changed. Then it hands off to payment.

And the hand-off is the point of this project. The obvious checkout has a card number field. Yours won't. You'll build the obvious one first, take a test card through it, and then find that card number sitting in your log file and your database, where anyone who ever reads either can copy it.

    • Build It Step 1: Start from the Cart

    Copy the Shopping Cart project: its containers, composer.json and lock file, src/, the test, and both pages. The cart page gets one more line under the table, a link to /checkout.php. Then install:

    docker run --rm -v "$PWD":/app -w /app composer:2 composer install

    Same as ever: composer install fetches the exact versions in the lock file.

    Step 2: The Orders Tables

    Add these to the end of init.sql:

    CREATE TABLE orders ( id INT UNSIGNED AUTO_INCREMENT PRIMARY KEY, public_id CHAR(32) NOT NULL UNIQUE, checkout_token CHAR(64) NOT NULL UNIQUE, email VARCHAR(254) NOT NULL, name VARCHAR(100) NOT NULL, status VARCHAR(20) NOT NULL DEFAULT 'awaiting_payment', total_cents INT UNSIGNED NOT NULL, currency CHAR(3) NOT NULL DEFAULT 'usd', created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ); CREATE TABLE order_items ( order_id INT UNSIGNED NOT NULL, product_id INT UNSIGNED NOT NULL, name VARCHAR(200) NOT NULL, unit_cents INT UNSIGNED NOT NULL, quantity INT UNSIGNED NOT NULL, line_cents INT UNSIGNED NOT NULL, PRIMARY KEY (order_id, product_id), FOREIGN KEY (order_id) REFERENCES orders (id), FOREIGN KEY (product_id) REFERENCES products (id) );

    The whole file, with comments and one more table for Break It:

  • Order items copy the name and price. This is the place to break the "say it once" rule from Normalization on purpose: the order must say what was paid, even after the mug costs $16.
  • public_id is random. Order 41 in a URL invites someone to try 40.
  • checkout_token is unique. One per checkout form, so pressing the button twice can't make two orders.
  • There's no card column. There never will be.
    •  Step 3: Placing an Order

    src/Orders.php does it in one transaction. It locks the products' rows with FOR UPDATE, so two people buying the last mug take turns. It prices the cart fresh, refuses if anything ran out, writes the order and its items, takes the stock, and commits. If anything fails, it rolls back, and it's as if nothing happened.

    Problems the customer can fix are a CheckoutProblem, with a message meant for them. Anything else, like the database going away, is a different exception and stays out of the page.

    Step 4: The Checkout Page

    An email for the receipt, a name, and a button. And you couldn't possibly forget to never trust input. It reads those two fields and the tokens, and nothing else. If someone adds total_cents=1 or a card number to the request, nothing ever looks at it.

    Then the order page, which only the browser that placed the order can see. An order that isn't yours gets the same 404 as one that doesn't exist:

    Step 5: Run It docker compose up

    Add a few things at http://localhost:8000, open the cart, and check out. The order page shows what you bought and Status: awaiting payment. Press the browser's back button and Place Order again: you land on the same order, and there's still only one. Open the order's URL in a private window: 404.

    Break It

    Here's the checkout that asks for the card itself:

    Nothing in it is unusual. Logging every request while you build is a common habit, and saving the card "to charge it later" sounds reasonable. Pay with Stripe's best-known test card number, which is not a real card:

    curl -d email=bo@example.com -d card_number=4242424242424242 -d card_expiry=12/34 \ -d card_cvc=123 -d total_cents=2800 http://localhost:8000/naive-checkout.php

    Now be anyone who can read your log, or a backup of your database:

    grep 4242 logs/app.log docker compose exec db mysqldump --no-tablespaces -uapp -papp-password course | grep 4242

    Only the new parts:

    Search a file directly, rather than the output of another command. MySQL's backup tool. It prints the whole database as SQL: every table, every row. Leave out the tablespace details, which the app user isn't allowed to read. Without it, the dump stops with an error. [27-Nov-2026 20:30:00 UTC] checkout: {"email":"bo@example.com","card_number":"4242424242424242","card_expiry":"12\/34","card_cvc":"123","total_cents":"2800"} INSERT INTO `naive_orders` VALUES (1,'bo@example.com','4242424242424242','12/34','123',2800);

    Number, expiry and security code: everything needed to use the card, in two places, in plain text. Think about who can read those. Everyone with access to the server. Every backup, wherever it's copied. Whatever service you send logs to. And anyone who finds a hole like the one in Log Viewer. Card rules, the PCI DSS, forbid keeping the security code at all after a payment is authorized, and holding card numbers puts your whole server under a long list of audits.

    Fix It

    The fix isn't encrypting the column or filtering the log. It's not having the card. Look at the real checkout again: no card fields, nothing read but an email and a name. Send it the same card anyway:

    docker compose exec db mysqldump --no-tablespaces -uapp -papp-password course | grep -c 4242424242424242

    The only match is the naive table. The real orders have no card in them, because the real checkout never read one. The customer types their card on the payment provider's page, on the provider's servers, and your server is only ever told whether the payment worked. That's the next project. Then drop the naive_orders table, delete naive-checkout.php and logs/app.log.

    In late 2013, attackers got into the network of Target, the US retailer, using login details stolen from a heating and refrigeration contractor. They put malware on the checkout terminals in its stores, and over the holiday shopping weeks it collected the details of about 40 million cards as they were swiped. Card data is worth stealing wherever it passes through. The only safe amount to have is none. Gotchas
  • Logs collect what you'd never store on purpose. A debug line that dumps $_POST logs passwords and card numbers the moment a form has them. Log what happened, an order id and a status, not what was sent.
  • Taking stock at order time means giving it back. This checkout takes stock when the order is placed, before payment. Orders that are never paid hold stock forever, unless a cron job cancels old unpaid orders and returns it.
  • Double submits are normal. Slow connections, impatient fingers, the back button. Without the checkout token, each is a second order and a second charge.
  • Sequential ids leak more than you think. Two orders a week apart tell anyone how many orders you take a week. Random public ids say nothing.
  • Totals belong to the server. Shipping, tax, discounts: all computed from your data at the moment of the order, never accepted from the form.

    • Now and then, search your logs and database dumps for the shape of a card: grep -E '\b[0-9]{13,19}\b'. Most matches will be ids and timestamps, and that's fine. The one that's a card number is a bug you found before anyone else did.
