Caching Phillip Harrington

Every reader of the blog and its comments makes the database do the same work again. Most of the time, the answer hasn't changed since the last person asked. A cache keeps a copy of the answer, and hands out the copy until it's too old to trust.

You'll take a report that takes a full second to make, and cache it in two places: in files on your server, so the work happens once a minute instead of once a request; and in the browser, so a visitor who already has the latest copy is told so in a few bytes.

    In a project folder, src/report.php stands in for a big query or a call to another site. It always takes a second, and it stamps the time it was made, so you can see a copy when you get one:

    Step 2: The Cache

    src/FileCache.php is one class with one main method: remember() takes a key, how long to keep the value, and a function that makes it. If a fresh copy is on disk, it returns that. If not, it calls the function, saves the result, and returns it.

  • The key is hashed into the file name, so any key, with any characters, is a safe name.
  • The value is JSON, plain data. Never unserialize() a cache file: if anyone can ever write one, they can make it build objects in your code.
  • The write is atomic. It writes a temporary file, then renames it into place. A request that reads at the same moment gets the old file or the new one, never half of one.

    Step 3: The Page

    public/report.php uses both layers:

    Layer one is the file cache, with an X-Cache header saying whether this one was a hit. Layer two is HTTP. Cache-Control: public, max-age=60 tells the browser, and any cache in the middle, that this answer is the same for everyone and good for a minute. The ETag is a fingerprint of the body. When the minute is up, the browser asks again with If-None-Match and the fingerprint it has, and if nothing changed, the answer is 304 Not Modified, with no body at all.

    The town crier rang his bell and shouted it in the square every morning: never trust input, and that includes what goes into a cache key. The region must be one of four. If any string were allowed, anyone could ask for a million made-up regions, and you'd make a million slow reports and keep a million files.

    Step 4: Run It docker run --rm -it -p 8000:8000 -v "$PWD":/app -w /app php:8.4-cli php -S 0.0.0.0:8000 -t public

    The usual server: -p 8000:8000 connects port 8000 on your computer to the container's, where php -S is listening.

    From a second terminal, ask twice, and time it:

    curl -i -w '%{time_total}s\n' 'http://localhost:8000/report.php?region=north' curl -i -w '%{time_total}s\n' 'http://localhost:8000/report.php?region=north'

    The first says X-Cache: MISS and takes a second. The second says HIT, takes a few thousandths of one, and has the same made_at. Now copy the ETag from either, quotes and all, and ask the way a browser would:

    curl -i -H 'If-None-Match: "paste-the-etag-here"' 'http://localhost:8000/report.php?region=north'

    304 Not Modified, and nothing else. A minute later, the file cache expires, the report is made again with a new made_at, the fingerprint changes, and the same request gets the whole new report.

    To throw everything away at once, after a deploy or when the numbers behind the report change, clear-cache.php:

    docker run --rm -v "$PWD":/app -w /app php:8.4-cli php clear-cache.php

    "There are only two hard things in Computer Science: cache invalidation and naming things." The line is usually credited to Phil Karlton, a programmer at Netscape in the 1990s. Knowing when a copy is no longer true is the whole difficulty of caching; making the copy is the easy part. Gotchas
  • Never cache one person's page as public. A page with a name on it, a cart, an account: Cache-Control: private, no-store, so no cache in the middle keeps it and hands it to the next visitor.
  • The key must include everything the answer depends on. Language, currency, page number, whether someone is logged in. Leave one out, and the first visitor's version is everyone's.
  • When the cache expires, everyone misses at once. On a busy site, a hundred requests arrive in the same second, all find nothing, and all start the slow work together. A lock, so one request rebuilds while the others wait or use the old copy, fixes it.
  • A cache you can't clear is a bug you can't fix. Always have a way to throw it away, and keep max-age short for anything you might need to change in a hurry. Once a browser has a copy, you can't take it back.
  • Files are the simplest cache, not the fastest. With more than one server, each has its own files. A shared cache, like Redis or Memcached, is the next step, and the remember() idea stays the same.

    • Give stylesheets and scripts a fingerprint in their name, like style.3f9c.css, and cache them for a year. A change makes a new name, so browsers fetch it at once, and nothing ever has to expire. The images in the CMS project work the same way: a new upload is a new name.
