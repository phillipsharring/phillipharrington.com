Sending Email Phillip Harrington

Sooner or later your site has to send an email: a receipt, a password reset, a message from the contact form. The hard part isn't the code. It's testing it without sending real mail to real people while you get it wrong.

So this project starts with a mail catcher, Mailpit, in a container. It speaks SMTP like a real mail server, keeps everything you send it, and delivers none of it. Then you'll send it a proper email from PHP with Symfony Mailer: a plain text part, an HTML part, and a subject with an accent in it.

What You'll Use
  • Autoloading with Composer and PSR-4: installing the mailer.
  • Configuration and the Environment: where the mail server is.
  • Text and UTF-8: text that leaves your server.
  • Never Trust Input: an address is input.
  • What's in the Middle: two containers in one compose.yml.
    • Build It Install the Mailer

    In a new project folder, a .gitignore, then Symfony Mailer:

    docker run --rm -v "$PWD":/app -w /app composer:2 composer require symfony/mailer

    PHP has a built-in mail() function, but it hands the message to a sendmail program on the server, which containers don't have, and it leaves you writing headers by hand. A mailer library talks SMTP itself, builds the headers correctly, and encodes everything for the trip.

    Start the Mail Catcher

    compose.yml runs Mailpit, and a PHP container that knows where to find it:

    The PHP side reaches Mailpit at the name mailpit, on port 1025, its SMTP port. You reach its web page at http://localhost:8025. Start it:

    docker compose up -d mailpit Send One

    send.php sends a welcome email to the address you give it:

  • The address is checked first. filter_var() with FILTER_VALIDATE_EMAIL refuses anything that isn't one address. Never trust input, even on the command line: this same code will take its address from a form one day.
  • The mail server comes from the environment. Mailpit here; a real mail service on a live site. The code doesn't change, only the settings.
  • Two versions of the body. text() and html() go out together, and each reader's mail program shows the one it prefers.

    • Send it:

    docker compose run --rm php php send.php alice@example.com

    Open http://localhost:8025. There it is, in Mailpit's inbox, with the HTML version showing. Mailpit can also show you the raw message, exactly as it arrived. Part of it:

    Subject: Welcome to the =?utf-8?Q?caf=C3=A9?= MIME-Version: 1.0 Content-Type: multipart/alternative; boundary=yAK7a8_b --yAK7a8_b Content-Type: text/plain; charset=utf-8 Content-Transfer-Encoding: quoted-printable

    Email headers come from a time of plain ASCII, so the mailer encoded the é in the subject as its UTF-8 bytes, C3 A9, and labeled it utf-8. Every mail program decodes that back to "café." The body is labeled charset=utf-8 too. Leave the labels off, and someone's inbox shows cafÃ©.

    Now try to sneak a header in with the address, the way a form field could:

    docker compose run --rm php php send.php $'alice@example.com\nBcc: everyone@example.com' New here: In quotes with a dollar sign in front, this becomes a real line break, so the script gets an address with a second line tucked into it.

    Refused, and nothing sent. docker compose down stops Mailpit and throws its messages away.

    Ray Tomlinson sent the first email between two computers on the ARPANET in 1971. He needed a way to say "this person, at that machine," and picked the @ sign, because it was on the keyboard and almost never appeared in names. Gotchas
  • Header injection. Headers are lines, so a newline in anything that ends up in a header starts a new one. Glue a form's email field into a mail() header by hand, and someone can add a Bcc: with a thousand addresses, and your server sends their spam. Validate every address, and let a library build the headers.
  • Send from your own domain. Mail services check that a message claiming to be from example.com really came from a server example.com allows, using DNS records called SPF, DKIM and DMARC. Put a visitor's address in From, and the mail lands in spam or bounces. Use your own address in From, and theirs in Reply-To.
  • Sending is slow, and it fails. An SMTP conversation can take seconds, and the mail server can be down. A page that waits for it is a slow page, and one that crashes when it fails loses the message. The Queues project sends mail in the background.
  • Never point development at a real mail server. One test run against a copy of real data can email every customer you have. Development sends to a catcher, always, and test addresses use example.com, which is reserved for exactly this and can't receive mail.

    • Mail programs support far less HTML and CSS than browsers, and each supports a different part of it. Open a message in Mailpit and look at its HTML Check tab: it lists what in your message won't work in which mail programs, before a customer finds out for you.

    You can send mail. The obvious thing to do with that is let visitors send mail to you, which is where it gets interesting. Next: a contact form.
