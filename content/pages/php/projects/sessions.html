Sessions Phillip Harrington

The Cookies project kept a name in the browser, where the visitor could change it to anything. A session keeps the data on the server instead, and gives the browser only a long random id to bring back. The visitor can change the id, but all that gets them is someone else's nothing.

You'll build a shortlist: pick things from a list, remove them, start over. Along the way, a message that shows up exactly once after each change, a look at the file PHP keeps for each visitor, and a session started with the settings that every login in the next few projects depends on.

What You'll Use
  • Sessions: a cookie with an id, a file on the server.
  • Sessions and Cookie Flags: strict mode, HttpOnly, SameSite, Secure.
  • Request and Response: Post/Redirect/Get.
  • Never Trust Input: the item picked.
    •  Build It Starting a Session

    src/session.php has three small functions:

  • start_session() passes its settings straight to session_start(). use_strict_mode is the one people miss: with it off, which is PHP's default, a browser can show up with an id the server never made, and PHP will start a session under it. The Login Form project shows why that's dangerous. The cookie flags are the ones from the Cookies project.
  • flash() keeps a message for the next page and then forgets it. After a POST, you redirect; the message rides across the redirect in the session, is shown once, and is gone.
  • end_session() empties the data, deletes the cookie with the same settings it was set with, and destroys the file on the server. All three; any one alone leaves something behind.
    • The Shortlist

    public/index.php:

    The shortlist lives in $_SESSION['shortlist'], which PHP loads at session_start() and saves when the script ends. Every POST changes it, sets a flash message and redirects with a 303, so reloading never adds the same thing twice. The cave paintings at Lascaux show it clearly: never trust input. The item has to be a key in $fruit, and nothing else gets into the session.

    Run It

    This time, give the container a name, so you can look inside it in a moment:

    docker run --rm -it --name sessions -p 8000:8000 -v "$PWD":/app -w /app php:8.4-cli php -S 0.0.0.0:8000 -t public

    Open http://localhost:8000 and add Cherry. "Added Cherry." appears once; reload, and it's gone, but Cherry is still on the list. Open a private window: an empty shortlist, because it's a different browser with a different id. Now look at what the server keeps, from a second terminal:

    docker exec sessions sh -c 'ls /tmp/sess_*; cat /tmp/sess_*'

    One file per session, named after the id, holding your data:

    shortlist|a:1:{s:6:"cherry";b:1;}

    That's PHP's own format for $_SESSION: the key, a bar, and the value, serialized. Your browser has only the id in its cookie. Then try a made-up id:

    curl -si -b 'PHPSESSID=madeup123' http://localhost:8000

    Strict mode at work: there's no session called madeup123, so PHP ignores it and sends a fresh id of its own in Set-Cookie. Press Start over in the browser, and the cookie and the file are both gone.

    Gotchas
  • A session is locked while a request uses it. With the default file storage, PHP holds the session file locked from session_start() until the script ends, so a second request from the same browser waits. One slow page can stall every other tab. Call session_write_close() as soon as you're done changing the session.
  • Sessions expire on their own schedule. PHP cleans up files that haven't been touched for session.gc_maxlifetime seconds, 1440 by default, which is 24 minutes. And the cleanup runs only now and then, so "expired" is approximate. If a session must end at a certain time, store the time in it and check it yourself.
  • Files only work on one server. Behind a load balancer, the next request may go to a server that doesn't have the file. Several servers need shared session storage: a database or Redis.
  • The session id is the key to everything in it. Anyone who has it is that visitor, as far as your site knows. That's why it's HttpOnly, why it should be Secure, and why it changes at login.

    • Cookies are kept per host, not per port, so every app you run on localhost shares one PHPSESSID, and they log each other out. Give each app its own with session_name('shortlist_session') before session_start(), and the confusion stops. It also stops announcing to the world that your site runs PHP.
