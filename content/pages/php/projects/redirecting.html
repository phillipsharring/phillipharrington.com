Redirecting Phillip Harrington

A redirect is a response that says "not here, go there": a status code in the 300s and a Location header. You've used one already, after every form, so a reload doesn't post again. This project uses two more: one for a page that moved, and one for a settings form that sends you back to whatever page you were on.

That last one is where it goes wrong. "Back to where you were" means the request says where to go. Let it say anywhere, and your site becomes a link that starts on your domain and ends on someone else's. That's an open redirect, and you'll build one, use it the way a phisher would, then close it.

    The Naive Settings Page

    Each page links to the settings with ?back= saying where it is. The settings page keeps that in a hidden field, saves the theme, and sends you back. Build the naive version as public/naive-settings.php:

    docker run --rm -it -p 8000:8000 -v "$PWD":/app -w /app php:8.4-cli php -S 0.0.0.0:8000 -t public

    Check the moved page first:

    curl -i http://localhost:8000/about-us.php

    301 Moved Permanently and Location: /about.php. Then open http://localhost:8000/naive-settings.php?back=/about.php in the browser, pick Dark, and save. You land back on About. It works.

    Break It

    Pop quiz, no peeking: what's the rule? Never trust input, and back is input, from the query string and then the form. Give it someone else's site:

    curl -i -d 'theme=dark&back=https://evil.example/login' http://localhost:8000/naive-settings.php

    303 See Other, Location: https://evil.example/login. Your server just sent a visitor to a site you've never heard of.

    Here's how that gets used. An attacker sends this link to your users:

    http://localhost:8000/naive-settings.php?back=https://evil.example/login

    It's your domain, so it looks safe, and anyone who checks the link before clicking sees your name. They land on your real settings page, change something, press Save, and your site sends them to evil.example/login: a copy of your sign-in page that says "your session expired." They type their password into the attacker's form. Spam filters and link checkers also tend to trust a link to a known domain, which is why phishers go looking for open redirects on big sites.

    Fix It

    The settings page only ever needs to send people somewhere on your own site. So the fix is local_path(), from the helpers: the value must start with one /, which makes it a path on this site, and it's refused if it's anything sneakier:

  • //evil.example starts with a slash, but two slashes make it a scheme-relative URL: "the same scheme, on this other host."
  • /\evil.example looks like a path, but browsers treat a backslash in a URL as a forward slash, so it's //evil.example again.
  • A tab or newline, as in /%09/evil.example: browsers strip them out of URLs, which can leave two slashes behind.

    • Anything refused gets the fallback, the home page. Notice what local_path() doesn't do: it doesn't try to spot bad sites. It accepts one narrow shape and turns down everything else. Make the fixed page, public/settings.php:

    It checks back twice: when the page is shown, so the hidden field never holds a foreign address, and when the form is posted, because the posted value is input too. Attack it:

    curl -i -d 'theme=dark&back=https://evil.example/login' http://localhost:8000/settings.php curl -i -d 'theme=dark&back=//evil.example/login' http://localhost:8000/settings.php curl -i --data-urlencode 'back=/\evil.example/login' -d 'theme=dark' http://localhost:8000/settings.php

    All three: Location: /. A real path, like /about.php?x=1, still goes through.

    Gotchas
  • Pick the right code. 301 is permanent, and browsers cache it, sometimes for a very long time, so get it right or use 302 while you're testing. 303 after a form means "now GET this." 307 and 308 are the temporary and permanent ones that keep the method, so a POST stays a POST.
  • Checking the host with string tricks fails. str_starts_with($url, 'https://example.com') also matches https://example.com.evil.example. If you must allow other sites, parse the URL and compare the host against an allow list, exactly.
  • Redirecting to javascript:. If the same value is ever used as a link's href instead of a header, javascript:alert(1) runs a script when it's clicked. A path that has to start with / can't be that.
  • Newlines in a header. PHP's header() refuses a value with a newline in it, so back can't add headers of its own. Other languages and old PHP weren't always so careful.

    • When you remember where someone was, keep only the path and query, like /about.php?tab=2, never a whole URL with a scheme and host. A value that never had a host in it can't be pointed at someone else's, and it keeps working when your domain changes.
