Logging Phillip Harrington

The server's access log says a request came in. PHP's error log says something broke. Neither says what your app was doing: who searched for what, which page threw, what it was in the middle of. That's your own log, and it's the first thing you'll open when someone says "it didn't work."

You'll build a small app that writes every event to logs/app.log with Monolog, the logging library most PHP projects use. Each line gets a level and a request id, and anything that blows up is logged in detail while the visitor gets a polite apology with the id in it.

What You'll Use
  • Access and Error Logs and Errors and the Error Log: the logs you already have.
  • Autoloading with Composer and PSR-4: installing Monolog.
  • Exceptions and Try/Catch: the ones nobody caught.
  • Reading Logs: tail -f.

    Then ask Composer for Monolog:

    docker run --rm -v "$PWD":/app -w /app composer:2 composer require monolog/monolog:^3

    That writes composer.json and composer.lock, which you commit, and vendor/, which you don't. Anyone who clones the project runs composer install to get the same versions.

    Set Up the Logger

    src/bootstrap.php builds the logger once, for every request:

  • A logger and a handler. The Logger is what your code talks to; the StreamHandler decides where lines go, here a file outside public. Level::Debug means "write everything." On a live site you'd raise it to Info or Warning.
  • A request id. Sixteen random hex characters, made fresh for each request. A processor adds it to every line, and the X-Request-Id header sends it back, so one request's lines can be picked out of thousands.
  • An exception handler. set_exception_handler() runs when an exception goes uncaught. It logs the details and shows the visitor a 500 with the id, and nothing about your code.

    public/index.php is a tiny app with a home page, a search, a page that always fails, and a 404 for everything else, each logging what happened:

    The levels come from PSR-3, the shared logging standard: debug, info, notice, warning, error, critical, alert and emergency. Pick by what you'd want to happen: info is "for the record," warning is "look at this sometime," error is "look at this today."

    Run It docker run --rm -it -p 8000:8000 -v "$PWD":/app -w /app php:8.4-cli php -S 0.0.0.0:8000 -t public

    In a second terminal, watch the log, and in a third, make some requests:

    tail -f logs/app.log curl http://localhost:8000/ curl 'http://localhost:8000/search?q=caf%C3%A9' curl -i http://localhost:8000/boom

    Each one appears in the log as it happens:

    [2026-11-27T19:55:15.771326+00:00] app.INFO: Home page viewed [] {"request_id":"c52c43924e91238e"} [2026-11-27T19:55:15.784126+00:00] app.INFO: Search {"q":"café"} {"request_id":"6635c799a37a7ac5"} [2026-11-27T19:55:15.794508+00:00] app.ERROR: Uncaught exception {"exception":"[object] (RuntimeException(code: 0): The /boom page always fails, on purpose. at /app/public/index.php:26)"} {"request_id":"7ebd291ca018709a"}

    The search arrived as caf%C3%A9, the URL encoding of the UTF-8 bytes, and the log has café, because PHP decoded it and Monolog writes UTF-8. The /boom request got "Something went wrong" and an id; the log has the class, the message, the file and the line, under the same id.

    Gotchas
  • Input goes in the context, never in the message. A log is one event per line, so a newline is a new event. Never trust input: write a search to a log by hand, with error_log() or file_put_contents(), and a visitor can send ?q=x%0A[2026-01-01T00:00:00] app.CRITICAL: ... and add a fake line of their own. Monolog's line format turns newlines into spaces, and in the context it encodes the value as JSON, so the newline is written as \n, harmless and labeled. Try it, and look at the log.
  • Never log secrets. Passwords, session ids, API keys, card numbers, whole request bodies. Logs get copied, shipped to other services and read by people who shouldn't see any of those. Log that a login failed, and for which address, never what was typed.
  • Logs fill disks. A busy site writes a lot, forever. Rotate them: Monolog's RotatingFileHandler starts a new file each day and keeps a set number, or let the system's logrotate do it.
  • No stack trace by default. The line format keeps each event on one line, so it leaves the trace off. Call includeStacktraces() on a LineFormatter when you want it, and accept the extra lines.
    • Sailors once measured a ship's speed by throwing a piece of wood, the log, over the stern on a line knotted at regular intervals, and counting the knots that ran out in a set time. That's where "knots" comes from, too. The results went in the logbook, which became the record of everything that happened on board.

    When someone reports an error, ask for the id on the error page, then grep the log for it. You get every line that request wrote, in order, and nothing from the thousands of requests around it. A support ticket that comes with an id is ten minutes of work instead of an afternoon.
