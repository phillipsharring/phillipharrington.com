Protected Page Phillip Harrington

Sessions ended with "the session can remember who the visitor is." This project does that: a members' page that strangers can't see. A stranger who asks for it is sent to sign in, then straight back to the page they wanted. A member sees it. And everyone gets the same vague answer when a sign-in fails.

For now there's one member, in a settings file, so the project can be about the guard and not the database. The Signup Form and Login Form projects put members in MySQL and add the defenses a real sign-in needs.

What You'll Use
  • Sessions: the careful session_start().
  • Passwords: password_hash() and Nothing Else: password_verify().
  • Redirecting: local_path() for "where to next."
  • Expressive HTTP Response Codes, and When Not to Be: one answer for every failed sign-in.
  • What's in the Middle: keeping caches away from private pages.

    The Guard

    src/auth.php holds everything about who's signed in:

  • require_login() is the guard. If nobody is signed in, it redirects to the sign-in page, with the page they wanted in ?next=, and redirect() ends the script, so nothing below it runs. If someone is, it marks the response private, no-store and hands back who it is.
  • sign_in() changes the session id with session_regenerate_id(true) before it records who signed in. The id from before sign-in might be known to someone else; the one after is brand new. The Login Form project attacks a sign-in that skips this.
  • sign_out() clears all of it: the data, the cookie and the file on the server, as in the Sessions project.

    A 303 to the sign-in page, and an empty body. Nothing of the page left the server.

    A Guard That Forgot

    Now the mistake that guard exists to prevent. header('Location: ...') only adds a header; the script keeps going, and prints the page after it. Make public/forgot-exit.php, a guard that forgot to stop:

    Open it in the browser, and you're sent to the sign-in page, as you should be. Then ask the way a script would, without following redirects:

    curl -i http://localhost:8000/forgot-exit.php

    A redirect to the sign-in page, and right under it, "The meeting is Thursday at 7." The browser followed the redirect and never showed you the body; curl shows you everything the server sent. That's why redirect() is declared to return never, and PHP holds it to that.

    Gotchas
  • A redirect without exit hands out the page anyway. The guard that forgot, above, looks fine in a browser and gives everything away to curl. Make every redirect go through a function that ends the script.
  • Every protected page needs the guard. It's one line, which makes it one line to forget on the page you add next month. Once a site has more than a few of these, put the check in one place that every request goes through, as in Middleware and Pipelines.
  • Signing out is a POST. A sign-out link can be followed by anything: a browser prefetching links, or an image tag on someone else's page pointing at it. A button in a form can't be triggered that casually.
  • This sign-in can be guessed at forever. Nothing stops a script from trying a million passwords. The Login Form project adds the limits.

    • The browser hides what a page sends before it redirects. Every time you protect a page, curl -i it without signing in, and look at the body. It should be empty. If anything is there, the guard is in the wrong place, or it doesn't stop.

    One member in a file doesn't scale. Members belong in a database, and so does almost everything else a site keeps. Before that, the classic way a database gets broken into. Next: something database-y.
