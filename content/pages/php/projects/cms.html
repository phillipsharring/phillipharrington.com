Content Management System Phillip Harrington

Translation kept product names in a table so someone could change them without touching code. A content management system, a CMS, does that for whole pages. You'll build a small one: each page is a row in MySQL, an address like /about shows it, and an admin form behind a login edits it, picture and all.

The picture is the dangerous part. An upload form lets strangers put files on your server, and the naive version lets them run those files as code. You'll build that version, use it to run your own PHP on the server, and then build the one that can't be used that way.

    Step 5: The Upload Checks

    Never trust input, and an upload is input from top to bottom. The file name in $_FILES is whatever the client said. So is the type. The only thing you can examine is the bytes, and even those were chosen by someone else. src/uploads.php does five things:

    1. Checks that the upload arrived, and isn't too big.
    2. Asks finfo what the bytes are, ignoring the type the browser sent.
    3. Asks getimagesize() to read it as an image, and checks the two agree.
    4. Allows only PNG, JPEG and WebP.
    5. Moves it into storage/uploads, outside the web root, under a random name with an extension picked from the type it really is.
    Step 6: The Admin

    public/admin.php lists the pages, shows a form to edit one or make a new one, and saves it. enctype="multipart/form-data" on the form is what lets it carry a file. After a save, it redirects, so a reload doesn't send the form again.

    Break It

    Here's the uploader most people write first:

    It keeps the file's own name, drops it in the web root, and never looks at it. Make a file that isn't a picture at all:

    printf '<?php echo "ran: " . (6 * 7);' > shell.php curl -F 'image=@shell.php' http://localhost:8000/upload-naive.php curl http://localhost:8000/uploads/shell.php

    From File Uploads: -F 'image=@shell.php' sends the file as the form's image field.

    The last line prints ran: 42. That multiplication happened on your server. Anything PHP can do, the uploader can now do: read .env, query the database, delete files. A file like this is called a web shell, and an upload form like this one is how a lot of them get onto servers.

    Checking the type isn't enough on its own. Make a tiny real PNG, one dot, put the same line of PHP on the end, and name it .php:

    echo 'iVBORw0KGgoAAAANSUhEUgAAAAEAAAABCAQAAAC1HAwCAAAAC0lEQVR42mNkYAAAAAYAAjCB0C8AAAAASUVORK5CYII=' | base64 -d > dot.png cat dot.png shell.php > sneaky.php curl -F 'image=@sneaky.php' http://localhost:8000/upload-naive.php curl -s http://localhost:8000/uploads/sneaky.php | tail -c 20

    New here:

    Print the two files one after the other. Given more than one file, cat joins them. Save the joined result as a new file.

    ran: 42 again. The file is a valid image; image viewers open it, and getimagesize() would accept it. It's also valid PHP, because PHP runs whatever is between <?php and the end, and passes the rest through as output.

    Fix It

    Now send both to the real admin form, at /admin.php:

  • shell.php gets PNG, JPEG or WebP images only. Rename it cat.png first and it still does; the name was never asked.
  • sneaky.php gets in: the bytes really are a PNG. But it's stored as 3f9c...e1.png, in a folder no URL reaches, and image.php sends it as image/png. Ask for it, and the PHP comes back as bytes. It never runs.

    • That's the fix in layers. Check what the bytes are, so most junk never lands. Choose the name and extension yourself, so nothing arrives as .php. Keep uploads out of the web root, so even a file that slips through can't be visited, let alone run. Then delete upload-naive.php and anything in public/uploads.

    Gotchas
  • A blocked-extensions list loses. Refuse .php, and someone tries .phtml, .php5, .PHP, or .php.jpg on a server set up to run anything with .php in the name. Allow a short list of types, and pick the extension yourself.
  • Too big can mean empty. If a POST is bigger than PHP's post_max_size, PHP throws the whole body away: $_POST and $_FILES are both empty, so here the token check fails first. A file over upload_max_filesize arrives with an error code instead. Both settings live in php.ini.
  • Images can carry more than a picture. Photos straight off a phone often hold the location they were taken in. Resizing every upload, with GD or Imagick, makes a fresh file and drops the rest along the way.
  • SVG is a picture made of code. An SVG file can contain JavaScript, and opened directly it runs on your site. Leave it off the allow list unless you clean it first.
  • An image served from your site is served as your site. That's why image.php sends X-Content-Type-Options: nosniff: without it, some browsers look at a file's bytes and decide for themselves what it is.

    • When uploads have to live in the web root, tell the web server never to run PHP there. In nginx, a location block for the uploads folder that doesn't pass to PHP-FPM; in Apache, a <Directory> block that does the same. It's one more layer, and it catches the day someone else adds an uploader without reading this page.
