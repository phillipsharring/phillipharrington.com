Log Viewer Phillip Harrington

HTTP Authentication put a page behind a password. Here's something worth hiding: your logs. You'll build a staff page that lists the files in a logs folder and shows the last lines of whichever one you pick. Handy on a server where you can't easily get a terminal.

It's also the classic place for a hole called path traversal. A page that takes a file name from the URL will open any file it's told to, unless you stop it. You'll build it the naive way first, read the server's secrets with it, and then fix it.

    Step 2: The Viewer

    public/index.php does four things, top to bottom:

  • Asks for a login, with the function from HTTP Authentication.
  • Builds its allow list: the names of the .log files actually in the folder.
  • Checks the requested name against that list, exactly, and answers 404 for anything else.
  • Shows the last lines, read one at a time with SplFileObject so a gigabyte log doesn't have to fit in memory, and escapes every one.

    • Start it:

    docker run --rm -it -p 8000:8000 -v "$PWD":/app -w /app php:8.4-cli php -S 0.0.0.0:8000 -t public

    Open http://localhost:8000, log in as editor with correct horse battery staple, and click access.log. The script in the third line shows up as text. It never runs, because every line went through htmlspecialchars(). Add &lines=2 to the URL, and you get just the last two.

    Break It

    Here's the viewer most people write first. It takes the name from the query string, sticks it on the end of the logs folder, and sends the file:

    It works for the files you meant:

    curl 'http://localhost:8000/naive.php?file=app.log'

    Now ask for a name with ../ in it. In a path, .. means "the folder above," so logs/../.env is the .env next to logs:

    curl 'http://localhost:8000/naive.php?file=../.env'

    Out comes API_KEY="not-a-real-key-but-pretend-it-is". Keep climbing, and it's any file the server can read:

    curl 'http://localhost:8000/naive.php?file=../../../../../etc/passwd' curl 'http://localhost:8000/naive.php?file=../users.php'

    The machine's list of accounts, and your password hashes, as plain text, with no login asked. Putting the secrets outside the web root didn't help, because the hole is in your code, and your code can read everything.

    Fix It

    The fix is already in index.php, and it's the one that hasn't changed since the pyramids went up: never trust input, so don't use the name to build a path at all. Use it to pick from a list you made yourself. Try the same attacks on the real viewer:

    curl -u 'editor:correct horse battery staple' 'http://localhost:8000/?file=../.env' curl -u 'editor:correct horse battery staple' 'http://localhost:8000/?file=app.log/../../.env'

    Both get No such log. and a 404. Neither is in the list, and nothing else matters. Encoded dots, %2e%2e%2f, get the same answer: PHP decodes the query string before your code sees it, and ../.env still isn't on the list.

    Then delete naive.php. A broken file left in the web root is still a broken file in the web root.

    In 2000, Microsoft's IIS web server had a traversal hole of exactly this kind. It checked request paths for ../, but a slash written in an unusual, overlong UTF-8 form got past the check and was decoded into a real slash afterward. The Nimda worm used it in 2001 to spread. The lesson stuck: check the name you'll actually use, after all decoding, or better, don't build paths from input at all. Gotchas
  • Checking for ../ isn't enough. There are too many ways to write it: encoded, doubled, with backslashes on Windows, through a symbolic link. An allow list doesn't care how the attack is spelled.
  • When you can't list the files ahead of time, check where the path lands. realpath() resolves every .. and link into the real location; then make sure it starts with your folder plus a slash, and refuse it otherwise.
  • basename() helps, but read what it does. It keeps only the part after the last slash, so ../.env becomes .env. That stops the climbing, but a .env inside the logs folder would still be served. The allow list is stricter.
  • Logs are full of input. User agents, URLs, form fields that got logged: anyone can put HTML there. Show a log in a page, and you escape it like anything else. A viewer that doesn't is an XSS hole aimed at your own staff.
  • Logs hold secrets too. Email addresses, tokens in URLs, the odd password someone typed in the wrong field. A log viewer is a staff-only page, behind a login, over HTTPS, with no cache keeping a copy.

    • grep -c '\.\./' access.log on a public site's access log often finds someone trying this already. Scanners try ../ on every parameter they see. Knowing it's being tried makes it much easier to remember to test for it.
