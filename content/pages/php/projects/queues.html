Queues Phillip Harrington

Cron runs work on a clock. Some work is set off by a visitor instead: a signup that needs a welcome email, an upload that needs resizing, an order that needs a receipt. Doing it during the request makes the visitor wait, and if the mail server is slow or down, the signup fails along with the email.

A queue splits that in two. The page writes down what needs doing and answers at once. A separate program, a worker, takes jobs off the list and does them, retrying the ones that fail. You'll build both, with the queue in a MySQL table, then switch off the mail server and watch the jobs wait for it.

    src/Database.php makes the connection, as before, now as a class. The queue itself, src/Queue.php, has four methods:

    reserve() is the one that matters. Two workers asking at the same moment must never get the same job, or someone gets two welcome emails. Inside a transaction, FOR UPDATE locks the row it finds, and SKIP LOCKED makes any other worker pass over locked rows and take the next one instead of waiting. The row is marked running, the transaction ends, and the job is this worker's alone.

    It also takes back jobs that have been running for more than ten minutes. That's a worker that crashed, or a server that restarted, halfway through. Without this, those jobs would sit there forever.

    Step 5: The Worker

    A loop: take a job, run its handler, mark it done. When there's nothing to do, wait a second and ask again. When a job throws, catch it, so one bad job can never stop the worker, and put it back with a delay that grows each time: 30 seconds after the first failure, 60 after the second. After the third, it's marked failed, with the last error kept, for a person to look at.

    Step 6: The Signup Page

    It checks the address, pushes a job, and redirects. It never talks to the mail server. However slow or broken mail gets, signing up stays fast.

    Step 7: Run It docker compose up

    Sign up at http://localhost:8000, then open http://localhost:8025: the welcome email is there, sent by the worker a moment after the page had already answered. Now break the mail server, from a second terminal:

    docker compose stop mailpit

    Sign up again. The page is exactly as fast, and says thanks. In the first terminal, the worker reports failed, attempt 1 ... Now queued. Start Mailpit again within the next half minute or so:

    docker compose start mailpit

    At the next attempt, the email goes out. Nobody lost a signup because the mail server had a bad minute. To see the table as it goes:

    docker compose exec db mysql -uapp -papp app -e 'SELECT id, status, attempts, available_at, last_error FROM jobs'

    And to retry jobs that gave up, once you've fixed whatever was wrong, put them back in the queue:

    UPDATE jobs SET status = 'queued', attempts = 0, available_at = NOW() WHERE status = 'failed';

    The mathematics of waiting in line started with telephones. In 1909, Agner Krarup Erlang, an engineer at the Copenhagen Telephone Company, published a paper on how calls arrive at an exchange, and went on to work out how many lines an exchange needs so that few callers have to wait. Queueing theory grew from it, and the unit of telephone traffic is still called the erlang. Gotchas
  • Jobs can run more than once. A worker can send the email and crash before marking the job done, and the job gets taken back and sent again. Make jobs safe to repeat where you can, for example by recording that the welcome email went out and checking before sending.
  • Put ids in the payload, not whole records. A job may run minutes after it was queued. Carry the user's id and look them up when the job runs, so it works with what's true now, not what was true then.
  • A long-running worker keeps old code. PHP loads your files once, when the worker starts. After a deploy, restart the workers, or they'll go on running yesterday's code.
  • Workers leak, slowly. A script meant to run for a second can run for weeks as a worker, and small leaks add up. Many setups let a worker stop itself after a few hundred jobs, and let something like Compose's restart: unless-stopped start a fresh one.
  • Failed jobs are a to-do list. Look at them. A pile of failed rows that nobody reads is the queue's version of an error log nobody reads.

    • A worker that can stop when the queue is empty, like this one's --until-empty, is easy to test, easy to run by hand while you debug, and can be run from cron every minute on a server where you can't keep a process running. One flag, and three problems go away.
