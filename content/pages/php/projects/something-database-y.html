Something Database-y Phillip Harrington

Every project so far has kept its data in files. From here on, most of it goes in a database. This one is a small library catalog: a table of books, a search box, and a choice of how to sort the results. It's the most ordinary database page there is.

It's also where SQL injection lives. Build the search by pasting what someone typed into the SQL, and they're no longer searching your database; they're writing queries for it. You'll do exactly that, use it to read a table the page never meant to show, then fix it for good.

    Break It

    Search for a single quote. In a second terminal:

    curl "http://localhost:8000/naive.php?q=%27" Fatal error: Uncaught PDOException: SQLSTATE[42000]: Syntax error or access violation: 1064 You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near '%' ORDER BY title' at line 1

    Your quote ended the string in the SQL early, and MySQL choked on what was left. That error is the attacker's first clue: what you type becomes SQL. So type SQL. This search ends the string, adds a second SELECT with three columns to match the first, and turns the rest of the original query into a comment with --:

    curl -G --data-urlencode "q=' UNION SELECT email, password_hash, 0 FROM users -- " http://localhost:8000/naive.php

    New here:

    The short way to write --get: put the data in the URL's query string and send a GET, not a POST.

    The query MySQL ran was this:

    SELECT title, author, year FROM books WHERE title LIKE '%' UNION SELECT email, password_hash, 0 FROM users -- %' ORDER BY title

    And the page shows every book, then:

    <tr><td>admin@example.com</td><td>$2y$12$V7YmYyHThlzBFxJ50/IaK.NxdbvumRLq0B6SP9OoE1Zzm8.NxxwmS</td><td>0</td></tr> <tr><td>librarian@example.com</td><td>$2y$12$pXjePItb5XPrLW28lDK/tuRc/2Xpp/fA7bfvOj.qZhL05PItyzNSG</td><td>0</td></tr>

    Every user's address and password hash, in a table labeled "Title, Author, Year." The page never asked for the users table; the visitor did. With a little more typing, the same hole reads any table this database user can see. The sort is a second hole of the same kind: ?sort= goes into ORDER BY untouched. (This setup refuses a second statement after a ;, so a DROP TABLE fails here. A UNION doesn't need one.)

    Never trust input. The fix is not to look for quotes, or the word UNION, and strip them. That's a deny list, and every deny list for SQL has been beaten. The fix is to never let input become SQL at all.

    Fix It

    The fixed search, public/index.php:

  • A prepared statement. The SQL has a placeholder, :pattern, and the search is sent separately, as a value. MySQL never reads it as SQL, whatever it contains. A quote is a quote; UNION is five letters.
  • Wildcards escaped. Inside a LIKE pattern, % means "anything" and _ means "any one character," even in a placeholder value. addcslashes() puts a backslash before each, so a search for % finds titles with a percent sign, not every title.
  • Sorting from an allow list. Placeholders hold values, never column names or SQL keywords, so ORDER BY :sort can't work. The request picks a key in $sorts, and the SQL comes from your array. Anything else gets title.
  • Errors stay private. If the query fails, the details go to the error log and the visitor gets one polite sentence.

    • Send it the same attack:

    curl -G --data-urlencode "q=' UNION SELECT email, password_hash, 0 FROM users -- " http://localhost:8000/

    "No books match." It searched for a book whose title contains that whole sentence, and there isn't one. The quote alone: "No books match." A %: "No books match." And "mise" still finds Les Misérables. docker compose down -v stops everything and deletes the database; the next up builds it fresh.

    Gotchas
  • Escaping is not the fix. Functions that add backslashes before quotes depend on the connection's character set, and there have been ways around them. Prepared statements don't escape anything; the value never becomes part of the SQL text. Use them for every value, every time, even ones you think are safe.
  • Your own data is input too. A value that came out of the database was put there by someone. If it ever goes back into a query, it goes in as a placeholder value, like anything else.
  • Give the app's database user only what it needs. A user that can only SELECT from the tables it uses turns a hole like this from "read everything, drop everything" into much less. The app user here can do anything to its database, which is fine for your laptop and nowhere else.
  • A hash is not a password, but it's still a leak. Those bcrypt hashes are slow to crack, which buys time. Weak passwords still fall, and the addresses alone are worth something to a spammer.
    • In 2007, the webcomic xkcd ran a strip called "Exploits of a Mom": a school calls a mother because her son's name, Robert'); DROP TABLE Students;--, has wiped out the year's student records. She calls him Little Bobby Tables, and hopes they've learned to sanitize their database inputs. Programmers have used the name ever since.

    Grep your project for query strings with a variable in them: grep -rnE 'SELECT.*\$|WHERE.*\$' src public. Every hit is either a placeholder you forgot, or a column name that needs an allow list. It's a crude check, and it finds real holes in about a minute.
