Cookies Phillip Harrington

A page that remembers you: type your name once, and from then on it says "Welcome back, Alice." The name lives in a cookie, in your browser, and comes back with every request. It takes about ten lines to build, and the ten-line version has two problems, one in how the cookie is set and one in how it's read.

You'll build it naive, attack it with a planted cookie and a line of JavaScript, then fix it the way every cookie on a real site should be set: through one function that never forgets the flags.

What You'll Use
  • Cookies: setcookie() and $_COOKIE.
  • Sessions and Cookie Flags: HttpOnly, Secure and SameSite.
  • Never Trust Input and XSS and Escaping Output: a cookie is input.
  • Request and Response: Post/Redirect/Get.
    • Build It

    Make a project folder with a public folder in it. Build the naive version first, as public/naive.php, so you can keep it beside the fixed one and compare:

    When the form is posted, it sets the cookie and redirects with a 303, so a reload doesn't post again. On every other visit, it reads the cookie and says hello. Run it:

    docker run --rm -it -p 8000:8000 -v "$PWD":/app -w /app php:8.4-cli php -S 0.0.0.0:8000 -t public

    Open http://localhost:8000/naive.php, type your name, and press the button. Welcome back. Close the tab, come back, and it still knows you. It works.

    New to Docker or the terminal? Tools has the setup.

    Break It

    First, look at the cookie it sets:

    curl -si -d 'name=Alice' http://localhost:8000/naive.php

    The header is Set-Cookie: name=Alice, and nothing else. No HttpOnly, so any JavaScript in the page can read it. No SameSite, so you're relying on each browser's default for whether other sites can make it send the cookie. No Secure, so on a live site it would also go over plain HTTP, readable and changeable by anyone in between. And no expiry, so it's a session cookie, gone whenever the browser decides the session is over.

    See the first one for yourself. On the naive page, open your browser's developer tools, go to the Console, and type:

    document.cookie

    It answers "name=Alice". Any script that runs in the page can do the same and send the answer anywhere: an injected script, or a third-party script that was compromised. Here it's a name. On most sites, it's the cookie that keeps someone logged in.

    Now the second problem, and you can probably finish this sentence for me. Never trust input, and a cookie is input: it's whatever the browser sends, and anything that can write to the browser's cookies can put anything there. A page on a sibling subdomain can set a cookie for the whole domain, and so can anyone in the middle of a plain HTTP request. Plant one:

    curl -b 'name=<script>alert(document.cookie)</script>' http://localhost:8000/naive.php

    The page comes back with this in it:

    <p>Welcome back, <script>alert(document.cookie)</script>.</p>

    In a browser, that's a script running on your site, reading the cookies the first problem left readable. The two bugs help each other.

    Fix It

    First, the setting. Every cookie the site sets goes through one function, so none can go out without its flags. Make src/cookies.php:

  • httponly: JavaScript can't read it. document.cookie no longer shows it.
  • samesite set to Lax: the browser sends it when someone follows a link to your site, but not with forms other sites post to you or requests they make in the background. Set it yourself rather than trusting each browser's default.
  • secure, whenever the request came over HTTPS: the browser will only send it back over HTTPS. On http://localhost it's left off, so the cookie still works while you develop.
  • expires: a real lifetime, so "remember me" means 30 days, not "until the browser feels like it."

    • cookie_text() is the reading half. It treats the cookie like any other input: it has to be a string, valid UTF-8, and short enough. Anything else counts as no cookie at all.

    Then the page, public/index.php:

    It checks the name before it goes into a cookie, reads it back through cookie_text(), and escapes it with htmlspecialchars() on the way out, every time. There's a Forget me button too, which deletes the cookie.

    Run the same attacks against the fixed page:

    curl -si -d 'name=Alice' http://localhost:8000/ curl -b 'name=<script>alert(document.cookie)</script>' http://localhost:8000/

    The cookie now goes out with everything it needs:

    Set-Cookie: name=Alice; expires=Sun, 27 Dec 2026 19:56:52 GMT; Max-Age=2592000; path=/; HttpOnly; SameSite=Lax

    And the planted script comes back as text: Welcome back, &lt;script&gt;alert(document.cookie)&lt;/script&gt;. In the browser, set your name on the fixed page and type document.cookie in the console again: "". The cookie is still there, in the Application or Storage tab, and still sent with every request. Scripts just can't see it.

    Gotchas
  • Deleting a cookie needs the same path and domain. A cookie set with path=/ is only deleted by one with path=/. That's why forget_cookie() repeats the settings. PHP sends the deletion as name=deleted with a date in 1970, and the browser throws it away.
  • HttpOnly doesn't make a cookie secret. It hides it from JavaScript, not from the person whose browser it's in. They can still see it and change it in their developer tools. The value is input, every time.
  • Not every cookie needs HttpOnly. A theme setting your own JavaScript reads is fine without it. Anything that identifies a person never is.
  • Secure has to know about HTTPS. Behind a CDN or proxy, PHP may only ever see plain HTTP, so is_https() says no forever. Have the proxy tell you, with X-Forwarded-Proto, and trust that header only from your own proxy, as in What's in the Middle.
    • One of my apps sent its login cookies without the Secure flag for months. The code set it whenever the request was HTTPS, which looked right. But the app sat behind a CDN that handled HTTPS and talked to the server over plain HTTP, so PHP never saw $_SERVER['HTTPS'] set, and never added the flag. Repeated side story: the months-without-Secure cookie story is also told in Sessions and Cookie Flags. Keep one, make this a callback, or cut it.

    Every so often, curl -sI your live login page and read the Set-Cookie lines. You're looking for three words: Secure, HttpOnly and SameSite. It takes ten seconds, and it catches exactly the kind of mistake that looks right in the code.
