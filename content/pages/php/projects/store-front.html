Store Front Phillip Harrington

The newsletter told people about things. Now build the shop window they arrive at: a list of products from the database, filtered by category, sorted by name or price, with a page for each one. This and the next three projects build an online shop in order: store front, shopping cart, checkout, and taking a payment.

Nothing here is new on its own. What matters is getting two habits right before money is involved: prices stored as whole cents, and every choice in the URL checked against a list of your own.

    •  Build It Step 1: The Products

    The containers, Dockerfile and src/db.php are the ones from Translation, with the database called store. The tables:

    price_cents is an integer. A float can't hold most decimal fractions exactly, and in PHP 0.1 + 0.2 === 0.3 is false. That's fine for a temperature and wrong for money, where every cent has to add up. Whole cents in an integer add up exactly, always.

    active hides a product without deleting it. Old orders still point at old products, so products are almost never really deleted.

    Step 2: Showing a Price

    Cents stay cents until the last moment, when they become text. intdiv() and % split them into dollars and cents without a float in sight.

    Step 3: The Queries

    The category goes into the query as a placeholder, like everything else. The sort can't: ORDER BY takes a column, and placeholders only stand for values. So the visitor picks a key, like price-low, and the SQL comes from SORTS, written by you. Whatever they send, only your own SQL reaches the database.

    Step 4: The Pages

    Never trust input. Both choices in the query string are checked against lists before they're used: the category against the categories in the database, the sort against the keys of SORTS. Anything else, including an array where a string should be, quietly becomes the default. The links are built with http_build_query(), which encodes each value, and then escaped for the page.

    Step 5: Run It docker compose up

    Open http://localhost:8000. Click a category, sort by price, open a product. The white mug is sold out; the old sticker isn't there at all. Then try the things a visitor shouldn't be able to do:

    curl 'http://localhost:8000/?sort=price_cents%3B%20DROP%20TABLE%20products' curl -i http://localhost:8000/products/old-sticker

    The first is sorted by name, and the table is fine: the sort wasn't one of ours, so it was never used. The second is a 404: an inactive product doesn't exist, as far as visitors know.

    In 1982, the Vancouver Stock Exchange started a new index at 1,000. Every time it was recalculated, thousands of times a day, the result was cut off to three decimal places instead of rounded, and the lost fractions piled up. By late 1983 the index stood near 520, when it should have been above 1,000. Once it was recalculated correctly, it nearly doubled overnight. Small errors in arithmetic don't stay small when they're repeated. Gotchas
  • Not every currency has cents. The Japanese yen has no minor unit, and a few currencies have three decimal places. If you sell in more than one currency, store the amount in the currency's smallest unit, and the currency's code beside it.
  • Sold out today, back next week. Hide inactive products, but keep sold-out ones visible and marked. A product page that suddenly 404s loses its place in search results.
  • A price on the page is a fact about now. Prices change. Anything that records a sale, starting with the checkout two projects from now, must copy the price at that moment, not point at the current one.
  • Filters multiply pages. Every combination of category and sort is a URL search engines may crawl. A <link rel="canonical"> pointing at the plain version tells them which one counts.

    • Call it price_cents, not price. Then $product['price_cents'] / 100 looks as wrong as it is, and nobody ever has to guess whether 1400 means fourteen dollars or fourteen hundred. timeout_seconds, size_bytes and weight_grams work the same way.
