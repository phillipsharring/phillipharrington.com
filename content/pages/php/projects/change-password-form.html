Change Password Form Phillip Harrington

Of every form on a site, this is the one that hands over the account. Whoever changes the password owns it, and the real owner is locked out. So the question it has to answer isn't "is someone signed in?" It's "is this really the person whose account it is, on purpose, right now?"

You'll build the naive version, take it over from another site with the trick from the Profile Page, then fix it with the CSRF token, plus one more check that no token can replace: asking for the current password again. And when the password does change, every other place the account is signed in gets signed out.

  • Login Form: the sign-in and the failure limits.

    Break It

    Make attacker/index.html, the other site, with a form that submits itself to your naive form:

    In the same browser, still signed in, visit http://localhost:8001. It lands on your account page: "Password changed." Open a private window and try to sign in as Alice with her password: "Wrong email or password." Try the attacker knows this one: you're in. Alice visited a page about wallpapers, and lost her account.

    The other site doesn't even have to be involved. Anyone who gets a few minutes with a signed-in session, at a laptop left open, on a shared computer, or with a session cookie copied by malware, can do the same with the form itself. The naive form trusts the session completely, and a session is a much weaker proof than a password.

    Fix It

    The fixed form, public/change-password.php:

    It asks four questions, in order:

    1. Did this come from our own form? csrf_check(), exactly as in the Profile Page. The attacker's page stops here, with a 403.
    2. Is it really them? The current password, checked with password_verify(). Someone at an unlocked laptop has the session and the token, but not the password. And a wrong guess counts as a failed sign-in, through the same LoginLimiter, so this form can't become a place to guess the password without limits.
    3. Is the new one any good? The Signup Form's rules: at least 12 characters, no more than 72 bytes, typed the same twice, and not the one they already have.
    4. Then change it, and sign everyone else out. The UPDATE adds one to session_version. This session gets a new id, the new version and a fresh token, and stays signed in. Every other session still remembers the old version, so the guard signs it out on its next request.

    That last step matters more than it looks. People change their password because they think someone else has it. If changing it leaves the other person signed in, it hasn't helped. Never trust input runs through all of it, as it has since roughly the Bronze Age: three fields, each checked for type before anything else.

    Point the attacker's form at /change-password.php and visit http://localhost:8001 again: "That form had expired," a 403, and nothing changed. Then use the real form, from two browsers signed in as Alice: change the password in one, and the other is sent to the sign-in page the next time it loads anything.

    Gotchas
  • Changing the email address needs the same care. Whoever controls the address controls the password reset, so a form that changes it is a change password form in disguise. Ask for the password there too.
  • Tell them it happened. Send an email to the account's address after any password change: "If this wasn't you, here's what to do." It's the one warning an attacker can't switch off, because they can't change the address the warning goes to without the password.
  • Don't send the new password anywhere. Not in the email, not in a log, not in an error message. The flash message says "changed," and nothing else.
  • Help the password manager. The hidden username field with autocomplete="username", and current-password and new-password on the right fields, let a password manager fill in the old one, offer a strong new one, and save it under the right account.

    • The session_version column is the cheapest "sign out everywhere" there is: one number in the users table, one in the session, compared on every request. Add one to it from an admin page, and you can sign a compromised account out of every device at once, without knowing where its sessions are stored.

    Every sign-in so far has been a form, a session and a cookie, all built by you. HTTP has a way to ask for a password that's older than all of it, built into every browser. Next: HTTP authentication.
