PHP on the Command Line Phillip Harrington

Caching ended with a script you ran in a terminal. Every docker run ... php in this course has been PHP on the command line, with no web server anywhere. A lot of real PHP runs this way: imports, reports, cleanups, queue workers, anything that happens without a visitor waiting for a page.

You'll build a small tool that prints the most common words in some text. It's a normal citizen of the terminal: it takes options, reads files or whatever is piped into it, prints results where other tools can use them, prints errors somewhere else, and says with its exit code whether it worked.

    \p{L} is any letter in any language and \p{N} any digit, and the u at the end tells PCRE the text is UTF-8. Without it, é is two bytes that aren't letters, and café splits in half.

    Step 2: The Command

    bin/top-words.php is the part that talks to the terminal:

  • PHP_SAPI says how PHP is running: cli in a terminal. If the script is ever reached through a web server, it refuses.
  • getopt() reads the options, and its third argument says where they stop, so everything after is a file name. $argv is the whole command line as an array.
  • STDIN, STDOUT and STDERR are streams PHP opens for you. Results go to STDOUT; complaints go to STDERR, so they show on the screen but don't end up in a file or a pipe with the results.
  • exit() with a number is the exit code: 0 for success, anything else for failure. Here, 1 means a file couldn't be read, and 2 means the options were wrong, which is a common habit among command-line tools.

    • Some sample.txt to count:

    Step 3: Run It docker run --rm -v "$PWD":/app -w /app php:8.4-cli php bin/top-words.php --top=5 sample.txt

    New here:

    An option for your own script, in the same shape real tools use. PHP passes it along like any other argument, and the script reads it. The file to count, as a plain argument after the options. 5 café 5 the 2 at 2 coffee 1 any

    Café, CAFÉ and café counted as one word. Now pipe text in instead of naming a file. Docker needs -i to pass the pipe through:

    cat sample.txt | docker run --rm -i -v "$PWD":/app -w /app php:8.4-cli php bin/top-words.php --top=3 --min-length=4

    Then get it wrong, and check the exit code with echo $? right after:

    docker run --rm -v "$PWD":/app -w /app php:8.4-cli php bin/top-words.php nope.txt; echo $? docker run --rm -v "$PWD":/app -w /app php:8.4-cli php bin/top-words.php --top=lots; echo $?

    Can't read nope.txt and 1; then the usage and 2. Add > out.txt to the first one, and the message still shows on your screen, while out.txt stays empty: the error went to STDERR, and only STDOUT was sent to the file.

    Never trust input on the command line either. A person typing --top=lots is the friendly case. The unfriendly one is a script that builds the command from something a visitor sent, which is why every option is checked here, and why your PHP should never pass input to a shell command without escapeshellarg().

    New to Docker or the terminal? Tools has the setup.

    Standard input, output and error come from Unix, built at Bell Labs in the early 1970s. Doug McIlroy pushed for pipes, so the output of one small program could flow straight into the next, and they arrived in 1973. In 1978 he wrote down the habits that grew from them, starting with "Make each program do one thing well" and "Expect the output of every program to become the input to another, as yet unknown, program." A tool that prints plain lines to STDOUT can be piped into sort, head or grep without knowing they exist. Gotchas
  • The command line has its own php.ini. Settings like memory and time limits can differ from the web's, and max_execution_time is 0, no limit, on the command line. A script that's fine in a terminal can be cut off on a web page, and the other way around.
  • There's no $_GET, no headers, no session. Input is $argv, STDIN and the environment, with getenv().
  • Keep command-line scripts out of the web root. The PHP_SAPI check is a backstop. A bin folder next to public, never inside it, is the real protection.
  • A shebang line only works in a terminal. #!/usr/bin/env php on the first line lets you run a script as ./top-words.php. Only the command line skips that line, though: through a web server, it's printed as text, and with declare(strict_types=1) after it, the script won't even compile.
  • Exit codes are how scripts talk to scripts. Cron, deploy tools and CI all check them. A script that prints "failed" and exits 0 has succeeded, as far as they know.

    • Any command-line script that changes things, deletes rows, sends mail or moves files, should take a --dry-run that prints what it would do and does nothing. Write that path first. You'll use it every time you run the script against real data for the first time.
