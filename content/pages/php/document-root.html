Document Root Phillip Harrington

At the end of every chain in What's in the Middle is a server with a folder. Ask for /images/logo.png, and it goes looking for a file called logo.png in an images folder inside that folder. That folder is the document root, also called the web root, and the most important thing about it is what you leave out of it.

What's a Document Root?

The one folder a web server hands out. Everything inside it can be reached by a URL. Nothing outside it can. The server's settings name it: root in nginx, DocumentRoot in Apache, and -t for PHP's built-in server.

Project Root and Web Root

A project is much more than what visitors should see. So most projects, and all of yours, keep the web root as one small folder inside the project, usually called public:

my-project/ the project root: never served .env settings and secrets composer.json src/ your code vendor/ other people's code logs/ public/ the web root: the only folder served index.php style.css

Visitors can reach index.php and style.css, and nothing else. Your code can still use everything, because PHP reads files from disk, not through URLs: index.php reaches up a folder for the settings, and the world can't.

On a lot of shared hosting, the web root is a folder called public_html. The name comes from early web servers, which let every user on a shared machine publish pages from a public_html folder in their home directory, at addresses like /~yourname/. The tilde URLs mostly went away. The folder name stuck. How It Works
  1. The request asks for a path, like /style.css.
  2. The server joins it to the web root: public/style.css. It refuses any path that tries to climb out with ...
  3. If the file exists, the server sends it, with a content type picked from its extension. A .php file is different: the server runs it and sends what it printed. How that works is two lessons from now.
  4. If the path is a folder, it looks for an index file, index.php or index.html.
  5. If there's nothing there, it's a 404. Or, in most PHP apps, the server hands every unknown path to index.php, and your code decides what it means.
Try It

Then a public folder, and in it, index.php:

From the project folder, start the server with -t public, so only public is served:

docker run --rm -it -p 8000:8000 -v "$PWD":/app -w /app php:8.4-cli php -S 0.0.0.0:8000 -t public

Only the new part:

The document root: serve files from the public folder only, not the folder you started in.

Open http://localhost:8000: the greeting, read from the .env the page can't serve. Now go after the secret:

curl http://localhost:8000/.env curl --path-as-is http://localhost:8000/../.env

New here:

Send the path exactly as typed. Without it, curl tidies away the /../ before the request ever leaves.

Both just get the greeting again. There's no .env in public, and the server won't climb out of it, so it hands the unknown path to index.php, like the apps in step five. Stop the server, and start it the wrong way, without -t public, so the whole project is the web root:

docker run --rm -it -p 8000:8000 -v "$PWD":/app -w /app php:8.4-cli php -S 0.0.0.0:8000

Then ask again:

curl http://localhost:8000/.env

There's your API key, for anyone who asks. That's the whole lesson in one command.

In PHP
  • __DIR__ is the folder the current file is in, and dirname(__DIR__) is the one above it: from public/index.php, that's the project root.
  • Build paths from those, like dirname(__DIR__) . '/.env', never from the current directory, which can be anything.
  • $_SERVER['DOCUMENT_ROOT'] is the web root the server is using.
    •  Gotchas
  • Deploying the project folder as the web root. The Try It's second run, for real: .env, the .git folder with your whole history, logs, and everything else become downloads. Automated scanners ask every site for /.env and /.git/ all day long.
  • Leftovers in the web root. A config.php.bak or an editor's swap file isn't a .php file, so the server sends it as text, source and all.
  • Directory listings. With an index file missing, some servers list the folder's contents instead. Turn that off.
  • Uploads in the web root. If someone can upload a file into a served folder and then visit it, they can upload a .php file and run it. Never trust input, and uploads are input. File Uploads, in Security, is about this.
    • Macs leave a hidden .DS_Store file in folders, listing the names of the files around it. For a while, one sat in this site's web root, and anyone asking for /.DS_Store got a list of my file names. The deploy deletes them now, before anything uploads.

    After every new setup or deploy, ask your live site for the things that should never be served: curl -I on /.env, /.git/HEAD, and /composer.json. If any of them answers with your file, fix it before someone else's scanner finds it.
