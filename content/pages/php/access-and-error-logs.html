Access and Error Logs Phillip Harrington

Document Root ended with the server answering requests for files that were there and files that weren't. It also wrote every one of them down. Servers keep two kinds of diary: an access log, with a line for every request, and an error log, for when something goes wrong. When a page breaks, they're the first place to look, and very often the only place that knows what happened.

What's an Access Log?

A text file with one line per request, written by the web server. Most servers use the same layout, called the combined log format:

192.0.2.10 - - [27/Nov/2026:19:51:44 +0000] "GET /nope HTTP/1.1" 404 24 "-" "curl/8.7.1"
  • 192.0.2.10: the address that connected.
  • - -: two old fields that are almost always empty: an identity nobody sends, and the user name from HTTP authentication.
  • [27/Nov/2026:19:51:44 +0000]: when, with the time zone.
  • "GET /nope HTTP/1.1": the request line, exactly as it arrived: method, path and query string, and protocol.
  • 404: the status code sent back. From Request and Response.
  • 24: the size of the response body, in bytes.
  • "-": the Referer header, the page that linked here, or - for none.
  • "curl/8.7.1": the User-Agent header.
    •  The header that says which page linked to this one is spelled Referer, with one R in the middle. It was misspelled in the original proposal, and the misspelling went into the HTTP/1.0 specification in 1996. By then the software already used it, so it stayed. Log formats call the field "referer" too. What's an Error Log?

    A file of things that went wrong, each with a time and a level: notice, warning, error. There are usually two, and it matters which is which.

    The Server's Error Log

    The web server's own problems: a file it couldn't open, a setting it didn't like, or, most often, PHP not answering. When a visitor gets a 502 or 504 from What's in the Middle, this is where the server says why.

    PHP's Error Log

    Your code's problems: warnings, errors, and anything you write there yourself. Two settings decide where they go. display_errors prints them into the page, for the visitor to see. log_errors writes them to the file named in error_log. On your own computer, display is handy. On a live server, display goes off and logging goes on, always: error messages show file paths and pieces of your code to anyone who can trigger one.

    The official PHP Docker images ship with no settings file at all, so PHP's defaults apply: errors displayed, and not logged. The Try It turns that around. The full story of errors is in Errors and the Error Log.

    How It Works
    1. A request reaches the web server.
    2. The server hands it to PHP. If it can't reach PHP, it writes that to its error log and answers with a 502 or 504.
    3. PHP runs your code. Any warning or error goes to PHP's error log, or into the page, depending on those two settings.
    4. The server sends the response.
    5. Then it writes the access log line. It waits until the end because that's when it knows the status code and the size.

    So one bad request can leave a line in three files. The time is what ties them together: find the request in the access log, then look at the same second in the error logs.

    In PHP
  • error_log('Something happened') writes your own line to PHP's error log.
  • display_errors: show errors in the page. On while you work, off on a live server.
  • log_errors: write errors to the log. On, everywhere.
  • error_log, the setting: the file to write to. With none set, PHP writes to the web server's error log, or to the terminal, which in Docker means docker logs.
  • ini_get('error_log') tells you where it's going right now.
    •  Gotchas
  • Everything in a log line came from outside. The path, the query string, the user agent and the referrer are whatever the client sent. Never trust input, and a log is full of it: escape it before you show a log in a page, and don't let it into anything that runs. The Never Trust Input lesson, and the Log Viewer project, come back to this.
  • Query strings are logged. Anything in a URL ends up in access logs, yours and every server's in the middle. Never put a password or a key in one. That's one more reason forms that send secrets use POST.
  • Logs grow until the disk is full. Servers rotate them: every day or week, the log is renamed, compressed, and eventually deleted, and a new one starts. On Linux, a tool called logrotate does it. A full disk takes the whole site down with it.
  • The address may not be the visitor's. Behind a proxy or a CDN, the access log records the last hop, the same problem as REMOTE_ADDR in What's in the Middle. Servers can be told to log X-Forwarded-For instead.
  • Logs hold personal data. Addresses, and anything you write about your users. In some places, privacy law counts an IP address as personal data. Keep logs only as long as you need them, and never write a password to one.

    • In the combined format, the status code is the ninth thing on each line. This counts them, most common first:

    awk '{print $9}' logs/access.log | sort | uniq -c | sort -rn Go through the log line by line and print only the ninth word of each, the status code. The pipe: hand the output of one command to the next, instead of to the screen. Sort the lines, so the same codes end up together. Squash each run of identical lines into one, with a count in front. Sort again, by that count (-n), biggest first (-r).

    A pile of 404s you didn't expect is a broken link or a scanner. Any 500s at all are a reason to open the error log.
