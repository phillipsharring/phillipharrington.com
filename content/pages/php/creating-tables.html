Creating Tables Phillip Harrington

In SQL, the books table was already there. Someone had to decide what it holds: which columns, what type each one is, which ones can be empty. That decision is a CREATE TABLE statement, and it's worth getting right, because the database enforces it on every row, forever, whatever your code forgets to check.

What's CREATE TABLE?

The statement that makes a table, naming each column and its rules:

CREATE TABLE `books` ( `id` INT UNSIGNED NOT NULL AUTO_INCREMENT, `title` VARCHAR(200) NOT NULL, PRIMARY KEY (`id`) );

Each line is a column: a name, a type, then any rules. The last line says which column identifies a row.

Types
  • Whole numbers: INT (up to about 2.1 billion, or 4.2 billion when it's UNSIGNED, which means no negatives), BIGINT for more, SMALLINT and TINYINT for less. MySQL has no true yes-or-no type: BOOLEAN is a TINYINT holding 0 or 1.
  • Exact decimals: DECIMAL(10, 2), ten digits with two after the point. Never FLOAT or DOUBLE for money; they're approximate, the same way they are in PHP. Or do what Types of Types says and count cents in an INT.
  • Text: VARCHAR(200) holds up to 200 characters, and TEXT holds a lot more, for things like the body of a post.
  • Dates and times: DATE for a day, DATETIME for a moment.
    • Rules
  • NOT NULL: the column must have a value. Without it, a column accepts NULL, which means "no value," and every column does, unless you say otherwise.
  • DEFAULT: the value it gets when an insert doesn't give one. DEFAULT CURRENT_TIMESTAMP stamps the time a row was made.
  • AUTO_INCREMENT: the database numbers the rows itself, 1, 2, 3, so every row gets an id without your code picking one.
  • PRIMARY KEY: the column that tells one row from every other. There's one per table, it can't repeat, and it can't be NULL. The next lesson is about keys.
    • Old schemas are full of VARCHAR(255), whatever the column holds. Until MySQL 5.0.3, in 2005, 255 characters was as long as a VARCHAR could be, so it was the safe choice. The limit is long gone. The habit isn't. Pick a length that fits the thing: 200 for a title is plenty. How It Works
    1. You run CREATE TABLE once, when the table is made.
    2. The database stores the definition, and from then on checks every insert and update against it.
    3. A value that breaks a rule (too long, a NULL where one isn't allowed, a number out of range) is refused with an error, and the row isn't written.
    4. Changing the table later takes another statement, ALTER TABLE. That's what Migrations, at the end of this section, are for.

    Step three depends on strict mode, which MySQL 8.4 turns on by default. Without it, MySQL cuts the value down to fit, writes it anyway, and leaves you a warning nobody reads.

    Try It

    Make a table with rules, then break every one of them. Use the same compose.yml and Dockerfile as in SQL:

    This time, init.sql is the table definition itself:

    Start the database and open the mysql command:

    docker compose up -d --wait db docker compose exec db mysql -u app -papp-password course

    Look at what you made:

    DESCRIBE `books`;

    Add a book, giving only the columns that need a value, and look at the row:

    INSERT INTO `books` (`title`, `format`, `price_cents`) VALUES ('Frankenstein', 'paperback', 1299); SELECT * FROM `books`;

    The database filled in the rest: an id of 1, NULL for the pages and the date, and the time for created_at. Now break the rules, one at a time:

    INSERT INTO `books` (`title`, `format`, `price_cents`) VALUES (NULL, 'paperback', 1299); INSERT INTO `books` (`title`, `format`, `price_cents`) VALUES ('Dracula', 'paperback', -1); INSERT INTO `books` (`title`, `format`, `price_cents`) VALUES (REPEAT('x', 201), 'paperback', 1299);

    Three refusals: Column 'title' cannot be null, Out of range value for column 'price_cents', and Data too long for column 'title'. Now one the table can't catch:

    INSERT INTO `books` (`title`, `format`, `price_cents`) VALUES ('Dracula', 'scroll', 999);

    Accepted. format is just text, and the database has no idea which formats you sell. That list belongs in your code. Type exit, and make add-book.php, which keeps the list and checks everything else too:

    It needs the db.php from SQL, too:

    Add a book the right way, and then the wrong way:

    docker compose run --rm php php add-book.php 'Jane Eyre' ebook 899 docker compose run --rm php php add-book.php 'Jane Eyre' scroll 8.99

    The first is added, with the next id. The second is refused twice, for the format and for the price, before the database ever sees it. Every space traveler knows to never trust input: the table's rules are the last line of defense, and your code is the first. docker compose down -v when you're done.

    In PHP
  • in_array($value, $allowed, true) is the allow list for a column like format, the same check as the shirt sizes in Forms.
  • filter_var($value, FILTER_VALIDATE_INT) for anything bound for an integer column, with min_range and max_range to match the column.
  • mb_strlen(), not strlen(), to check text against a VARCHAR length. The length counts characters, and strlen() counts bytes. Text and UTF-8 has the difference.
  • A PDOException is what PHP gets when the table refuses a row. Most of the time it means a check is missing from your code: catch the problem before the database has to.
    • Gotchas
  • Don't use ENUM columns. MySQL has an ENUM type that takes only listed values, and it looks like the answer for format. It isn't. Adding a value means altering the table. It sorts by the order of the list, not alphabetically. And with strict mode off, a value that isn't on the list is stored as an empty string. Use a VARCHAR, and keep the list in your code.
  • A decimal in an integer column is rounded, not refused. Give price_cents the value 12.99, and strict mode or not, it stores 13, without an error. That's why add-book.php checks for a whole number itself.
  • Strict mode can be off. It's the default, but some hosts and old configurations turn it off, and then too-long text is cut short and out-of-range numbers are clamped, silently. SELECT @@sql_mode; should include STRICT_TRANS_TABLES.
  • TIMESTAMP ends in 2038. MySQL has a TIMESTAMP type, too, and it can't hold a moment after January 19, 2038. It also converts to and from the connection's time zone as it goes. Use DATETIME, and store times in UTC.
  • Columns accept NULL unless you say they don't. Leave off NOT NULL, and every query that touches the column has to handle "no value." Make a column nullable only when "no value" means something, like a book whose page count you don't know yet.

    • SHOW CREATE TABLE `books`\G prints the exact statement that would make the table as it stands now, defaults and all, including the ones you didn't write. It's the quickest way to see what a table really is, and to copy it somewhere else.
