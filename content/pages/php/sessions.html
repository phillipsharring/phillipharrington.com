Sessions Phillip Harrington

HTTP forgets you the moment it answers. Every request arrives alone, with no memory of the one before. Cookies gave the browser a way to remember a little. Sessions put the memory on the server instead, where the visitor can't read it or change it, and hand the browser only a ticket.

What's a Session?

Two things. A cookie, usually called PHPSESSID, holding a long random id. And a file on the server, named after that id, holding whatever you saved for that visitor. The cookie is the ticket. The file is the coat.

The id is all the browser ever has. What's in the session, a user id, a cart, a message to show on the next page, stays on the server.

How It Works
  1. Your code calls session_start().
  2. PHP looks for the session cookie in the request. If there isn't one, it makes a new random id and sends it back in a Set-Cookie header.
  3. It opens the file for that id, reads it, and puts what's in it into $_SESSION, an ordinary array.
  4. Your code reads and changes $_SESSION.
  5. When the script ends, PHP writes $_SESSION back to the file.

The id arrives in a cookie, and a cookie is input. Anyone can send any id they like. What they can't do is change what's in the file, so the data you put in a session is yours. The id is the only part to doubt.

Try It

A page that counts your visits. In a folder, make index.php:

Start it with a name this time, --name sessions, so you can look inside the container in a minute:

docker run --rm -it --name sessions -p 8000:8000 -v "$PWD":/app -w /app php:8.4-cli php -S 0.0.0.0:8000

Only the new part:

Give the container a name, so other commands can point at it. Without one, Docker makes up a name.

Open http://localhost:8000 and reload a few times: the count goes up. From a second terminal, do it with curl, keeping the cookie in a jar file between requests:

curl -c jar.txt -b jar.txt http://localhost:8000 curl -c jar.txt -b jar.txt http://localhost:8000

New here:

Save any cookies the server sets into jar.txt, a file curl keeps them in. Send the cookies from that file. Given a file name instead of name=value, -b reads the file.

Visit number 2. Now look at the other half of the session, the file on the server. Use the id the page printed:

docker exec sessions cat /tmp/sess_YOUR_ID Run a command inside the running container named sessions. Print a file's contents. The session file, inside the container. Put your id in place of YOUR_ID.

visits|i:2;: your count, in PHP's own format, on the server's disk. The cookie in jar.txt holds only the id. Now send an id you made up:

curl -i -b 'PHPSESSID=madeup' http://localhost:8000

Visit number 1, and a fresh id in Set-Cookie. That's use_strict_mode at work: PHP refuses an id it didn't make. It's carved over the door of every server room: never trust input, not even the ticket.

In PHP
  • session_start() before you use $_SESSION, and before any output, because it may send a header. It takes an array of settings, as in the example.
  • $_SESSION is an array: set, read and unset() keys like any other.
  • session_regenerate_id(true) gives the visitor a new id and throws the old one away. Do it whenever someone logs in.
  • session_destroy() deletes the file. To log someone out, empty $_SESSION, destroy the session, and expire the cookie.
  • session_write_close() saves and closes the session early, once you're done changing it.
    • Gotchas
  • The id is the key to the account. Whoever has it is that visitor, as far as PHP knows. That's why the cookie needs its flags, and why a login gets a new id. Sessions and Cookie Flags, in Security, is all about it.
  • Sessions lock. While one request has a visitor's session open, the next request from the same visitor waits for it. A slow page can stall every other tab they have open. Call session_write_close() when you're done writing.
  • Files live on one server. Behind a load balancer, from What's in the Middle, the next request may land on a server that has never heard of you. Busy sites keep sessions in a database or a cache like Redis instead.
  • Sessions expire. By default PHP treats a session as garbage after 1,440 seconds, 24 minutes, without a visit, and cleans it up when it gets around to it. Someone who walks away from a long form can come back to nothing.
    • Browsers have always been able to refuse cookies, so PHP once offered a fallback: it could add the session id to every link on the page, as ?PHPSESSID=.... The id then showed up in bookmarks, in server logs, and in the Referer header sent to other sites, and anyone who saw it could use it. The setting is off by default now, and should stay that way.

    Put the user's id in the session, not their whole row from the database. Look the rest up on each request. When they change their name, or you lock their account, the next page knows, instead of trusting a copy from an hour ago.

    session_start() has to come before any output, because headers go first. PHP can hold output back so you can change your mind. Next: output buffering.
