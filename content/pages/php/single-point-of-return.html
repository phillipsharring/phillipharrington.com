Single Point of Return Phillip Harrington

Return Early said: answer the stopping cases first and get out. There's an older rule that sounds like its opposite: a function gets one return, at the end. I wrote code that way, strictly, for a few years, and I still think the rule is mostly right. It just needs one exception, and the exception is Return Early.

What's a Single Point of Return?

A function with exactly one way out. It works out its answer into a variable, and the last line returns that variable. However the answer was reached, it leaves through the same door.

What It's Good For
  • One place to look. Every answer the function gives passes one line. Log it there, or put a breakpoint there, and you see all of them.
  • One place to finish. Anything that has to happen after the work, logging, closing, counting, happens once, above the return, and can't be skipped.
  • A result with a name. return $cents; says what comes back. Six scattered returns of six expressions don't.
    • The rule comes from structured programming, in the 1960s and 70s. In languages of that era, a subroutine could be entered at more than one point, and FORTRAN even let a subroutine return to different places in its caller. "Single entry, single exit" meant one way in and one way back. Edsger Dijkstra's 1968 letter "Go To Statement Considered Harmful" was part of the same push: code you can follow from top to bottom. How It Works

    Here's how the two rules share a function:

    1. Guards at the top return early. Bad arguments, nothing to do, not allowed. They leave before any work starts, so there's nothing to finish and nothing to log.
    2. The work builds one result. One variable, named for what it is, set and adjusted as the function goes.
    3. Anything that has to happen to every result happens next, once.
    4. One return, at the bottom.

    Early returns are for the cases where the function never really started. A single return is for everything that did. What you avoid is the third kind: a return in the middle of the work, which leaves without doing the finishing.

    In PHP
  • match is a single point of return in one expression: $cents = match (true) { ... }; picks one result, then you carry on.
  • ?? and += let you start with a default and adjust it, like after/shipping.php, instead of branching to separate returns.
  • try/finally runs the finally block on every way out, returns and exceptions included. It's the tool for cleanup when a function can't be shaped this way.
  • A void function has no result, so the rule there is simply: no return in the middle of the work.
    • Gotchas
  • Strict single return brings back the arrow. With no early returns at all, every guard becomes an if wrapping the rest, and you're back to the nesting from Return Early. That's why the guards get their exception.
  • Don't fake it with a flag. $done = true; and an if (!$done) around every later step is a return in disguise, and harder to read than the real thing.
  • A guard that does work isn't a guard. If the early case needs logging too, it's part of the work. Let it set the result and fall through to the bottom with the rest.
  • Exceptions are another way out. Code above the return doesn't run when something throws. If it must run no matter what, it goes in finally.

    • Call the variable you return what it is: $cents, $user, $isAllowed. Never $result or $ret. Then the last line of every function tells you what it gives back, and a reader skimming for the return finds it at once.
