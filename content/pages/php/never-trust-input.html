Never Trust Input Phillip Harrington

Testing checks that your code does what you meant, with the values you thought to try. Security is about the values you didn't think of, sent on purpose by someone who wants your code to do something you didn't mean. Every lesson in this section is one way that goes wrong. This one is the rule under all of them.

Never trust input. Anything your code didn't make itself, check before you use it. Then, wherever it goes next, escape it for that place.

What's Input?

Anything that comes from outside your code. On the web, that's every part of every request, and more:

  • The URL: the path and the query string, $_GET. See Query Strings.
  • Form fields, $_POST, hidden ones included. See Forms.
  • Cookies, $_COOKIE. You set them, but the browser sends them back, and anyone can change them first. See Cookies.
  • Headers, in $_SERVER['HTTP_...']: User-Agent, Referer, Host, X-Forwarded-For, all of them. See What's in the Middle.
  • Uploads, $_FILES: the file, its name and the type the browser claims for it. See File Uploads.
  • The request body, from php://input: the JSON an API client sends.
  • Everything you read later: rows in your database, files on disk, answers from other people's APIs, emails, webhooks.

    • The last one surprises people. A comment sits in your database because a visitor typed it. Reading it back out a week later doesn't make it yours. It's still what they typed.

    What "Trust" Means

    Trusting a value means letting it decide something without checking it first: a price, a quantity, which file to open, which row to change, what HTML goes on the page, who is logged in. The browser is a program the visitor controls, and so is curl. Any value it sends can be anything at all: missing, empty, an array, a million characters long, not even valid UTF-8.

    On November 2, 1988, a program written by Robert Tappan Morris, a graduate student, spread across the early internet and slowed thousands of machines to a crawl. One of the ways it got in was fingerd, a small service that answered questions about users. It read each request into a fixed-size buffer with a C function, gets(), that never checks length. The worm sent a line longer than the buffer, and the extra bytes overwrote the program with the worm's own instructions. It was input nobody had expected anyone to send. How It Works

    The rule has two halves: check it on the way in, escape it on the way out.

    1. A value arrives. PHP hands it to you as a string, or an array of strings, or not at all. Nothing from a request arrives as a number or a yes or no.
    2. Check that it's there, and that it's a string. Add [] to a field's name, and PHP makes it an array, so this step is not optional.
    3. Check it against what you'll accept: a whole number from 1 to 10, an email address, one of the four sizes you sell. An allow list (what's allowed) beats a deny list (what's forbidden), because nobody can list every bad value.
    4. If it fails, refuse it. Answer with an error, usually a 422, and say what's wrong. Don't try to repair it into something valid.
    5. Use the checked value from then on, never the raw one. Anything that should be yours to decide, like a price or who someone is, comes from your own code or database, never from the request.
    6. When the value leaves your code, escape it for wherever it's going: htmlspecialchars() into a page, a prepared statement into SQL, escapeshellarg() into a shell command, rawurlencode() into a URL.

    Steps two to five keep out values that are wrong. Step six is for values that are perfectly valid and still dangerous in the wrong place: a name like O'Brien is a fine name and a broken SQL query. You need both halves, every time. The next two lessons, SQL Injection and XSS and Escaping Output, are what happens when step six is missing.

    Try It

    See for yourself how much of a request is up to the sender. In a folder, make show.php, which reports everything a request brought with it:

    Start the server:

    docker run --rm -it -p 8000:8000 -v "$PWD":/app -w /app php:8.4-cli php -S 0.0.0.0:8000

    Open http://localhost:8000/show.php in a browser, and you'll see what your browser chose to send. Then send a request of your own, and make all of it up:

    curl -A 'Definitely a real browser' -e 'https://example.com/trust-me' \ -b 'admin=yes' -H 'X-Forwarded-For: 1.2.3.4' -d 'price=1' \ 'http://localhost:8000/show.php?id[]=7&id[]=8' New here: The referer: the page the request claims it came from. Any address will do. At the end of a line, it means "the command keeps going on the next line." It's there so a long command fits on the page.

    Every line comes back exactly as you wrote it. A browser you never ran, a page you never came from, a cookie the server never set, an address that isn't yours, a form field the page doesn't have, and an id that's an array instead of a number. PHP didn't check any of it, and neither did anything else. That's your job.

    One more, with a byte that isn't valid UTF-8:

    curl 'http://localhost:8000/show.php?name=%FF'

    The name comes back as �, the replacement character, because the script asks json_encode() to swap bad bytes for it. Without that flag, json_encode() refuses the whole thing and returns false. Text is input too, encoding and all.

    In PHP
  • is_string($_POST['qty'] ?? null): there, and not an array. Check this first, every time.
  • filter_var($value, FILTER_VALIDATE_INT, ['options' => ['min_range' => 1, 'max_range' => 10]]) returns the number, or false. There are filters for floats, booleans, email addresses, URLs and IP addresses too.
  • in_array($value, $allowed, true), with the true, for an allow list. Without it, PHP compares loosely.
  • preg_match('/\A[a-z0-9-]{1,40}\z/', $slug) for a shape of your own. Anchor both ends with \A and \z, or the pattern can match part of the value and pass the rest.
  • mb_check_encoding($value, 'UTF-8') before you store text or measure it with mb_strlen().
  • http_response_code(422) when you refuse something: the request arrived, and the content is wrong.
  • On the way out: htmlspecialchars(), prepared statements with PDO, escapeshellarg(), rawurlencode() and http_build_query(), json_encode().
    • Gotchas
  • Anything can be an array. ?id[]=1 turns $_GET['id'] into an array, and code that expected a string crashes, or worse, carries on. Check with is_string() before anything else.
  • Hidden fields are visible and editable. type="hidden" only means the page doesn't draw it. Prices, user ids and roles never go in a form for the server to read back.
  • Missing, empty and "0" are three different things. empty() treats all three the same, and "0" is often a valid answer. Say exactly which you mean: isset(), === '', or a filter.
  • == is not a check. In PHP, "0e123" == "0e456" is true, because both look like numbers (zero, in scientific notation). Compare input with ===, and secrets with hash_equals().
  • Filters forgive a little. FILTER_VALIDATE_INT trims spaces from both ends before it checks, so " 3 " passes as 3. That's usually what you want. Know that it happens.
  • Don't repair, refuse. Stripping out the parts that look bad (strip_tags(), removing quotes) changes what people meant and still misses things. Check against what's allowed, refuse the rest, and escape on the way out.
  • The browser's checks don't count. required, maxlength and type="email" are for honest visitors. The server checks again, every time, as in Forms.
  • The Host header is input. Build a password reset link from $_SERVER['HTTP_HOST'], and someone can ask for a reset with their own host name in the header, and your email sends the victim to their site. Put your site's address in configuration, and build links from that.
    • Break It

    A shop that sells mugs, built the way a lot of real shops once were: the price rides along in a hidden field, so the order page can multiply it by the quantity. Make naive.php:

    Open http://localhost:8000/naive.php and buy two: $24.00. The browser won't let you type a quantity under 1 or over 10. Now go around it:

    curl -d 'qty=2&price=1' http://localhost:8000/naive.php

    Order total: $0.02 for 2 mugs. The server charged what the request said the price was. Then a quantity the form would never send:

    curl -d 'qty=-5&price=1200' http://localhost:8000/naive.php

    Order total: $-60.00 for -5 mugs. In a real shop, that's a refund for mugs nobody bought. And one more, an array:

    curl -d 'qty[]=1&price=1200' http://localhost:8000/naive.php

    Uncaught TypeError: Unsupported operand types: array * string, with your file's path and line number printed on the page for the visitor to read.

    Fix It

    The price belongs to the shop, so it lives in the code. The quantity belongs to the visitor, so it's checked: there, a string, a whole number, from 1 to 10. Anything else is refused with a 422. Make index.php:

    Send the same three attacks to http://localhost:8000/:

    curl -d 'qty=2&price=1' http://localhost:8000/ curl -d 'qty=-5' http://localhost:8000/ curl -d 'qty[]=1' http://localhost:8000/

    The first costs $24.00: the form has no price field to tamper with, and the one in the request is ignored. The second gets "Pick from 1 to 10 mugs." The third gets "How many mugs?" instead of a crash. Add -i to see the 422 on both.

    Whenever you finish a form, send it four things with curl before anyone else does: the field as an array (name[]=x), empty (name=), far too long (name=$(head -c 100000 /dev/zero | tr '\0' a)), and invalid UTF-8 (name=%FF). Each should get a polite refusal. A warning, a crash or a blank page means a check is missing.
