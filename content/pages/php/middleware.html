Middleware and Pipelines Phillip Harrington

REST's API checked the method and the content type at the top of every route, and a real one would check a token there too. That's the same few jobs, done for every request, before and after the code that's actually about notes. Middleware takes those jobs out of the routes and lines them up in front, as layers.

What's Middleware?

A small class with one method. It gets the request and the next thing in line. It can do something first, then pass the request on and get a response back, then do something to the response, then return it. Or it can decide the request goes no further, and answer by itself.

What's a Pipeline?

The line of middleware, with a handler at the end: the code that does the real work. The request travels in through each layer to the handler, and the response travels back out through the same layers, in reverse. People draw it as an onion.

In 1964, Doug McIlroy at Bell Labs wrote a memo saying programs should connect "like garden hose," the output of one screwed into the input of the next. Ken Thompson added pipes to Unix in 1973, and ls | grep php | sort has worked that way since. Middleware is the same idea, for a request. How It Works

With three layers, A, B and C, and a handler:

  1. A gets the request, does its "before" work, and calls next: B.
  2. B does the same, and calls C.
  3. C checks something, like a token. If it fails, C returns a 401 right there, and the handler never runs.
  4. If it passes, C calls the handler, which returns a response.
  5. The response goes back to C, then B, then A, and each can change it on the way out: add a header, log the status.

So the order is the design. A layer only sees what got past the layers outside it, and only changes what comes back through it.

In PHP
  • PSR-15 is the standard version of these two interfaces: MiddlewareInterface::process() and RequestHandlerInterface::handle(), from psr/http-server-middleware and psr/http-server-handler. Middleware written to it works in any framework that supports it.
  • PSR-7 defines the request and response objects they pass around. They're immutable, like the ones here: withHeader() returns a new response.
  • getallheaders() gives you the request's headers, in the built-in server and behind most web servers. They're all input. Never trust input.
  • random_bytes() for anything that should be unguessable, like a request id.
    • Gotchas
  • The order is a decision, every time. Error handling goes outermost, so it can catch everything. Logging usually goes just inside it. Anything that needs a logged-in user goes inside the login check.
  • A layer that forgets to call next stops everything. Every path through a middleware either returns its own response on purpose or calls $next->handle().
  • Not every route needs every layer. A health check for a load balancer shouldn't need a token. Most routers let you attach middleware per route or per group, instead of to the whole app.
  • Middleware is for every-request jobs. A rule about notes belongs in the notes code, not in a layer that runs for every request.

    • When AddRequestId makes an id, have the error log use the same one. Then a user who reports "it broke" can send you the X-Request-Id from the response, and you can find their exact error in the log in one search.
