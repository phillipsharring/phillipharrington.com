SQL Injection Phillip Harrington

Never Trust Input ended with a rule for values on their way out of your code: escape them for wherever they're going. SQL injection is what happens when the place is a database query and nobody did. It's one of the oldest attacks on the web and still one of the most common, and in PHP the fix is one habit you've had since PDO and Prepared Statements.

What's SQL Injection?

Your code builds a query by gluing input into a string of SQL:

$sql = "SELECT `name` FROM `members` WHERE `email` = '$email'";

You meant $email to be a value. But the database can't see where your SQL ends and the input begins; it gets one string and runs all of it. If the input contains a quote, it closes yours, and whatever comes after is SQL the visitor wrote. They've injected it.

What's a Prepared Statement?

A query sent in two parts. First the SQL, with a ? (or a name like :email) where each value goes. Then the values, separately. The database has already read the SQL before it sees the values, so a value can only ever be a value. A quote in it is a quote character, nothing more.

One of the first public write-ups of SQL injection appeared in December 1998, in the hacker magazine Phrack, by Jeff Forristal under the name rain.forest.puppy. He showed how web pages that pasted input into queries for Microsoft SQL Server could be made to run extra commands. More than 25 years later, it's still on every list of the most common web vulnerabilities. How It Works

The attack, against a query glued together from input:

  1. The attacker types a quote, ', into a field.
  2. Your code pastes it in. The query now has one quote too many, and the database answers with a syntax error. That error tells the attacker the field goes straight into SQL.
  3. They type something that closes your quote and adds a condition of their own: ' OR '1'='1. Now the WHERE is true for every row.
  4. Then a UNION, which tacks a second query of their choosing onto yours, and the page shows its results as if they were yours: any table, any column.

And the defense, with a prepared statement:

  1. PHP sends the SQL with a ? in it. The database reads it and plans it.
  2. PHP sends the value. The database puts it in the ? as data.
  3. The query looks for a member whose email is, character for character, ' OR '1'='1. There isn't one.

Escaping a value by hand, adding backslashes before its quotes, can also work, and it is how this was fought for years. It's easy to forget once, and once is all it takes. Prepared statements make the safe way the only way.

In PHP
  • $pdo->prepare('... WHERE `email` = ?'), then $statement->execute([$email]). Or named: :email, and execute(['email' => $email]).
  • PDO::ATTR_EMULATE_PREPARES => false makes PDO send real prepared statements to MySQL, instead of building the query itself with escaped values.
  • charset=utf8mb4 in the connection string, so PHP and MySQL agree on how the bytes are read. See Character Sets and Collation.
  • $pdo->query() only for SQL with no input in it at all. If you're about to put a variable in the string, stop and use prepare().
    • Gotchas
  • Column and table names can't be bound. A ? stands for a value, never for ORDER BY ?. For a sort column picked by the visitor, use an allow list: $column = match ($_GET['sort'] ?? '') { 'email' => 'email', default => 'name' };, then put $column in the SQL.
  • LIKE has its own wildcards. A bound value is safe, but a % or _ in it still matches anything. Escape those yourself if a search should take them literally.
  • IN (...) needs one ? per value. Build the placeholders, implode(',', array_fill(0, count($ids), '?')), and bind the values. Never implode() the values themselves into the SQL.
  • The database's data is input too. A value that went in safely through a prepared statement can still be pasted unsafely into a later query. Second-order injection, it's called. Bind it again, every time.
  • Error messages help the attacker. The naive page printed MySQL's complaint, with your file path. Turn display_errors off in production, as in Errors and the Error Log.
    • Break It

    Never trust input, and here's why. With Try It still running, start with one quote:

    curl --get --data-urlencode "email='" http://localhost:8000/naive.php

    The query is now WHERE `email` = ''', and the answer is a fatal error: "You have an error in your SQL syntax." The attacker now knows this field goes straight into SQL. Next, a condition that's always true:

    curl --get --data-urlencode "email=' OR '1'='1" http://localhost:8000/naive.php The query: SELECT `name` FROM `members` WHERE `email` = '' OR '1'='1' Found: Alice Found: Bob Found: Chloé

    Every member. Then a UNION, to read columns the page never meant to show. The -- - at the end starts a comment, which swallows your closing quote:

    curl --get --data-urlencode "email=' UNION SELECT CONCAT(email, ' ', password_hash) FROM members -- -" http://localhost:8000/naive.php Found: alice@example.com $2y$12$HEA59rdH50QDhKzo1h3G7Oxt0X.q59l7rP5Jio4u/kbNJ2Xd3TO4i Found: bob@example.com $2y$12$Tj1fZosmNkQQ1LO6zcMr9Or2WaIl8AfptGAbNefTZTTuIPPWS0ULa Found: chloe@example.com $2y$12$eVGWV53tJlybT6QhQDs45ebkfpm33TCNZzTT4i0uJ.FR1V4A6lHey

    Every email address and every password hash, from a page that was only ever supposed to say a name. The same trick reads any table the database user can.

    You may have heard of the attack that ends in DROP TABLE. Try '; DROP TABLE members; -- - here, and MySQL refuses it with another syntax error. With emulation off, PDO sends even query() as a real prepared statement, and MySQL allows only one statement in one of those. That's luck, not safety. The UNION didn't need a second statement.

    Fix It

    Make index.php. The SQL has a ?, and the email goes separately:

    Send it the same three:

    curl --get --data-urlencode "email='" http://localhost:8000/ curl --get --data-urlencode "email=' OR '1'='1" http://localhost:8000/ curl --get --data-urlencode "email=' UNION SELECT CONCAT(email, ' ', password_hash) FROM members -- -" http://localhost:8000/

    Each one gets "No member with that email." The database looked for a member whose email is that whole string, quotes and all, and found nobody. Honest lookups still work. docker compose down -v stops everything and deletes the database.

    In 2007, the webcomic xkcd ran "Exploits of a Mom": a school calls a mother because her son's name has broken their records, and the name is Robert'); DROP TABLE Students;--. She hopes they've learned to sanitize their database inputs. Developers have been sending each other that strip ever since, and "Bobby Tables" is the nickname the attack never lost.

    Search your code for SQL with a variable in it: grep -rnE "(query|exec)\(.*\\$" src/ finds query() and exec() calls with a $ in the line. Every hit is either SQL with no input in it, which is fine, or a prepared statement waiting to be written.
