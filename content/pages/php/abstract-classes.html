Abstract Classes Phillip Harrington

Say you have several reports. Each one has its own numbers, but they're all laid out the same way: a title, a line under it, a column of labels and values. Copy the layout code into every report, and the day you change it, you change it everywhere, and miss one. One class can be built on another, sharing its code. An abstract class is one built to be built on, and nothing else.

What's extends?

class SalesReport extends Report makes SalesReport a child of Report. The child gets every public and protected method and property of the parent, and can add its own, or replace the parent's with its own version (override them). A SalesReport is a Report: anywhere that wants a Report will take one.

A class in PHP has at most one parent. protected, from the last lesson, means "this class and its children."

What's an Abstract Class?

A class marked abstract can't be made with new. It exists to be extended. It can have finished methods, which every child shares, and abstract methods: a name and a signature with no body, which every child must write.

The usual shape: the parent does the part that's always the same, and calls abstract methods for the parts that differ. A method marked final can't be overridden, so no child can change the shared part by accident.

How It Works
  1. When PHP loads a class that extends an abstract one, it checks that every abstract method has been written, with a compatible signature. If not, it stops right there, before any of your code runs.
  2. new SalesReport() makes an object with the parent's methods and the child's together.
  3. $report->render() runs the parent's render(). Inside it, $this is the SalesReport.
  4. So when render() calls $this->rows(), it gets the child's rows.

In PHP
  • abstract class Report declares a class that can't be made directly.
  • abstract protected function rows(): array; declares a method every child must write. Note the semicolon where the body would be.
  • class SalesReport extends Report builds on it.
  • parent::render(), inside a child, calls the parent's version of a method the child has overridden.
  • final on a method stops children overriding it; on a class, stops anyone extending it.
  • #[\Override], above a method, asks PHP to check that it really does override a parent's method, and to stop if it doesn't.
    • Gotchas
  • Change the parent, change every child. A fix to the parent lands in every class built on it, including the ones that relied on the old behavior.
  • Deep family trees are hard to read. When a method is defined in a grandparent and overridden in a parent, finding out what $this->rows() actually runs means reading three files. Keep it to one level where you can.
  • One parent only. A class that wants to be two things at once can't extend both. That's a job for interfaces, the next lesson.
  • Protected isn't private. Anyone can extend your class and reach every protected property. Use private for what children don't need.
    • In 1987, Barbara Liskov gave a talk called "Data Abstraction and Hierarchy" that set out what became the Liskov substitution principle: a child should work anywhere its parent does, without surprising the code using it. A report that throws away its title or prints to a file instead of returning a string breaks the rule, even if PHP accepts it. Liskov, one of the first women in the United States to earn a PhD in computer science, won the Turing Award in 2008.

    Before you write extends, say it as a sentence: "a sales report is a report." If it sounds right, extend. If it sounds wrong ("a mailer is a logger"), you want one object to hold the other instead, and call it.
