Normalization Phillip Harrington

Relating Tables moved the authors out of the books table and into their own, so each name is written once. Normalization is that move, made into a habit: say each fact once, in the table it's about. It has a reputation for theory and numbered forms, but the idea fits in a sentence, and the reason for it fits in one Try It.

What's Normalization?

Arranging tables so that every fact is stored in exactly one place. A customer's email is a fact about the customer, so it lives in one row of customers. Not on every order she's ever placed.

When a fact is written in two places, the two can disagree, and then nobody knows which is right. Normalization doesn't make that rare. It makes it impossible.

The Normal Forms

Database books number the rules. The first three are the ones that matter day to day, and each fits in a line:

  • First: one value per column. No list of tags in a tags column, no phone1, phone2, phone3. A list is rows in another table.
  • Second: when the key is more than one column, every other column depends on all of it. In book_tags, keyed on book and tag, a tag's name depends on the tag alone, so it belongs in tags.
  • Third: no column depends on another column that isn't the key. An order's customer email depends on the customer, not the order, so it belongs in customers.

    • Put together: every column is a fact about the thing the table is about, and nothing else.

    Edgar Codd, a mathematician at IBM, published "A Relational Model of Data for Large Shared Data Banks" in 1970. It described data as tables related by values, and the first normal form came with it. He defined the second and third the year after. Most of what this section teaches, tables, keys and the rules about where facts go, traces back to those papers. How It Works

    To normalize a table, go column by column and ask whose fact it is:

    1. Find the thing the table is about: an order. Its key identifies one of them.
    2. For each column, ask: is this a fact about the order? The product it was for, yes. The customer's email, no: that's a fact about the customer.
    3. Move each fact that's about something else into that thing's table, and leave a foreign key in its place: customer_id.
    4. When you need them together again, join.

    Some facts look like copies and aren't. An order's price is what the customer paid that day. The product's price is what it costs now. They start out equal, and they're supposed to drift apart, so the order keeps its own.

    Breaking It on Purpose

    Sometimes you store a copy anyway, because working it out every time costs too much. A page that shows every customer with their number of orders would count all the orders of every customer, on every view. Storing an order_count on each customer makes that page cheap. It's a copy of a fact (the real one is the orders themselves), and it's fine, as long as you treat it like one:

  • Every piece of code that adds or removes an order updates the count, too.
  • Both changes happen together, or not at all.
  • You know which one is the truth (the orders), and you have a query that rebuilds the copy from it.

    • Do it when you've measured a real cost, not in advance. Most counts are cheap to work out, given the right index.

    Try It

    The same four orders, stored the flat way and the normalized way. The same compose.yml, Dockerfile and db.php as in SQL, and this init.sql:

    Start the database and open the mysql command:

    docker compose up -d --wait db docker compose exec db mysql -u app -papp-password course

    As in SQL: start the database in the background, then open mysql inside its container.

    Alice gets a new email address. In the flat table, code that updates "the order she's looking at" changes one row:

    UPDATE `orders_flat` SET `customer_email` = 'alice@example.org' WHERE `id` = 3; SELECT DISTINCT `customer_name`, `customer_email` FROM `orders_flat` WHERE `customer_name` = 'Alice Rivera';

    Alice now has two email addresses, and nothing in the database says which is current. Send her a receipt, and it's a coin toss. Now the normalized tables:

    UPDATE `customers` SET `email` = 'alice@example.org' WHERE `id` = 1; SELECT `orders`.`id`, `customers`.`email` FROM `orders` INNER JOIN `customers` ON `customers`.`id` = `orders`.`customer_id` WHERE `customers`.`id` = 1;

    One row changed, and all three of her orders show the new address, because there was only ever one. Then raise the price of a mug, and look at the old order:

    UPDATE `products` SET `price_cents` = 1400 WHERE `id` = 1; SELECT `orders`.`id`, `orders`.`price_cents` AS `paid`, `products`.`price_cents` AS `now` FROM `orders` INNER JOIN `products` ON `products`.`id` = `orders`.`product_id` WHERE `products`.`id` = 1;

    Paid 1200, now 1400. Both are true. Type exit. Last, the copy kept on purpose. place-order.php adds an order and bumps the customer's order_count, together:

    docker compose run --rm php php place-order.php 2 1

    Bo's order costs the new price, 14.00. Check the copy against the truth, from the mysql command again:

    SELECT `customers`.`name`, `customers`.`order_count`, COUNT(`orders`.`id`) AS `counted` FROM `customers` LEFT JOIN `orders` ON `orders`.`customer_id` = `customers`.`id` GROUP BY `customers`.`id`;

    The stored count and the real one agree: 3 and 3, 2 and 2. Run that query now and then in real life, too. docker compose down -v when you're done.

    In PHP
  • Read the current price from products, on the server, and copy it into the order. Who remembers the rule? Now let's not see the same hands. Never trust input: a price that arrives in a form is whatever the visitor decided to pay.
  • $pdo->beginTransaction() and $pdo->commit() around a change and its copy, so they can't come apart. Transactions has the rest.
  • SET `order_count` = `order_count` + 1 lets the database do the adding. Reading the count into PHP, adding one, and writing it back loses updates when two orders land at once.
    • Gotchas
  • A repeated value isn't always a repeated fact. Two customers who both live in Portland don't need a table of cities. Each one's city is a fact about that customer. It's only a copy when it has to change everywhere at once.
  • Lists in a column can't be joined, checked or indexed. 'classic,science fiction' in one column looks easy until you need every book with a tag, or need to rename one. Use a table with a row per item.
  • Copies drift. Store a count, and someday a script will delete an order straight from the database and forget it. Keep the rebuild query, and the truth, close by.
  • Don't point at a value that's meant to stay put. An order that looks up the product's current price shows the wrong total the day the price changes. Copy what has to stay as it was.

    • Whenever you store a copy on purpose, put a comment beside the column saying what it copies, and the query that rebuilds it, like the one on order_count in init.sql. The next person, or you in a year, will know which number to trust, and how to fix the other.
