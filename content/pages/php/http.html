HTTP, HTTPS and TLS Phillip Harrington

DNS gave the client an address, and it has opened a connection. Now the two of them need a language. On the web, that's HTTP, the Hypertext Transfer Protocol: the Spanish from the Client/Server lesson. It's simple on purpose. The client asks for something, the server answers, and that's one exchange.

What's HTTP?

The rules for that one exchange: a request, then a response. Each request stands on its own. The server doesn't remember you from one request to the next unless something reminds it (that's what cookies are for, later). And in its classic form, it's plain text you could read, or even type by hand.

The first version of HTTP, from 1991, had one method, GET, no headers and no status codes. You asked for a page, you got the page, and the connection closed. Its whole description fit on about a page. What's HTTPS?

The same HTTP, sent through an encrypted connection. Nobody between you and the server (the coffee shop Wi-Fi, your internet provider, anyone along the way) can read the conversation or change it.

What's TLS?

Transport Layer Security, the encryption that puts the S in HTTPS. Its older version was called SSL, and people still say "SSL" out of habit, but SSL itself has been broken and retired for years. TLS does two jobs: it scrambles the conversation, and it proves the server is who it says it is, with a certificate. A certificate is the server's ID card, vouched for by a certificate authority your browser already trusts.

What the Padlock Promises

Two things: the connection is encrypted, and you're talking to the domain in the address bar. That's all. It doesn't mean the site is honest. A scam site can have a perfectly good certificate for its own scammy domain.

So many people read the padlock as "this site is safe" that in 2023 Chrome replaced it with a neutral settings icon. Encryption had become normal, and the padlock had started promising something it never meant. How It Works

An HTTP request, as it travels, looks like this:

GET /hello HTTP/1.1 Host: example.com Accept: text/html

A method (GET, "give me"), a path, the protocol version, then a few headers, then a blank line to say "that's my request." The response comes back in the same shape:

HTTP/1.1 200 OK Content-Type: text/html Content-Length: 20469 <!doctype html>...

A status line (200 OK, "here it is"), headers, a blank line, then the page itself. Every part of those two has a job, and the next lesson goes through them line by line.

With HTTPS, one thing happens first: the TLS handshake. The client says hello, the server shows its certificate, the client checks it, and the two agree on keys. After that, exactly the same request and response travel through the encrypted connection.

HTTP/2 and HTTP/3

Same conversation, faster wire. HTTP/2 packs requests and responses into binary instead of text, and sends many of them at once over one connection instead of one at a time. HTTP/3 does the same over a different kind of connection that copes better with flaky networks, like a phone on a train. The requests and responses mean exactly what they meant in HTTP/1.1, and your PHP code sees no difference at all. Usually the CDN or web server in front of your app speaks HTTP/2 or 3 with browsers, and you get it for free.

Until about 2015, certificates cost money and took paperwork to get, so most of the web ran on plain HTTP. Then Let's Encrypt started giving them away, free and automatic, and within a few years most page loads were HTTPS. Now a site without it gets a warning. Try It

Same as before: a throwaway PHP container, with your folder as /app, running one file.

The first line is the status line: HTTP/1.1 200 OK. Then the response headers: the type of the content, when it was last changed, and a few that show a CDN answered (Cloudflare's, for example.com). Then the size of the page itself.

Now ask with curl, and add -v, for verbose:

curl -v https://example.com/ -o /dev/null

New here:

Verbose: show everything curl does along the way, not just the page. Write the page to a file instead of the screen. /dev/null is the file that throws away whatever goes into it.

The lines starting with * are the TLS handshake: the TLS version, the certificate's name and who issued it, when it expires. The lines starting with > are the request curl sent, and < the response. (-o /dev/null throws the page away so it doesn't fill your screen. On Windows, write -o NUL, and type curl.exe if plain curl does something odd.)

Look closely and the two clients didn't speak the same version: PHP said HTTP/1.1, and curl said HTTP/2. Same server, same page, same meaning.

In PHP
  • The request you're answering is in $_SERVER: $_SERVER['REQUEST_METHOD'], $_SERVER['SERVER_PROTOCOL'], and $_SERVER['HTTPS'], which is set when the connection to PHP was HTTPS.
  • header() adds a response header, and http_response_code() sets the status. Both have to happen before any of the page is sent.
  • file_get_contents() on a URL makes a simple request, and http_get_last_response_headers() shows what came back.
    • Gotchas
  • Behind a CDN, PHP may think it's plain HTTP. The browser talks HTTPS to the CDN, but the CDN may talk plain HTTP to your server, so $_SERVER['HTTPS'] is never set. Code that asks "is this HTTPS?" gets it wrong. One app of mine sent its login cookies without the "HTTPS only" flag for months because of exactly this.
  • Mixed content. An HTTPS page that loads an image or script over plain http:// gets that part blocked or flagged by the browser. Use https://, or a link that starts with /.
  • Certificates expire. Let's Encrypt certificates last 90 days, on purpose, so that renewing is automated. If renewal isn't automated, it will be forgotten, and the site will break on a Saturday.

    • curl -I and a URL asks for just the status and headers, no page. It's the fastest way to see what a server is actually saying: is it a redirect, and to where? Is it cached? Is it even up?
