MVC Phillip Harrington

Separating Concerns split a page into reading, deciding and showing, joined by a few lines of glue. MVC is that same split with names, and with the glue promoted to a part of its own. Nearly every PHP framework is organized around it, so it's worth knowing what each letter is for.

What's the Model?

The data and the rules about it: what a menu item is, which items are in a category, how to find one. Reading and deciding, from the last lesson, live here. The model knows nothing about HTTP or HTML. You could use it from a command-line script unchanged.

What's the View?

What goes back to the client: an HTML template, or JSON. It's handed what to show, loops over it, and escapes everything it prints. It doesn't fetch anything or decide anything.

What's the Controller?

The part that handles a request. It reads the input, checks it, asks the model for what's needed, picks a view, and returns the response with its status code. It should be short. When a controller grows long, the extra code is usually a rule that belongs in the model.

Trygve Reenskaug came up with MVC in 1978 and 1979, while visiting Xerox PARC, for Smalltalk. His first notes called it Thing-Model-View-Editor. Smalltalk itself came from the group around Alan Kay, Adele Goldberg and Dan Ingalls; Goldberg co-wrote the books that taught Smalltalk-80 to the world. MVC was designed for desktop programs, where a view watched its model and redrew itself when the model changed. The web version, with a request coming in and a page going out, came much later. How It Works
  1. A request arrives, and an entry point builds the parts and calls a controller.
  2. The controller reads the input it needs and checks it. Never trust input: this is the edge.
  3. It asks the model: "the drinks," "item 2."
  4. It hands the model's answer to a view, and gets back the page.
  5. It returns the page with a status code: 200, or 404 if there was nothing to find.

In PHP
  • Controllers and models are classes, one per file, found by Composer's PSR-4 autoloader. Views are plain PHP templates.
  • The controller gets what it needs through its constructor, here the Menu and the View, rather than reaching for them. That's Dependency Injection, and it's why the controller can be tested with a made-up menu.
  • Pass the controller $_GET as an argument instead of reading the superglobal inside it. Then it works the same in a test.
  • ob_start() and ob_get_clean() turn a template's output into a string the controller can return.
    • Gotchas
  • Fat controllers. Pricing rules, discount math and SQL in the controller mean they can only run during a request. Move them to the model, and the controller goes back to being glue.
  • Views that fetch. A template that queries the database is a model hiding in a view. Give it what it needs instead.
  • "Model" means more than the database table. It's all the rules and data of the app. Some of it maps to tables; some is plain classes with no storage at all. The next few lessons split it further.
  • Two entry points that are nearly the same file. index.php and item.php repeat their setup line for line, which is exactly what DRY warned about. With twenty pages, someone will forget a line in one.

    • A good controller method reads like a sentence: "check the category, get the items in it, show the list." If yours needs a paragraph, find the part that isn't about the request and move it into the model, where it can be named and tested.
