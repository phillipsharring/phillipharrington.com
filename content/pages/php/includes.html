Includes Phillip Harrington

A site with ten pages has one header and one footer, not ten copies of each. Put them in their own files, and have each page pull them in. That's an include. It's also how your functions, your settings, and eventually your whole app get split into files you can find things in.

What's an Include?

A line that tells PHP to run another file, right there, as if its contents were pasted in at that spot. PHP has four ways to say it:

  • require 'file.php';: run it, and if it's missing, stop with a fatal error. Use this one for anything the page can't do without, which is nearly everything.
  • include 'file.php';: run it, and if it's missing, warn and carry on.
  • require_once and include_once: the same, but skip the file if it's already been run. Use them for files that define functions, since defining a function twice is a fatal error.
    • Paths

    Build every include path from __DIR__, the folder the current file is in, as Document Root did: require __DIR__ . '/functions.php';. A bare 'functions.php' is looked up through a setting called include_path and the current directory, which can be anything depending on how PHP was started.

    A File That Returns

    An included file can end with return, and the include gives you that value. So a settings file can be just return ['site_name' => 'Example Shop'];, and $config = require __DIR__ . '/config.php'; hands it to you, with no global variable involved.

    Before PHP, early web servers like NCSA HTTPd had Server Side Includes: a comment in an HTML page, like <!--#include virtual="/footer.html" -->, which the server replaced with the other file before sending the page. Shared headers and footers were one of the first things anyone wanted from a web server, and it's one of the first things PHP made easy. How It Works
    1. PHP reaches the require line and works out the path.
    2. It reads that file from disk. Not through a URL: the file can be, and should be, outside the document root.
    3. It runs the file in the same scope as the line that included it. The included file sees the same variables, and any it sets are there afterward.
    4. The included file's output goes into the page at that spot, like everything else.
    5. When the file ends, or returns, PHP carries on from the line after the require.

    Shared scope is handy for templates: the header can print $config['site_name'] without being handed it. It's also why a big include can quietly overwrite a variable you were using. Files of functions don't have that problem, because each function gets its own scope, as Scope showed.

    curl -i 'http://localhost:8000/?page=../config'

    A 404 and "Not found." The page name has to be one on the list, so nothing a visitor sends ever becomes part of a path. Without that check, ?page= would be a way to run any .php file on the server, inside your page and with your variables. Never trust input, and never let it near an include.

    Last, the difference between include and require. Make missing.php:

    docker run --rm -v "$PWD":/app -w /app php:8.4-cli php missing.php

    The include warns and keeps going. The require stops the script cold.

    In PHP
  • require, for what the page needs; require_once, for files of functions.
  • include, only when the page really can go on without the file.
  • __DIR__ and dirname(__DIR__): this file's folder, and the one above, to build paths from.
  • $value = require 'file.php';: take what a file returns.
  • get_included_files(): every file run so far, in order.
    •  Gotchas
  • Never build an include path from input. require "pages/$page.php" with $page straight from the query string lets a visitor climb out with ../ and run files you never meant to be pages. Check against an allow list, as the example does. The Log Viewer project attacks this kind of path on purpose.
  • Relative paths depend on where PHP started. require 'functions.php' works when you run it from one folder and fails from another. __DIR__ every time.
  • Included files should be outside the web root. A config.php inside public/ can be requested by URL. It's run, not shown, so usually nothing leaks, until a server is set up wrong and sends it as text.
  • "Cannot redeclare." Including a file of functions twice, from two different places, is fatal. require_once it, or later, let an autoloader handle it: Autoloading with Composer and PSR-4.

    • When a page acts as if it's using the wrong settings or an old copy of a function, put error_log(print_r(get_included_files(), true)); at the bottom. It lists every file PHP actually ran, with full paths. More than once, the answer is a file with the right name in the wrong folder.
