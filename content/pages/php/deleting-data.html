Deleting Data Phillip Harrington

Updating Data ended with every price in the shop set to zero, and a ROLLBACK to put them back. DELETE has the same missing-WHERE mistake, and a worse result: the rows are gone, along with anything set up to go with them. This lesson is about deleting exactly what you mean to, and about the times you shouldn't delete at all.

What's DELETE?

The statement that removes rows:

DELETE FROM `posts` WHERE `id` = 1;

Which table, and which rows. Like UPDATE, it does every row that matches the WHERE, and every row in the table if there isn't one.

What Happens to the Children

When a row has other rows pointing at it with a foreign key, as in Relating Tables, the key says what happens when it's deleted:

  • RESTRICT, the default: the delete is refused while anything points at the row. A user with posts can't be deleted.
  • CASCADE: the rows pointing at it are deleted too. Delete a post, and its comments go with it.
  • SET NULL: the rows pointing at it stay, with their foreign key set to NULL. The column has to allow it.

    • Pick per key, by asking whether the child means anything without its parent. A comment on a deleted post doesn't. An order from a deleted customer still does, to your accountant.

    What's a Soft Delete?

    Not deleting the row at all, but marking it: a deleted_at column that's NULL until the moment it's "deleted." Nothing pointing at it breaks, and you can undo it. The price is that every query has to leave the marked rows out, forever.

    How It Works
    1. The database finds the rows that match the WHERE.
    2. For each one, it checks the foreign keys pointing at it. If any is RESTRICT and has rows, the whole delete is refused.
    3. It removes the rows, and does what each CASCADE or SET NULL says to the rows pointing at them, and to the rows pointing at those, all the way down.
    4. It answers with the number of rows deleted from the table you named. The cascaded ones aren't counted.

    Step three is why cascades need care. One DELETE of one row can empty half the database, if the keys are set up that way, and report that it deleted 1.

    docker compose up -d --wait db docker compose run --rm php php delete-post.php 1

    Posts deleted: 1, and of the four comments, one is left. The cascade deleted three more rows, and the count didn't mention them. Now try to delete a whole user, in the mysql command:

    docker compose exec db mysql -u app -papp-password course DELETE FROM `users` WHERE `id` = 1;

    Refused: Alice still has a post, and that key is RESTRICT. Good. Then the mistake, safely, inside a transaction:

    START TRANSACTION; DELETE FROM `comments`; SELECT COUNT(*) FROM `comments`; ROLLBACK; SELECT COUNT(*) FROM `comments`;

    Zero, then one again. Without the START TRANSACTION, there would be nothing to roll back to. Type exit. Last, the soft delete. close-account.php marks a user as gone, and lists who's left:

    docker compose run --rm php php close-account.php 2

    Bo's account is closed, and only Alice is listed. Bo's row, his post, and the comment on it are all still in the database, so nothing broke, and the account could be reopened. Try to sign him up again, from the mysql command:

    INSERT INTO `users` (`email`, `name`) VALUES ('bo@example.com', 'Bo');

    Duplicate entry. His closed row still holds the email address. That's the other price of soft deletes. docker compose down -v when you're done.

    In PHP
  • $statement->rowCount() after a DELETE is the number of rows removed from the table you named, not counting cascades.
  • The id to delete is input. Never trust input: check that it's a whole number, then check that the row belongs to whoever is asking, in the same WHERE: WHERE `id` = ? AND `user_id` = ?. Otherwise anyone can delete anyone's post by changing a number in a URL.
  • Deletes change things, so they come from a POST form, never a link. CSRF, in Security, is why.
  • With soft deletes, add WHERE `deleted_at` IS NULL to every query. A view or a single function that every query goes through makes it harder to forget.
    • Gotchas
  • A DELETE without a WHERE empties the table. Every row, at once, and with CASCADE, every row in the tables below it too. The same --safe-updates option from Updating Data refuses it.
  • Cascades are quiet. The count says 1, the database removed 300. Use CASCADE where the children truly belong to the parent, and RESTRICT everywhere else, so a surprising delete is refused rather than done.
  • Soft deletes leak. Forget the deleted_at IS NULL in one query, and closed accounts show up in a list, a count, or a search. And a unique column still sees the closed rows, as Bo found out.
  • Soft deleted isn't deleted. When someone asks you to delete their data, keeping it with a mark on it may not be enough. Privacy laws, like the European Union's GDPR, can require that it's really gone.
  • TRUNCATE isn't a fast DELETE. TRUNCATE TABLE empties a table by recreating it: it can't be rolled back, it resets AUTO_INCREMENT, and MySQL refuses it on a table that other tables point at.

    • Before any DELETE or UPDATE you type by hand on a real database, type START TRANSACTION;. Run the statement, read the row count, and SELECT to check. Then COMMIT; if it's right, or ROLLBACK; if it isn't. It costs two lines, and it's the only undo button SQL has.
