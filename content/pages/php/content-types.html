Content Types Phillip Harrington

Ever clicked a link expecting a page, and your browser downloaded a file instead? Or opened a page and got a screen full of raw code? Both come down to one response header, Content-Type. A response body is just bytes. The browser doesn't look at the bytes, or at the end of the URL, to decide what they are. It believes the header.

What's a Content Type?

A label in the form type/subtype, also called a media type or MIME type. The ones you'll see most:

  • text/html: a web page. Render it.
  • text/plain: plain text. Show it, tags and all.
  • text/css and text/javascript: a stylesheet, a script.
  • application/json: data, usually for JavaScript to read.
  • image/png, image/jpeg, image/webp: pictures.
  • application/pdf: a PDF.
  • application/octet-stream: "some bytes, no idea what." The browser downloads it.

    • Requests have content types too, when they carry a body. A form posts application/x-www-form-urlencoded, the name=value pairs from the last lesson, or multipart/form-data when it includes a file.

    MIME stands for Multipurpose Internet Mail Extensions. It was invented in the early 1990s so email could carry attachments, pictures and languages other than English. The web borrowed the labels wholesale, which is why the header that tells your browser "this is a web page" is named after email. What's a Character Set?

    Text types usually carry one more piece: text/html; charset=utf-8. The charset says how the bytes become letters. UTF-8 covers every language and every emoji, and it's the only one you should use. Get it wrong, and "café" turns into "cafÃ©."

    How It Works

    When a response arrives, the browser reads Content-Type and decides:

    1. Something it can show, like HTML, an image or a PDF? It shows it.
    2. Plain text? It shows the text as text.
    3. Something it can't show, or "no idea"? It downloads it.

    So the download mystery is the server, labeling something the browser can't display, or not labeling it at all. The file's extension doesn't enter into it. This site's own pages have no extension, /about and not /about.html, so its deploy has to tell the server, page by page, "this one is text/html." Without that label, the server would send them as unknown bytes.

    A second header can overrule the browser's choice. Content-Disposition: attachment says "save this, don't show it," even for a page the browser could show, and it can suggest a name for the file: attachment; filename="report.csv". That's how a site hands you a download with a proper name. Sending files gets a lesson of its own, later.

    Why "octet-stream" and not "byte stream"? On some early computers a byte wasn't eight bits; it could be six, or nine. Network standards wanted to be exact, so they said "octet," eight bits, every time. The name stuck around long after every byte became eight bits anyway. Try It

    Start it the usual way:

    docker run --rm -it -p 8000:8000 -v "$PWD":/app -w /app php:8.4-cli php -S 0.0.0.0:8000

    Same as before: -p 8000:8000 connects port 8000 on your computer to the container's, and php -S is PHP's web server.

    Then open each of these in your browser:

  • http://localhost:8000/: a heading and a paragraph.
  • http://localhost:8000/?as=text: the same bytes, tags showing.
  • http://localhost:8000/?as=json: labeled as data, and it isn't JSON. Firefox tries to show it as data and reports an error; Chrome just shows the text.
  • http://localhost:8000/?as=bytes: a download.
  • http://localhost:8000/?save=1: labeled as a web page, but downloaded anyway, as hello.html.

    • The body never changed. Only the label did. To see the labels themselves, ask with curl -I:

    curl -I "http://localhost:8000/?as=text"

    New here:

    Ask for the headers only (a HEAD request), and print them. No body. The quotes keep the terminal from reading the ? as one of its own wildcards. Quote any URL with a query string in it.

    In PHP
  • PHP sends text/html; charset=UTF-8 unless you say otherwise, and adds the charset to any text/ type you set. Both come from the default_mimetype and default_charset settings.
  • header('Content-Type: application/json'); before echo json_encode($data); is how an API answers.
  • header('Content-Disposition: attachment; filename="report.csv"'); makes a download.
  • mime_content_type() guesses a file's type from its contents, which is what you want for a file on your own server.
    • Gotchas
  • JSON labeled as HTML. Forget the header in an API, and every JSON response goes out as text/html. Some clients won't mind. Some will refuse it, and some will treat it as a page.
  • Never trust input. Not even the type a browser sends. An upload's content type comes from the client, which means from whoever is uploading. A script can arrive labeled image/png. File Uploads, in Security, is about exactly this.
  • Strict browsers. With the X-Content-Type-Options: nosniff security header, a browser takes the label at its word: a script sent as text/plain won't run, and a stylesheet with the wrong type won't apply. Good for safety, and a puzzle the first time it bites.

    • A page that downloads instead of showing, a script that won't run, an API response your code can't parse: before anything else, run curl -I on it and read Content-Type. It's the answer more often than it has any right to be.

    Content-Type tells the browser what it got. Another header, Set-Cookie, asks it to remember something. Next: cookies.
