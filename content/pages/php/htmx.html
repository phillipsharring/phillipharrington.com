HTMX Phillip Harrington

The search box in fetch() and AJAX took three files: a PHP endpoint that answered in JSON, and a script that turned the JSON back into HTML. htmx does the same job with no script of your own. PHP sends the HTML, already built, and a few attributes on the page say where to put it. It's optional: plenty of sites never need it. But it suits PHP, which has been building HTML on the server all along.

What's htmx?

A small JavaScript library, one file, that lets any HTML element make a request and put the answer somewhere on the page. You don't write JavaScript; you add attributes:

  • hx-get="/search", or hx-post: the request to make, like a link's href or a form's action.
  • hx-trigger="input changed delay:300ms": when to make it. Here, 300 milliseconds after the visitor stops typing. Buttons and forms default to click and submit.
  • hx-target="#results": which element the answer goes into. Without it, the element that made the request.
  • hx-swap: how. The default replaces what's inside the target; outerHTML replaces the target itself, and beforeend adds to the end.
    • Fragments

    What the server sends back: not a whole page, just the piece that changes, like a few <li> elements. htmx adds the header HX-Request: true to its requests, so PHP can tell them apart from a normal visit and answer with the fragment alone.

    htmx is by Carson Gross, and it isn't his first try at the idea. It came out in 2020 as the successor to intercooler.js, a library of his from years earlier that did the same thing with jQuery underneath. htmx dropped the dependency. How It Works
    1. The page loads htmx with a <script> tag.
    2. htmx reads the page and finds the elements with hx- attributes.
    3. The trigger happens. htmx sends the request, with the element's value if it has a name, and HX-Request: true.
    4. PHP sees the header, and answers with only the fragment.
    5. htmx swaps it into the target. Nothing else on the page changes.

    The fragment is HTML going straight into the page, so everything from XSS and Escaping Output applies, every time. Never trust input: escape every value in the fragment, exactly as you would in a whole page. And an hx-post that changes something is a POST that changes something, with the same CSRF protection as a form.

    Try It

    The color search again, in one PHP file. Without JavaScript, it's a plain form. With htmx, it updates as you type. In a folder, make a public folder, and in it, index.php:

    Start it:

    docker run --rm -it -p 8000:8000 -v "$PWD":/app -w /app php:8.4-cli php -S 0.0.0.0:8000 -t public

    Open http://localhost:8000 and type b. The list fills in without a reload. Watch the Network tab: each pause in typing is one request, and the answer is just the list items. Ask the way htmx does, then the way a plain browser does:

    curl -H 'HX-Request: true' 'http://localhost:8000/?q=b' curl 'http://localhost:8000/?q=b'

    The first is three <li> lines. The second is the whole page, with the same three already in it. Turn JavaScript off in your browser, type b and press Search: the form still works, the old-fashioned way, because it was a real form all along.

    In PHP
  • $_SERVER['HTTP_HX_REQUEST'] is 'true' when htmx is asking. It's a header, so it's only a hint about what to send back, never a reason to trust the request.
  • A function that renders the fragment, like results(), called both for the fragment and inside the full page, keeps the two from drifting apart.
  • header('Vary: HX-Request'), because one URL now has two answers, and a cache must not mix them up.
  • Response headers like HX-Redirect and HX-Trigger let PHP tell htmx to go to another page or to fire an event.
    • Gotchas
  • A fragment needs escaping like a page. It's easy to forget in a function that prints a few list items. htmlspecialchars() on every value.
  • Without Vary, a cache can serve the fragment as the page. Someone opens the URL and gets three bare list items, no page around them, because the cache kept htmx's answer.
  • Error responses aren't swapped in. By default htmx ignores a 4xx or 5xx answer, and the page just doesn't change. Show errors with a 200 and a message in the fragment, or tell htmx how to handle them.
  • Pin the version. Load an exact version, like htmx.org@2.0.4, never "latest," and add the integrity hash so the browser refuses a file that's been changed.

    • Make the page work as plain links and forms, the way Forms did, and add the hx- attributes last. If htmx fails to load, the page still works, and each attribute is a small change you can take back out.
