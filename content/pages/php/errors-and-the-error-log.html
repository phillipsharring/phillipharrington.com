Errors and the Error Log Phillip Harrington

Every lesson so far has had a line that went wrong on purpose: a header sent too late, a TypeError, a missing variable. Each time, PHP said something. What it says depends on how bad the problem is, and where it says it depends on a few settings. On your computer, you want every message in your face. On a live site, you want every message in a log and none of them on the page.

What's an Error?

PHP's way of telling you something went wrong. They come in levels:

  • Deprecated: this works now, and will stop working in a future version of PHP. Fix it before you upgrade.
  • Notice: something minor, which might be a mistake. PHP 8 turned most of these into warnings.
  • Warning: something is wrong, and PHP carries on anyway. Reading a variable or array key that doesn't exist is a warning, and you get null. Carrying on is often worse than stopping: the page runs with a hole in it.
  • Fatal error: PHP stops the script, right there. A parse error, a typo in the code itself, is fatal before anything runs.
    • Exceptions

    An exception is an error your code can catch and handle. Code throws one with throw new RuntimeException('...'), and PHP throws its own for many problems: a TypeError, a ValueError, dividing by zero. If nothing catches it, it becomes a fatal error: "Uncaught RuntimeException." Catching them is Exceptions and Try/Catch.

    The Error Log

    A file, or a stream, where PHP writes one line per error: when, what, which file, which line. It's the same idea as the server logs in Access and Error Logs, and often the same place.

    On September 9, 1947, Grace Hopper's team working on the Harvard Mark II found a moth stuck in one of its relays. They taped it into the logbook with a note: "First actual case of bug being found." Engineers had called faults bugs for decades already, which is the joke. The page, moth included, is at the Smithsonian. It's also, fittingly, an entry in a log. How It Works

    When something goes wrong, PHP asks four settings what to do:

    1. error_reporting: which levels count at all. Use E_ALL, everything, which is PHP 8's default.
    2. display_errors: print the message into the output, so it shows up on the page. On while you're building. Off in production, always.
    3. log_errors: write the message to the error log. On, everywhere.
    4. error_log: where the log is. Set it to a file path, or leave it empty and PHP hands the message to whatever is running it: the terminal for the command line and the built-in server, the web server's own error log under Apache, PHP-FPM's log under FPM.

    Why off in production: an error message is written for you, and it's full of things nobody else should see. File paths, the line of code that failed, sometimes the SQL query, sometimes a value from your settings. On a live page, it's a free map of your app for whoever is attacking it.

    Where the Log Is in Docker

    A container's habit is to write logs to its own output, not to files, and PHP's images follow it: with no error_log set, messages go to the terminal you started the container in, or to docker logs and the container's name if it's running in the background. The official PHP-FPM images point FPM's log there too. When you're hunting for "the PHP log" in a container, start with docker logs.

    Try It

    A page that goes wrong two ways, run with development settings, then production ones. In a folder, make index.php:

    Start it the way you would while building, with errors on the page and in the log. The -d flag sets a setting for this one run:

    docker run --rm -it -p 8000:8000 -v "$PWD":/app -w /app php:8.4-cli php -S 0.0.0.0:8000 -d display_errors=1 -d log_errors=1

    Only the new parts:

    Set one PHP setting for this run: show errors in the page. (This is PHP's -d, after php; it has nothing to do with curl's.) And another: write errors to the log, here the terminal.

    From a second terminal:

    curl -i 'http://localhost:8000/?problem=warning' curl -i 'http://localhost:8000/?problem=exception'

    The warning is right there in the page, "Undefined array key," and the page carried on to "Order 1001 is done" with a blank where the email should be. The exception stopped everything, and its message, with the file path and line, is in the page too. And look at the status: 200 OK. The error message was output, so the headers had already gone out, success code and all.

    Every message also went to the first terminal, along with the line from error_log(). Stop the server and start it with production settings:

    docker run --rm -it -p 8000:8000 -v "$PWD":/app -w /app php:8.4-cli php -S 0.0.0.0:8000 -d display_errors=0 -d log_errors=1

    Run the same two curls. The warning page shows nothing wrong, just the blank. The exception gets 500 Internal Server Error and an empty page: no path, no line, nothing for an attacker. Everything is still in the first terminal, which is where you'd look.

    One more thing the example does: it only logs problem if it's one of the two known values. Never trust input, not even in a log. A value with a new line in it can forge a whole fake line in your log file.

    In PHP
  • In php.ini: error_reporting = E_ALL, display_errors = Off, log_errors = On, and error_log if you want a file.
  • In Docker, start from PHP's own production settings: RUN cp "$PHP_INI_DIR/php.ini-production" "$PHP_INI_DIR/php.ini" in your Dockerfile.
  • php -d display_errors=1 ...: one setting, for one run.
  • ini_set('display_errors', '1'): change it from code. Too late for a parse error in the same file, which happens before any code runs.
  • error_log('message'): write your own line to the same log.
  • docker logs -f and the container's name: follow a container's log.
    •  Gotchas
  • display_errors on a live site. Paths, code, queries and settings, on the page, for anyone who can make your code fail. And attackers try to make it fail, precisely to see what it says.
  • A fatal error can still say 200. If anything was printed before it, the headers are gone, and the broken page goes out as a success. Monitoring that only counts 500s won't see it.
  • Warnings are bugs. PHP carries on after a warning, with null where a value should be. Treat every warning in the log as a bug to fix, and keep the log empty enough that a new one stands out.
  • The @ operator hides errors. @file_get_contents($path) silences the warning, and you're left with false and no idea why. Check the result instead.
  • Input in a log is input. Log the values you've checked, or encode the ones you haven't with json_encode(), so a new line can't start a fake entry.

    • When you can't print to the page, like in the middle of a redirect or an API response, dump to the log instead: error_log(print_r($thing, true));. The true makes print_r() return the text instead of printing it. Watch it arrive with docker logs -f in another terminal, and take the line out when you're done.
