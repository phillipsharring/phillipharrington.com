Model, Table, Mapper Phillip Harrington

CRUD's src/notes.php ran the SQL and handed back rows as plain arrays. That's fine for one page. Once a note travels through an app, you want it to be a real object with rules, and you want the SQL in one place. MVC called all of that "the model." This lesson splits it into three parts, each with one job.

What's the Model?

A class for one thing: a Note, with typed properties and the rules that make it valid. A note is 1 to 500 characters, so its constructor refuses anything else. It has never heard of a database. You can make one, change one and test one with no database anywhere.

What's the Table?

A class for one database table: NotesTable, holding the connection and the SQL. Insert, find, list, update, delete. It speaks in rows, plain arrays with the table's column names, and knows nothing about Note.

What's the Mapper?

The translator between them: NoteMapper turns a row into a Note, and a Note into a row. That's where created_at the string becomes createdAt the DateTimeImmutable, and where column names meet property names. No SQL, and no rules of its own.

Martin Fowler's Patterns of Enterprise Application Architecture (2002) named most of the ways to connect objects to tables. A class for a table's SQL is a Table Data Gateway. A class that moves data between objects and the database while keeping them independent is a Data Mapper. A class that is a row and saves itself is Active Record, which is what Rails and Laravel's Eloquent use. How It Works

Saving a note:

  1. Your code makes a Note. If it breaks a rule, it never exists.
  2. The mapper turns it into a row.
  3. The table inserts the row, with a prepared statement.

And reading one is the same, backwards:

  1. The table finds the row.
  2. The mapper turns it into a Note, which checks its rules again.
  3. Your code gets a Note, never a raw row.

Each part changes for one reason. A new column changes the table and the mapper. A new rule changes the model. Moving to another database changes only the table.

Then the interesting part: the demo slips a blank row straight into the database with SQL, the way a bug or an old script might, and the mapper won't turn it into a Note. The rows in your own database are input too. Never trust input, even from yourself, and the model's constructor is where that's enforced, every time.

In PHP
  • final readonly class (PHP 8.2) for models: properties set once in the constructor, never changed. A change makes a new object, like withBody().
  • Constructor promotion, public function __construct(public string $body), keeps a model short. See Modern PHP.
  • The table takes the PDO in its constructor, never makes its own. That's Dependency Injection, and it's how a test can hand it a test database.
  • DateTimeImmutable::createFromFormat() to read a DATETIME column, and ->format('Y-m-d H:i:s') to write one.
  • $mapper->toModel(...), with the three dots, makes a function you can pass to array_map() to map a whole list of rows at once.
    • Gotchas
  • Rules in the table are rules in the wrong place. If NotesTable::insert() checks the length, then a Note made anywhere else can still be invalid. The model owns its rules.
  • Keep the database's rules too. NOT NULL and VARCHAR(500) are a second line of defense for whatever skips your PHP. They aren't instead of the model's check.
  • Active Record is simpler, until it isn't. A model that saves itself ($note->save()) is less code at first. It also means every model needs a database to exist, which makes testing it harder and ties its rules to its storage.
  • You'll also hear "repository." Usually it's a class that hides a table and a mapper behind methods like find(int $id): ?Note. Same parts, one front.

    • Because Note has never heard of MySQL, its tests need nothing: make one with a blank body, expect the exception. That's a test that runs in a millisecond. Put as many rules as you can in the model, and most of your tests get that fast.
